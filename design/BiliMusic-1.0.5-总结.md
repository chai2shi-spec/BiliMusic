# BiliMusic 1.0.5 优化与改变总结

> 版本区间：`versionCode 1000004 → 1000005`（`AppScope/app.json5`，2026-10-06 00:39 递增）
> 覆盖开发期：**2026-10-04 ~ 10-06**，共 3 天，十几轮迭代，每轮均编译通过（ERROR 0）
> 基线版本：1.0.4（10-03 22:00）

---

## 一句话概括

这一版的重心**不在堆功能，而在「把已有能力接通 + 把地基修好」**：
新增 4 个用户可感知的功能（UP 主页订阅、搜 UP 主、整单下载、下载重试、歌单导入导出），
修掉 3 个会导致数据丢失或体验事故的隐患，同时做了一次全工程体检把技术债清了一轮。

---

## 二、新增功能（用户可感知）

### 1. UP 主主页 + 投稿订阅（10-03 落地，1.0.5 期间持续修复）

新增 `pages/UpSpacePage.ets`：

- UP 资料头（头像 / 昵称 / 粉丝 / 签名）+ 投稿列表（30 条/页，`onReachEnd` 三重闸门）
- **订阅投稿** → 新投稿自动进本地订阅歌单；「拉取新投稿」按 `pubdate` 排序，新的排前面、超限丢最旧
- 曲目「⋯」菜单从 4 项变 5 项，多出「进入 UP 主主页」
- 数据模型：`Track` 加 `upMid`、`Playlist` 加 `upMid`/`upName`

**这一路踩了 B 站风控的坑，最终方案是「搜索反查」**（详见第五节）。

### 2. 搜索 UP 主（10-05）

搜索框同行加「视频 / UP主」切换，命中 `search_type=bili_user`：

- UP 行显示头像 / 昵称 / **认证徽章**（`verify_info`）—— 匿名搜 UP 最需要的信息，用来区分官方号与同名搬运号
- 「95.1 万粉丝 · 258 个投稿」友好化显示
- 新增 `NavStackHolder.upFace`，搜索结果自带头像 → UP 主页首帧就有图

闭环：**搜 UP → 进主页 → 订阅 → 新歌自动进订阅歌单**。

### 3. 歌单整单下载（10-04）

- 入口在歌单「⋮」菜单（不是行内按钮 —— 避免热区拥挤）
- 批量入队**串行 + 每首间隔 350ms**（`requestDownload` 内部每首都发一次 view 请求，密集请求会被限流）
- 下载管理里按**「歌单卡片」归组**，展开才见单曲；歌单组优先级高于分 P 归组
- 踩到重大坑：**鸿蒙 RDB 没有版本升级钩子**，加列必须自己写幂等迁移（见第四节）

### 4. 下载失败重试（10-04）

之前失败后唯一操作是「删除」，删了还得回搜索页重找。现在三层入口：

- 失败行右侧显式「↻」按钮（44vp 命中区）
- 失败行整行点击 = 重试
- 多选栏「重试选中」/ 组头「重试本组失败项」

关键约束：重试**只重排这一条**，不经 `expandVideoParts`（那会把用户手动删掉的分 P 偷偷排回来）。

### 5. 歌单导入 / 导出（10-05）

剪贴板方案，入口在设置页：

- 导出 JSON → 剪贴板；导入先读剪贴板判断「像不像歌单数据」，像才弹确认框
- 导入侧容错齐备：id 撞了自动重生成、名字重了加「导入」后缀、缺封面取第一首、畸形条目跳过并计数

### 6. 播放页加「下载」「加入歌单」按钮（10-05）

控制区功能键行从 2 个变 4 个（左边播放模式 + 右边一组）。

### 7. 蓝牙断开自动暂停（10-03）

新增 `service/AudioRouteWatcher.ts`：蓝牙耳机断开时暂停 + toast「蓝牙已断开，已暂停播放」。

## 三、优化与体验改进

### 播放页进场动效（10-03，方案 A + B 合并落实）

原问题有三个，都能从参数算出来：封面 300ms 到位而整页 360ms 落（**60ms 错位窗口**）；
整页 `translate y=128` 污染共享元素目标框导致封面**走弧线**；进场有动画而返回没有。

改法：

- 统一 300ms + `EaseInOut`（原来封面 EaseInOut / 整页 Friction，曲线不一致）
- 整页**只淡入**（`ENTER_RISE` 归 0），5 个子组件按 0/90/210ms 错峰浮现
- 补 POP 分支做镜像退场（240ms），进出对称
- `gotoPlayer()` 加连点防护

### 全站顶栏统一为毛玻璃（10-06）

8 个页（搜索/歌单/下载/设置/歌单详情/最近/关于/UP主页）全部统一为自绘 `GlassTopBar`：

- `opacity = 0.62 基线 + 0.38 × reveal` → **静止时也有淡毛玻璃**，滚动时增强到完全显影
- 材质用 `backgroundEffect` 真高斯模糊（`systemMaterial` 会静默不渲染，已弃用）
- 粉色光晕与粉色细线按要求移除

### UI 铁律修复（10-04）

- `UpSpacePage` 3 个 32vp 按钮外包 44vp 命中区（触达铁律：视觉可以小，命中区必须 ≥44）
- `SearchPage:1504` `fontSize(15)` → 16（15 是禁用档）
- `AppToast` 硬编码 `Color.White` → 走 `app.color.brand_on` 语义 token

### 访客 Cookie 补齐（10-03）

`BiliDevice.completeVisitorCookie()` 补齐 `b_nut` / `_uuid` / `b_lsid`（原来只发两个字段）。
**这是全局收益** —— 首页推荐等接口同样受益。

## 四、修复的隐患（这才是这一版最值钱的部分）

### 1. 歌单存储溢出（10-03，**最严重**）

实测 `slimTrack` 后单条约 **519 字节** → 整张歌单塞进一个 Preferences key 时，**超过约 11 首 `put()` 就抛错**。
症状是「加了歌、重启后消失」。**这不是订阅功能引入的，是一直存在的隐患。**

改为分片存储：元信息留 `PREF_PLAYLISTS`（含 `chunkCount`），曲目每 8 条一片存 `pl_tracks_{id}_{n}`，上限 200 首，旧格式按 `chunkCount` 分流兼容。

### 2. 导出文件泄漏本机路径（10-05）

`createPlaylistsExport()` 直接返回内存快照，曲目带着 `localFilePath`（本机绝对路径）。
导到别的设备上必然无效，还误导人以为「导入后能离线播」。现在导出逐首清空该字段，导入侧对称处理。

### 3. RDB 加列没有迁移（10-04）

`StoreConfig` 没有 `version` 字段，`RdbStore.version` 是**只读**，`CREATE TABLE IF NOT EXISTS` 遇到已存在的表什么都不会做
→ 老用户的库没有新列，之后每次 insert 都报 `no such column`。而原 `initRdb` 里两个版本分支代码完全一样，
是「看着有版本逻辑、其实从来没有」。

解法：`ensureColumns()` —— `PRAGMA table_info` 查已有列 → 缺则 `ALTER TABLE ADD COLUMN`（SQLite 不支持 `IF NOT EXISTS`，必须先查）。

### 4. 一次严重误判被编译当场打回（10-04）

体检结论说「10 处 `showAlertDialog` 无 `.catch()` → 闪退」，改完编译直接报 `Property 'catch' does not exist on type 'void'`。
**`showAlertDialog` 返回 `void`，根本不是 Promise**。我照搬了子代理结论没查 SDK 就动手。

三个弹窗 API 的真实返回类型已记入记忆：`showAlertDialog` → void、`showToast` → void、`promptAction.showDialog` → Promise。

## 五、B 站接口风控：这一版最大的技术收获

### 匿名可用性实测矩阵（10-05，12 个接口逐个真打）

| 结论 | 接口 |
|---|---|
| ✅ 匿名可用 | `view`、`archive/related`（**实测 40 条，之前没发现**）、`card`、`popular/series/list`、`search/type?bili_user` |
| ⚠️ 已失效 | **`ranking/v2` 排行榜（工程现用，复测 2 次都是 -352）** |
| ❌ 不可用 | 空间投稿、每周必听、热搜、弹幕、评论、歌词候选（已下线）、稍后再看、收藏夹 |

**核心结论**：B 站对「榜单 / 空间」类接口的匿名风控明显严于「搜索 / 详情 / 关系」类。
新功能必须建在后者上 —— 排行榜页签这阵子是空的就是这个原因。

### 「订阅 UP 投稿」的三次返工（10-03）

| 轮次 | 当时的结论 | 实际情况 |
|---|---|---|
| 20:15 | 412 = 访客身份不完整；`jsonp=jsonp` 是关键 | ❌ 误判 |
| 20:25 | 补 cookie 就能过 | ❌ 降级为「预防性措施」 |
| 20:45 | 根因是「搜不到」不是「被限」 | ✅ 正确 |

**最终方案**：`getUserVideosViaSearch()` —— 用「UP 昵称」搜视频再按 `mid` 精确过滤 + `order=pubdate` 时间排序。
理由不只是绕开限流，而是**语义更契合**（订阅只关心新投稿，本来就不需要翻到最老的）。
空间接口降级为兜底（3 次重试 × 间隔 2.5s，单次成功率约 20%）。

### 方法论沉淀

- **任何「改了 X 之后就好了」的结论，必须先做重复实验（≥8 次）** —— 同一天同一接口给过三个互相矛盾的结论，全部来自限流抖动
- **同 IP 同时刻做单变量对照实验**，才能区分「代码错」与「平台风控」
- **`code=0` 不代表有数据**（`acc/info` 永远 code=0 但只有 `v_voucher`）；**HTTP 200 也不代表成功**（412 是连 JSON 都没有的一层）

## 八、这一版最值得记住的三件事

1. **「加了歌重启后消失」不是功能 bug，是 519 字节 × 11 首的存储溢出** —— 隐患一直存在，订阅功能只是把它暴露出来。
2. **B 站对「榜单/空间」类接口的匿名风控远严于「搜索/详情」类** —— 选错接口，功能就是空的；选对了，零依赖就能做。
3. **任何「缺失 / 不可用 / 已修好」的结论都要落到具体值或编译结果上** —— 这一版里我照搬结论导致 10 处 `.catch()` 误判，
   也把限流抖动当成参数规律（一天内给过三个矛盾结论）。这类错误编译器每次都会当场打回，但前提是**真去编译**。
