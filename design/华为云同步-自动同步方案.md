# 华为云同步 · 自动同步歌单与拾音数据

> ⚠️ **已被 `华为云空间同步-方案.md` 取代**（需求澄清为「华为云空间」而非「华为云」）。
> 本版走的是华为云 OBS 自建桶路线，**仅作 Plan C 参考**；其中 **§5 同步协议整段仍然有效**，
> 新方案直接沿用。作废的是存储层与凭证层（AK/SK、endpoint、bucket、费用、签名）。

> 目标：换机 / 多设备（手机 + 平板）时，歌单（**含订阅 UP 歌单，不含 B 站收藏夹镜像**）与拾音（听歌日记）数据自动保持一致。
> 本文只给方案与实施规格，**不含代码改动**。
> 落点结论：**华为云 OBS 对象存储 + 客户端直连（V4 签名）+ 「每设备独立写域 · 读取端合并」协议**。

---

## 0. 一句话方案

把「歌单」和「拾音会话」序列化成 JSON / JSONL，按 **设备 → 对象** 的层级写进华为云 OBS；每台设备**只写自己的前缀**（`devices/{id}/`），读取时把**所有设备的对象做并集/三路合并**。
并发写冲突被结构性消除 —— 不存在「两台设备同时 PUT 同一个对象」，因此不需要分布式锁、不需要条件写、不需要服务端。

## 1. 先看清要同步的东西（这决定协议形状）

### 1.1 数据盘点

| 数据 | 真源 | 结构 | 单条体积 | 量级估算 | 变更语义 |
|---|---|---|---|---|---|
| 歌单元信息 | `LibraryStore`（Preferences 分片） | `Playlist` 14 字段 | ~300 B | 10~50 个 | **可变**，随时改名/改封面 |
| 歌单曲目 | 同上（`pl_tracks_*` 分片） | `Track`（`slimTrack` 后） | ~480–560 B | 20 歌单 × 80 首 ≈ 1600 首 → ~800 KB | **可变集合**，增删排序 |
| 拾音会话 | `PlaySessionStore`（`filesDir/listen_log/YYYY-MM.jsonl`） | `PlaySession` 10 字段 | ~220 B | 每天 30 首 × 395 天 ≈ 1.2 万条 → ~2.6 MB | **只追加**，永不修改 |

合计 < 5 MB。这个体积是方案选型的**决定性事实**：不需要分页接口、不需要增量协议、不需要数据库，整对象读写完全够。

### 1.2 同步范围（逐条钉死）

**同步：**
- 普通歌单（`sourceKind === ''`）
- 订阅 UP 歌单（`sourceKind === 'up'`，带 `upMid` / `upName`）—— 曲目由 B 站投稿拉取，**歌单本身**要同步；另一台设备不需要重新拉全量投稿，直接拿合并后的曲目
- 拾音 `PlaySession` 全部字段（13 个月保留窗内）

**不同步（必须显式过滤，不是"忘了做"）：**
- **B 站收藏夹镜像**（`sourceKind === 'fav'`）。理由：它是 B 站账号侧数据的**投影**，真源在 B 站。上传后另一台设备会拿到一份「看起来像本地歌单」的镜像，而 `FavSyncManager` 的镜像识别依赖 `sourceKind` 与 `upMid = fav_{mediaId}`；一旦云端带过来一份降级过的副本，就会出现「同一收藏夹两个镜像」，`getFavMirrorByMediaId` 只取首个，另一个永远不再被同步也不会被清理（`importPlaylistsFromParsed` 里已有同样注释警告）
- 最近播放 / 播放进度 / 当前播放队列（设备本地语义，同步会造成互相打断）
- 下载文件、歌词缓存、首页推荐缓存、封面缓存
- 登录 Cookie、`access_key`、`refresh_token`（**红线**，永不上云）
- `Track.localFilePath`（本机绝对路径，换机必然无效）、`audioUrl` / `videoUrl`（带签名会过期）
- 所有 App 设置项（音质、音量、主题）—— 属于 P3，默认不做

### 1.3 两种数据的同步语义完全不同（方案的核心分野）

| | 拾音会话 | 歌单 |
|---|---|---|
| 变更类型 | 只追加（append-only） | 覆盖 + 集合增删 |
| 冲突 | **不存在**。`(trackId, startedAt, ms)` 是天然唯一键 | 存在。两台设备可能改同一个歌单 |
| 合并 | 并集 + 去重 | 三路合并（元信息 LWW / 曲目按 id 集合合并） |
| 删除传播 | 不需要 | 需要墓碑 |
| 现成能力 | ✅ `PlaySessionStore.mergeBackupSessions` 已经实现了消毒 + 保留窗过滤 + 逐月去重 + 串行追加 | ❌ **不能**用 `importPlaylistsFromParsed`（见 §4.1） |

也就是说：**拾音那半几乎不用写新逻辑**，难度全在歌单。

## 2. 落点选型：为什么是 OBS 直连

| 方案 | 客户端依赖 | 服务端 | 并发冲突 | 配置门槛 | 判断 |
|---|---|---|---|---|---|
| **A. 华为云 OBS 直连** | 仅 `@kit.CryptoArchitectureKit`（现算 V4 签名）+ 既有 `HttpUtil` | 无 | 用「每设备写域」结构性消除 | 建桶 + IAM 子账号取 AK/SK（一次性 5 分钟） | ✅ **推荐** |
| B. OBS + FunctionGraph 换 STS | 同上 | 一个 ~60 行云函数 | 可服务端收敛 | 还要部署函数 | 进阶可选（凭证不进客户端） |
| C. AGC 云数据库（Cloud DB） | `@hw-agconnect/cloud` har | AGC 托管 | SDK 内建冲突策略 | AGC 工程 + 云侧定义对象类型 + 认证方式 | 能力过剩，依赖重，字段限制严 |
| D. 系统备份扩展 → 华为云空间 | 一个 `BackupExtensionAbility` | 系统托管 | 不适用 | 零配置 | 不是「同步」，是「换机恢复」，只做兜底 |
| E. Drive Kit（华为云空间 Drive） | `@hms.core.drive` | 华为云空间 | — | **需申请 drive scope 并通过审核** | 个人开发者基本拿不到，不选 |

选 A 的四条硬理由：

1. **零新依赖**。工程当前只有 `pako` + `@ohos/hypium`。OBS 是纯 HTTPS REST，签名用 `cryptoFramework.createMac('SHA256')` + `createMd('SHA256')` + `util.Base64Helper` 现算即可，不需要 har、不需要 `agconnect-services.json`、不需要改 `module.json5` 权限（`INTERNET` / `GET_NETWORK_INFO` 已声明）。
2. **对象语义正好匹配**。OBS 的 PUT 是**原子替换**（读侧要么旧版要么新版，不会读到半截），GET 整对象。我们的数据是 5 MB 级的 JSON，天然契合；反之 Cloud DB 要求把 `Playlist.tracks[]` 拆成关系表或塞进单个 String 字段（单条 1 MB 上限），反而更别扭。
3. **单次配置、长期免费**。5 MB 存储 + 每月几千次请求，按当前公开价目量级在 **1 分钱/月以内**，实际等同于免费。
4. **协议可移植**。OBS 兼容 S3 语义，将来想换 B2 / R2 / MinIO 自建，只换 endpoint 与签名版本，`CloudSyncManager` 一行不改。

代价（必须写进文档、也必须写进 UI）：**AK/SK 会落在客户端**。缓解手段见 §7。

## 3. 云端对象布局

```
{prefix}/                                   ← 可配置，默认 bilimusic/
  devices/
    {deviceId}/                             ← 每台设备只写自己的目录
      meta.json                             {deviceName, appVersion, lastSyncAt, sessionStats}
      playlist-index.json                   {playlistId: {rev, updatedAt, hash, trackCount, deleted}}
      tombstones.json                       {playlistId: deletedAtIso}
      playlists/{playlistId}.json            单个歌单完整快照（含 tracks / removedTracks 不需要）
      sessions/{YYYY-MM}.jsonl               月度会话分片（与本地分片同构，一行一条）
```

**为什么每歌单一个对象而不是一个大 JSON**：只有单对象才能做「只传变化的那几个」；一轮同步的下载量从 800 KB 降到通常 < 20 KB。

**为什么按设备分目录**：这是整个方案的支点。设备 A 写 `devices/A/`，设备 B 写 `devices/B/`，两者永不触碰同一对象 → **没有并发写冲突，不需要 `If-Match` 条件写**（OBS 对普通 PUT 的条件头支持不如 S3 完整，依赖它是个隐藏风险）。

**代价与对策**：云端不再是「唯一真相」，而是「N 份设备视图的并集」。读侧负责合并 —— 这与现有 `FavSyncManager` 的「先推后拉 + 门控」哲学一致。设备数典型 1–3 台，成本可忽略。卸载重装会生成新 `deviceId`，留下幽灵目录 → 设置页提供「云端旧设备」列表，**手动**删除（不自动清，防误删）。

索引对象（`playlist-index.json`）是**提交点**：先 PUT 内容对象，最后 PUT 索引。索引写失败 → 下轮重试即可，内容对象覆盖写幂等。

## 4. 同步协议

### 4.1 先说不能复用的东西（踩坑预警）

`LibraryStore.importPlaylistsFromParsed` **不能**用于云同步，三个原因都会直接炸：

1. **重名会被改名**：`existingNames.has(name) ? name + ' 导入' : name`。每次同步都会在本地多出一份「歌单名 导入」，且会不断增殖。
2. **`updatedAt` 被重盖为 `now`**：同步后所有歌单都变成「刚改过」，LWW 判定彻底失真。
3. **`addedAt` 被重盖为 `now`**：曲目「谁先加的」顺序依据丢失。

所以云同步需要一个**新的 upsert 入口**：按 `id` 命中则原地替换（保留本地 `addedAt`），未命中则新增。**这是 §8 改动清单里唯一必须动 `LibraryStore` 的地方。**

### 4.2 一轮同步的 10 步

```
① LIST  {prefix}/devices/          （delimiter='/'）→ 拿到所有 deviceId
② GET   devices/*/meta.json        （并发 ≤3）→ 各设备 lastSyncAt / sessionStats
③ GET   devices/*/playlist-index.json + tombstones.json
④ 差量比对：远端 index 的 hash ≠ 本地已知 hash 的 playlistId → 待下载集合
⑤ GET   devices/*/playlists/{id}.json
⑥ 合并（纯函数，见 §4.3 / §4.4）→ 内存中的 merged 结果
⑦ 应用：LibraryStore.batchUpsertFromCloud(merged)  —— 一次落盘 + 一次 STORE_LIBRARY_REV
⑧ 会话：GET 其他设备的 sessions/{month}.jsonl（只取本地缺失或 count 更多的月份）
        → mergeBackupSessions()   ← 现成函数直接复用
⑨ 上传：本设备侧发生变化的 playlistId → PUT playlists/{id}.json
        本设备的月份分片（合并后的完整月份）→ PUT sessions/{month}.jsonl
⑩ 提交：PUT playlist-index.json → tombstones.json → meta.json
```

请求数：D=2 时约 8–10 次/轮；每天 10–20 轮 → 每月 3000 次量级。

### 4.3 歌单合并规则（每条都能一句话向用户解释）

设本地为 `L`，其他设备视图的并集为 `R`，`base` = 上次同步成功时各歌单的曲目 id 集合快照（存 `filesDir/sync_base.json`，**不进 Preferences**，避开 8192 字节上限）。

**① 元信息（name / description / coverUrl / upMid / upName / sourceKind / titleSorted）→ 整单 LWW**

取 `updatedAt` 更大的那一版；`coverUrl` 为空则回落到任一非空值。
理由：改名与加歌是两类操作，用户不会因为"在另一台设备加了首歌"就期望名字回退。

**② 曲目 → 三路集合合并（按 `track.id`）**

| base | 本地 L | 远端 R | 结果 | 语义 |
|---|---|---|---|---|
| 有 | 有 | 有 | 保留 | 两边都在 |
| 有 | **无** | 有 | **删** | 本地删过 |
| 有 | 有 | **无** | **删** | 远端删过 |
| 无 | 有 | 有 | 保留（新增合并） | 两边都新加 |
| 无 | **无** | 有 | 保留 | 新增 |
| 无 | 有 | **无** | 保留 | 新增 |
| **无 base（首次同步）** | 有 | 有/无 | **全部保留（并集）** | 宁多不少，绝不误删 |

最后一行是整个规则的安全阀：**首次同步、或 base 丢失时，只做并集永不删除**。这与 `FavSyncManager` 里「上游 0 条永不作为删除依据」是同一条纪律 —— 数据同步里最贵的错误是静默丢数据，不是多留一条。

**③ 顺序**

以 ② 判定出的「元信息赢家」的 `tracks` 顺序为骨架（过滤掉被判定删除的条目），把另一侧独有的、被保留的条目按 `addedAt` 升序追加到尾部。
理由：顺序无法局部调和，取一份完整可信的顺序比"自己算一个"更符合用户直觉（用户刚整理过的歌单要保持原样）。

**④ 歌单级删除 → 墓碑**

`tombstones.json`：`{playlistId: deletedAtIso}`，保留 60 天。

- 读取时全部设备墓碑**取并集**，`deletedAt` 取**最早**值（一台设备删了就算删，防止别的设备的旧快照把它复活）
- 本设备删除歌单时同步写墓碑
- 60 天后清理：长期离线（>60 天）的设备上线后可能让删除的歌单复活 —— 这是刻意的权衡，写进文档比隐藏好。想彻底避免就得永久保留墓碑，对象会永续膨胀。

### 4.4 拾音合并

直接复用 `PlaySessionStore.mergeBackupSessions`，它已经处理了：
- 字段消毒（缺 `trackId` / `startedAt` / `ms` 丢弃）
- 保留窗过滤（13 个月前、`ms < 1000` 的噪音丢弃）
- `(trackId|startedAt|ms)` 逐月去重
- 沿 `writeChain` 串行追加 + 递增 `STORE_SESSION_REV`（拾音页 `@Watch` 自动刷新，免重启）

需要注意的三点：

1. **同一天同一首歌听两次，`startedAt` 不同 → 两条都保留**。这是正确行为，不是重复。
2. **上传时上传「合并后的完整月份」**，而不是只传新增行。原因：`jsonl` 是追加格式，两边各追加一半时，谁后 PUT 谁覆盖谁 → 只传增量必丢数据。整月对象 200–300 KB，可接受；P1 可用 `pako.deflate`（工程已有 `pako` 依赖，`LxByteUtils` 在用 `inflate`）压到 ~40 KB。
3. **云端不额外延长保留期**。本地 13 个月窗口是产品口径，云端跟随；更早的分片可由 OBS 生命周期规则自动清理，不必在代码里写删除逻辑。

### 4.5 触发时机（诚实面对 HarmonyOS 的后台约束）

HarmonyOS 没有 iOS 式的「无限后台执行」，App 不在前台就不会自己醒来。所以「自动同步」的真实含义是**「每次你打开 App，它已经把数据对齐了」**，而不是服务端推送级别的实时。

| 触发点 | 延迟 | 说明 |
|---|---|---|
| 冷启动后 8 s | 一次性 | 避开首页首屏与推荐流首刷，不和启动链抢网络 |
| 前台化（`onForeground`） | 距上次 > 5 min 才同步 | 一天亮屏几十次，不做节流会打爆请求数 |
| 数据变更后 | debounce 20 s | 监听 `STORE_LIBRARY_REV` / `STORE_SESSION_REV`；连续加歌只触发一次 |
| 退后台（`onBackground`） | 立即 flush 一次 | 只上传变化对象；**不申请长时任务**（`BackgroundPlayback` 已占用 audioPlayback / dataTransfer，同一应用同一时刻只能持有一个长时任务，硬抢会打断播放或下载） |
| 手动 | 立即 | 页面「立即同步」 |
| 失败重试 | 30 s → 1 m → 2 m → 5 m → 15 m 封顶 | 退避期不弹窗、不写日志刷屏 |

**闸门（与下载链路同款思路）：**
- 「仅 WiFi 同步」开关（默认开），判据复用 `NetworkUtil.isUnmeteredNetwork()`
- **单飞锁**：`syncChain` Promise 串行（工程既有 `writeChain` 范式），任何触发点进来只排队不并发
- 播放中允许同步，但**单对象 15 s 超时 + 总轮次 90 s 截止**，超时留到下一轮，绝不影响播放

## 5. 安全与隐私

### 5.1 AK/SK 最小权限

- 用 **IAM 子账号**，不要用主账号 AK
- 桶策略只授予该 prefix：`GetObject` / `PutObject` / `ListBucket`（限 `prefix=bilimusic/*`）/ `DeleteObject`（供"清理旧设备"）
- 不开 `ListAllMyBuckets`、不开任何桶级管理权限

### 5.2 客户端存放

- `Access Key ID`：可存 Preferences（非敏感）
- `Secret Access Key`：存 **`@ohos.security.asset`（ASSET）**，系统级加密 + 应用隔离；**不落 Preferences 明文**
- 降级路径：ASSET 不可用时（低版本 / 真机异常），活动期内仅存内存，每次启动要求重填 —— 宁可麻烦，不静默降级成明文

### 5.3 可选：客户端加密（P1）

歌单名与听歌记录属于个人偏好数据。可在上传前做 **AES-256-GCM**（`cryptoFramework.createCipher('AES256|GCM|PKCS7')`），密钥由用户口令经 **PBKDF2-SHA256**（≥10 万轮）派生。

- 收益：AK 泄露 / 桶误公开时，云端只有密文
- 代价：**口令丢失 = 数据永久不可解**，换设备必须输入同一口令；必须用「我知道，我确认」式的二次确认弹窗，不能做成一个开关
- 结论：默认关闭，作为极客选项；默认路径靠 §5.1 的最小权限 + §5.2 的 ASSET 兜住

### 5.4 合规

- 隐私政策需新增条目：同步内容（歌单名称与曲目、听歌记录）、目的（多设备一致）、存储位置（华为云 OBS，用户自建桶）
- 上传前剥离：`access_key` / 任何 Cookie / `localFilePath` / 过期直链 / 设备唯一标识（`buvid` 等）
- 首次开启时给一屏说明：「数据会上传到你自己的华为云存储桶，本 App 不经过任何第三方服务器」

## 8. UI：入口与三态

**入口**：设置 →「歌单备份」页 → 新分组「云同步」→ 行「华为云同步」+ 副标题显示当前状态
（`已连接 · 3 分钟前同步` / `未配置` / `同步失败 · 点击查看`）

**页内三态：**

1. **未配置**：一句说明 + 「开始配置（约 5 分钟）」+ 前置条件清单（需华为云账号、需自建一个 OBS 桶）。底部保留一行灰色小字：「也可以继续用本地备份文件手动搬家」
2. **已连接**：状态卡（上次同步时间 / 本次上传下载对象数 / 数据量）+ 开关区（自动同步 / 仅 WiFi / 客户端加密）+「立即同步」+「云端设备」（列出 deviceId / 设备名 / 最后活跃 / 手动删除）
3. **冲突与详情**：极少出现（三路合并已静默处理绝大多数情况），仅在「同一歌单双方都删到只剩不同曲目」时列出差异，给「保留两边（并集）」/「以本机为准」

**文案纪律**：不要写「实时同步」。写「打开 App 时自动同步」，否则用户会拿它跟网盘比。

## 11. 明确不做的事

- ❌ 不做实时推送（无长连接、无服务端）
- ❌ 不把 B 站收藏夹镜像上云（真源在 B 站，双份必然打架）
- ❌ 不同步登录态（Cookie 上云 = 账号安全事件）
- ❌ 不做"同步即备份"的承诺（对象按设备存，删掉某设备目录 = 删掉它贡献的那份数据）
- ❌ 不在 `onBackground` 里申请长时任务抢 `BackgroundPlayback` 的额度

## 12. 三个最容易翻车的点（给实施者）

1. **别用 `importPlaylistsFromParsed` 做恢复**。它会给重名加「导入」后缀、重盖 `updatedAt` / `addedAt` —— 每次同步都在本地多长一份歌单，且 LWW 判定全废。必须新写 `batchUpsertFromCloud`。
2. **base 快照不能进 Preferences**。20 歌单 × 100 曲目 id ≈ 40 KB，远超单值 8192 字节上限，写进去会静默截断 → 三路合并退化成「无 base」→ 删除永不传播，且极难排查。存 `filesDir/sync_base.json`。
3. **会话必须整月上传，不能只传增量**。`jsonl` 追加格式 + 整对象 PUT 覆盖 = 谁后写谁丢失对方新增的行。`mergeBackupSessions` 合并在本地是对的，但上传那一侧必须上传「合并后的完整月份」。
