# 华为云空间同步 · 自动同步歌单与拾音数据

> 目标：换机 / 多设备（手机 + 平板）时，歌单（**含订阅 UP 歌单，不含 B 站收藏夹镜像**）与拾音（听歌日记）数据自动保持一致。
> 本版走**华为云空间**（华为账号那一侧），不是华为云的 OBS / AGC。
> 本文只给方案与实施规格，**不含代码改动**。

---

## 0. 一句话方案

打开 `AppScope/app.json5` 的 `"cloudFileSyncEnabled": true`，把数据写进应用沙箱的**云端目录** `context.cloudFileDir`（即 `/data/storage/el2/cloud`）。
系统负责把文件传进用户的**华为云空间**、并在同账号的多台设备间同步；读端用 `CloudFileCache` 把别的设备写的文件按需缓存到本地再读。
**零凭证、零建桶、零费用、零新权限**，同步协议沿用「每设备独立写域 + 读取端合并」，因此并发冲突被结构性消除。

## 1. 先把「华为云空间」这条路查实（决定方案能不能落地）

本工程 SDK 里能用的相关能力，逐个核过：

| 能力 | 入口 | SDK 证据 | 结论 |
|---|---|---|---|
| **端云文件协同**（应用云端目录） | `app.json5` → `cloudFileSyncEnabled: true`<br>运行时 `Context.cloudFileDir` | `toolchains/modulecheck/app.json:602`（boolean，default false）；`application/Context.d.ts:157`（**since 12**） | ✅ **主方案** |
| 云端文件按需缓存 | `@ohos.file.cloudSync` → `CloudFileCache` | `@ohos.file.cloudSync.d.ts`（**since 11**，`start`/`stop`/`on('progress')`/`cleanFileCache`）；**0 处 `@systemapi`、0 处 `@permission`** | ✅ 主方案 |
| 云文件统计（未上传/未下载数量） | `@ohos.file.cloudSyncManager` → `CloudFileInfo` | 同名 d.ts（**since 20**），`cloudFileCount` / `localFileCount` / `bothFileCount` | ⚠️ 探针验证（API 文档措辞面向"文件管理器"） |
| 结构化数据端云同步 | `app.json5` → `cloudStructuredDataSyncEnabled: true` + AGC 云空间建容器 | `app.json:607` 存在该字段；官方要求「容器名 = 本地 ArkData 数据库名、字段名与本地表一致」 | ⛔ 要把 Preferences + jsonl 全部迁到 relationalStore，代价远大于收益 |

| 系统备份 → 云备份 | `BackupExtensionAbility` + `backup_config.json` | `@ohos.application.BackupExtensionAbility.d.ts`（since 10/12/20）；schema 的 `includes` 正则**禁止 `/el3/` `/el4/`** | ✅ 兜底（换机恢复，不是实时同步） |

## 2. 这条路的能力边界（必须先讲清，否则实施会撞墙）

这是本方案与「自建桶」最大的区别：**调度权不在 App 手里**。

| 环节 | 谁控制 | App 能做什么 |
|---|---|---|
| 本机写入 → 上传到云空间 | **系统**（通常充电 / WiFi / 空闲时批量传） | 只能把文件写进 `cloudFileDir` 并标记待上传；无法强制立即上传 |
| 云空间 → 其他设备可见 | **系统** | 什么都做不了；另一台设备列目录时自然可见 |
| 其他设备的文件 → 本机可读 | App | `CloudFileCache.start(uri)` 按需拉取 + `on('progress')` 等完成 |
| 冲突 | App（协议设计） | 「每设备一份视图」→ 系统层面永不冲突，冲突全部落在读取端合并 |

由此推出三条产品口径（必须写进 UI，否则用户会觉得"同步卡住了"）：

1. **读取是即时可控的，写入是系统择时的**。所以按钮叫「立即读取云端」，不叫「立即同步」。
2. 页面上要有「**N 个文件等待系统上传**」（来自 `CloudFileInfo.localFileCount`），让用户知道不是卡死。
3. 首次开启后提示：「上传由系统在充电和 WiFi 下完成，通常几分钟到几小时」。

> 若实测发现上传延迟超过半天，P2 追加一条引导：「设置 → 云空间 → 立即备份」。这不是 API，是系统设置项的深链。

## 3. 云端目录布局

`context.cloudFileDir` 下（首次使用时 `fs.mkdirSync` 递归创建）：

```
{cloudFileDir}/bilimusic/
  devices/
    {deviceId}/                        ← 每台设备只写自己的目录
      meta.json                        {deviceName, appVersion, lastWriteAt, sessionMonths}
      playlist-index.json              {playlistId: {rev, updatedAt, hash, trackCount}}
      tombstones.json                  {playlistId: deletedAtIso}
      playlists/{playlistId}.json       单个歌单完整快照
      sessions/{YYYY-MM}.jsonl          月度会话分片（与本地分片同构，一行一条）
```

三条设计理由，和自建桶完全同源：

- **每设备一个目录** → 两台设备永不写同一文件。系统即使按「后写覆盖」处理，也覆盖不到别人的数据。**这是整个方案的支点**，也让「系统同步」这种粗粒度机制变得安全。
- **每歌单一个文件** → 读取时只拉变化的那个，不用整包 800 KB。
- **索引是提交点** → 先写内容文件，最后写 `playlist-index.json`。索引没写成功，下轮重写即可，内容文件覆盖写幂等。

## 4. 读写实现（关键 API 细节）

### 4.1 写：直接落云端目录

```
path = `${context.cloudFileDir}/bilimusic/devices/${deviceId}/...`
fs.mkdirSync(dir, true)                         // 递归建目录
fs.openSync(path, fs.OpenMode.CREATE | fs.OpenMode.READ_WRITE | fs.OpenMode.TRUNC)
fs.writeSync(fd, json)  →  fs.closeSync(fd)
```

写入完成即视为「已交给系统」。**不需要联网、不需要权限、App 本身一个请求都不发**（联网由系统服务完成）。

### 4.2 读：列目录 → 判定占位 → 缓存 → 读本地

```
fs.listFileSync(dir)                            // 云端占位文件也会出现在列表里
→ fileUri.getUriFromPath(path)                  // 缓存 API 吃的是 uri 不是 path
→ cache.start(uri)  +  await 一次 on('progress') 的 state=COMPLETED
→ 读本地缓存副本（占位文件本身不可直接 read）
→ 用完 cache.cleanFileCache(path)（可选，释放本机空间）
```

三个硬约束（都写在 d.ts 与官方适配指南里）：

1. **`CloudFileCache.start` 并发上限 10**，超过会抛 `22400004`，官方指南原话是"超过此限制会导致整机异常" → **必须串行或分批 ≤10**（本项目对象数本来就少，串行足够）。
2. `start` 会抛 `13900002`（文件不存在）/ `13900025`（空间不足）/ `14000002`（uri 非法），要分类处理而不是一律当失败。
3. 占位文件**不能**用 `fs.readSync` 直接读 —— 必须先缓存，否则拿到空内容或抛错。这是最容易踩的坑。

### 4.3 状态：有多少没传上去

```
cloudSyncManager.CloudFileInfo {
  localFileCount      // 本机有、云端还没有（= 等待上传）
  cloudFileCount      // 云端有、本机未下载（= 别的设备新写的）
  bothFileCount       // 两边都有
}
```

这个类没有 `@systemapi` 标记，但文档措辞是「for the file manager application」，三方调用可能返回 0 或抛错 → **放进探针验证**；不可用则退化为「按本地 index 与远端 index 的差集估算」，UI 上少一个数字而已，不影响功能。

## 5. 同步协议（与存储介质无关，整段可复用）

### 5.1 不能复用的东西（先说坑）

`LibraryStore.importPlaylistsFromParsed` **不能**用于云恢复，三个原因都会直接炸：

1. **重名会被改名**：`existingNames.has(name) ? name + ' 导入' : name` → 每次同步本地多一份「歌单名 导入」，且不断增殖。
2. **`updatedAt` 被重盖为 `now`** → 所有歌单都变成"刚改过"，LWW 判定彻底失真。
3. **`addedAt` 被重盖为 `now`** → 曲目「谁先加的」顺序依据丢失。

必须新写一个按 `id` 的 upsert：命中则原地替换（保留本地 `addedAt`），未命中则新增。**这是唯一必须动 `LibraryStore` 的地方。**

### 5.2 一轮同步（读取侧 8 步）

```
① 列 {cloudFileDir}/bilimusic/devices/  → 拿到所有 deviceId（含别的设备）
② 读各设备 meta.json / playlist-index.json / tombstones.json（先缓存再读）
③ 差量：远端 hash ≠ 本地已知 hash 的 playlistId → 待下载集合
④ 逐个缓存并读 playlists/{id}.json
⑤ 合并（纯函数，见 §5.3 / §5.4）
⑥ 应用：LibraryStore.batchUpsertFromCloud() —— 一次落盘 + 一次 STORE_LIBRARY_REV
⑦ 会话：缓存其他设备的 sessions/{YYYY-MM}.jsonl → mergeBackupSessions()
⑧ 回写本设备目录：变化的内容文件 → 索引 → 墓碑 → meta
```

第 ⑧ 步只是「把本机结果写回自己的目录」，写进去之后什么时候上云归系统管。

### 5.3 歌单合并规则

本地 `L`、其他设备视图的并集 `R`，`base` = 上次同步成功时各歌单的曲目 id 集合快照（存 `filesDir/sync_base.json`，**不进 Preferences**）。

**① 元信息（name / description / coverUrl / upMid / upName / sourceKind / titleSorted）→ 整单 LWW**
取 `updatedAt` 更大的一版；`coverUrl` 为空回落到任一非空。理由：改名与加歌是两类操作，用户不会因为"另一台设备加了首歌"期望名字回退。

**② 曲目 → 三路集合合并（按 `track.id`）**

| base | 本地 L | 远端 R | 结果 | 语义 |
|---|---|---|---|---|
| 有 | 有 | 有 | 保留 | 两边都在 |
| 有 | **无** | 有 | **删** | 本地删过 |
| 有 | 有 | **无** | **删** | 远端删过 |
| 无 | 有 | 有 | 保留 | 两边都新加 |
| 无 | 无 | 有 | 保留 | 新增 |
| 无 | 有 | 无 | 保留 | 新增 |
| **无 base（首次）** | 有 | 有/无 | **全部保留（并集）** | 宁多不少，绝不误删 |

最后一行是安全阀：**首次同步或 base 丢失时只做并集永不删除**。与 `FavSyncManager`「上游 0 条永不作为删除依据」是同一条纪律 —— 数据同步里最贵的错误是静默丢数据，不是多留一条。

**③ 顺序**：取「元信息赢家」的 `tracks` 顺序为骨架（滤掉被删条目），另一侧独有的保留条目按 `addedAt` 升序追加到尾部。

**④ 歌单级删除 → 墓碑**：`tombstones.json` = `{playlistId: deletedAtIso}`，保留 60 天；读取时全设备**并集**、`deletedAt` 取**最早**（一台删了就算删）。超过 60 天的长期离线设备上线后可能让歌单复活 —— 这是刻意权衡，写清比藏着好。

### 5.4 拾音合并

直接复用 `PlaySessionStore.mergeBackupSessions`，它已经做了：字段消毒 / 13 个月保留窗过滤 / `(trackId|startedAt|ms)` 逐月去重 / 沿 `writeChain` 串行追加 / 递增 `STORE_SESSION_REV`（拾音页 `@Watch` 自动刷新，免重启）。

三点注意：
1. 同一天同一首歌听两次（`startedAt` 不同）是两条，都要保留 —— 这不是重复。
2. **上传整月而不是增量**：`jsonl` 是追加格式，整文件覆盖写时谁后写谁丢对方新增行。整月对象 200–300 KB，可接受；P1 可用 `pako.deflate`（工程已有 `pako`）压到 ~40 KB。
3. 云端不额外延长保留期，跟随本地 13 个月口径。

### 5.5 触发与节流

| 触发点 | 延迟 | 说明 |
|---|---|---|
| 冷启动后 8 s | 一次 | 避开首页首屏与推荐流首刷 |
| 前台化 | 距上次 > 5 min | 一天亮屏几十次，不节流会反复列目录+缓存 |
| 数据变更后 | debounce 20 s | 监听 `STORE_LIBRARY_REV` / `STORE_SESSION_REV`；连续加歌只触发一次 |
| 退后台 | 立即写回本机目录 | **只写文件**（本地操作，毫秒级），不需要长时任务 |
| 手动 | 立即 | 页面「立即读取云端」 |

- 单飞锁：`syncChain` Promise 串行（工程既有 `writeChain` 范式）
- 「仅 WiFi 读取」开关默认开，判据复用 `NetworkUtil.isUnmeteredNetwork()`
- **不申请长时任务**：`BackgroundPlayback` 已占 audioPlayback / dataTransfer，同一应用同一时刻只能持一个，硬抢会打断播放或下载
- 缓存下载串行且单轮总预算 60 s，超时留到下一轮，绝不影响播放

## 6. 同步范围

**同步**：普通歌单（`sourceKind === ''`）、订阅 UP 歌单（`'up'`，带 `upMid`/`upName`）、拾音 `PlaySession` 全字段（13 个月窗内）。

**不同步（显式过滤）：**
- **B 站收藏夹镜像（`sourceKind === 'fav'`）**：它是 B 站账号侧数据的投影，真源在 B 站。上传后另一台设备会得到一份「看起来像本地歌单」的副本，而镜像识别依赖 `sourceKind` 与 `upMid = fav_{mediaId}`；一旦云端带来降级副本，就会出现「同一收藏夹两个镜像」，`getFavMirrorByMediaId` 只取首个，另一个永不再同步也不会被清理（`importPlaylistsFromParsed` 里有同样警告）
- 最近播放 / 播放进度 / 播放队列（设备本地语义，同步会互相打断）
- 下载文件、歌词缓存、首页缓存、封面缓存
- 登录 Cookie、`access_key`、`refresh_token`（**红线**）
- `Track.localFilePath`（本机绝对路径）、`audioUrl` / `videoUrl`（签名直链会过期）
- App 设置项（音质/音量/主题）—— P3

## 7. 安全与隐私

- **凭证为零**：App 不持 AK/SK、不持 token，数据在用户自己的华为云空间，由华为账号保护。这是本方案相比自建桶最大的优势。
- 仍要剥离：Cookie / `localFilePath` / 过期直链 / `buvid` 等设备标识。
- 隐私政策新增：同步内容（歌单名称与曲目、听歌记录）、目的（多设备一致）、存储位置（**华为云空间**，随账号加密存储）。
- 可选加强（P2）：写入前 AES-256-GCM 加密，密钥由用户口令派生 → 换机需输入同一口令，**口令丢失即不可恢复**，必须用二次确认弹窗，不做成普通开关。

## 9. 落地前必须跑的真机探针（P0 前置，不通就换路）

能力清单查到不等于真机能用。开工前先做一次 30 分钟的探针，六条全绿再写业务：

| # | 探针 | 判据 |
|---|---|---|
| 1 | `cloudFileSyncEnabled: true` 后 `context.cloudFileDir` 是否可写 | 写入不抛错，`fs.accessSync` 通过 |
| 2 | 设置 → 云空间 能否看到本应用开关 | 能开，开完 IDE 的 Device File Browser 能浏览 `el2/cloud` |
| 3 | 写文件后多久上云 | 记时间戳；另一台设备列目录时出现即算通（顺便量延迟） |
| 4 | 另一台设备能否列到占位文件 | `fs.listFileSync` 能看到对方 deviceId 目录与文件 |
| 5 | `CloudFileCache.start(uri)` 能否把占位拉成本地可读 | `on('progress')` 走到 COMPLETED，读到的内容与写入一致 |
| 6 | `cloudSyncManager.CloudFileInfo` 三方能否取到 | 返回非异常；不行就退化为差集估算 |

若 **3/4/5** 任一失败 → 放弃「同步」语义，退回 §11 的 `BackupExtensionAbility` 兜底（换机恢复），并如实告知用户"这是备份不是同步"。

| 1 | 设备 A 写 → 系统上传 → 设备 B 读取 | B 上歌单数/曲目数/`sourceKind`/`titleSorted`/`upMid` 全对，**收藏夹镜像不出现** |

## 11. 兜底方案：系统备份（零操作，但不是同步）

`BackupExtensionAbility`（`@ohos.application.BackupExtensionAbility`，API 10/12/20）接入成本极低：

- `module.json5` 加一个 `"type": "backup"` 的 extensionAbility
- `resources/rawfile/backup_config.json` 用 `includes` 列出要备份的目录（如 `./files/listen_log`），**不能含 `el3`/`el4`**（schema 正则直接拒）
- 重写 `onBackupEx` / `onRestoreEx` 返回结果 JSON

它由系统在**充电 + 锁屏 + WiFi** 时自动执行、AES-256 加密上云，换机/重装时恢复。**价值是零成本兜底，不能替代同步**（没有"另一台设备读到最新"的语义）。建议与主方案并存：99% 用户无感拿到"换机不丢数据"，极客用户开 `cloudFileSyncEnabled` 拿到真同步。

## 13. 明确不做的事

- ❌ 不承诺「实时同步」：上传时机归系统，文案写「打开 App 时读取云端最新数据」
- ❌ 不把收藏夹镜像上云（真源在 B 站，双份必然打架）
- ❌ 不同步登录态（Cookie 上云 = 账号安全事件）
- ❌ 不在 `onBackground` 抢长时任务
- ❌ 不用 Drive Kit REST（本 SDK 无客户端库，且 `client_secret` 不能落客户端）

## 14. 三个最容易翻车的点（给实施者）

1. **别用 `importPlaylistsFromParsed` 做云恢复**：重名加「导入」后缀 + 重盖 `updatedAt`/`addedAt` → 每次同步多长一份歌单、LWW 全废。必须新写 `batchUpsertFromCloud`。
2. **base 快照别进 Preferences**：20 歌单 × 100 曲目 id ≈ 40 KB，远超单值 8192 上限 → 静默截断 → 三路合并退化成"无 base" → 删除永不传播，且极难排查。存 `filesDir/sync_base.json`。
3. **占位文件不能直接 `fs.readSync`**：`el2/cloud` 里的文件在本机未缓存时是云端占位，必须先 `CloudFileCache.start(uri)` 等到 COMPLETED 再读；且并发上限 10（超限整机异常），本项目取 1。
