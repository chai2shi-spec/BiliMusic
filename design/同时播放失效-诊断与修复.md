# 「与其他应用同时播放」偶发失效 —— 诊断与修复

> 阅读基准：`entry/src/main/ets/player/MusicPlayer.ts`（5800+ 行）、`entryability/EntryAbility.ets`、
> `pages/PlaybackSettingsPage.ets`。本文**只诊断不改码**，文末第 8 节是可直接粘贴给 AI 编码助手的执行需求。

---

## 结论先行

**这个开关并不是「失效」，而是只在「点歌 / 切歌」那一刻才被打上。一旦系统在别的时刻把会话停掉，
就没有任何代码会把它重新打开 —— 而系统的停用是常态，不是异常。**

所以症状有明确规律：

| 你的操作 | 结果 | 为什么 |
|---|---|---|
| 开开关 → 点一首**新歌** | 生效 | 走 `loadAndPlay`，开头对账 |
| 暂停几十秒 → 点**播放** | 失效 | 走 `play()` 的 paused 分支，**不对账** |
| 一首放完自动下一首 | 生效 | 走 `loadAndPlay` |
| 单曲循环重播同一首 | 失效 | `handleEnded` 直接 seek+play，**不对账** |
| 锁屏 / 车机 / 耳机线控恢复 | 失效 | AVSession → `play()` → **不对账** |
| 切出去用别的 App，再回来点播放 | 大概率失效 | 会话已被系统停用，**没人重开** |

一句话：**「切歌就好、点播放不好」，这就是那个「偶尔」。**

---

## 一、现在这套是怎么实现的

只有三个事实点，先摆出来。

**① 激活只发生在一个地方 —— `loadAndPlay` 的最开头**

```ts
// MusicPlayer.ts:4180
private async loadAndPlay(track: Track, autoplay: boolean, startAt: number = 0): Promise<void> {
  ...
  // :4192
  await this.ensureMixAudioSession(AppStorage.get<boolean>(STORE_AUDIO_MIX_ENABLED) ?? false);
```

`ensureMixAudioSession()`（:4060）的逻辑：

```ts
const activated = mgr.isAudioSessionActivated();
if (mix && !activated) {
  await mgr.activateAudioSession({ concurrencyMode: CONCURRENCY_MIX_WITH_OTHERS });
} else if (!mix && activated) {
  await mgr.deactivateAudioSession();
}
```

注意它的判据只有 **`isAudioSessionActivated()`** —— 一个布尔值「会话有没有激活」，**不包含「用的是什么并发策略」**。

**② 第二个激活点只在设置页拨开关时**

```ts
// MusicPlayer.ts:5562
setAudioMixEnabled(enabled: boolean): void {
  this.ensureMixAudioSession(enabled).catch(...);
}
```

② 的注释自己已经承认了：「正在出声的这一首是 best-effort，下一首起必然完全生效。」

**③ `loadAndPlay` 的调用点只有三个**

```
:4436  恢复链重试
:4678  playTrack()      ← 用户点歌
:4721  play() 内的 !avPlayer || idle || error || released 分支
```

而 `play()` 在**播放器已存在、状态是 paused / prepared / completed / playing**（:4757 起）时，
**完全不碰 `loadAndPlay`**，直接 `this.avPlayer.play()`。

同理 `handleEnded()`（:5756）的单曲循环分支（:5771 起）也是直接 `seek` + `play`，
`next()` 才会走 `loadAndPlay`。

## 二、为什么是「偶尔」：会话会自己消失

`AudioSession` 不是「设置一次永久有效」的东西。它有两条退出通道，SDK 里写得很清楚：

```ts
// @ohos.multimedia.audio.d.ts:3408
enum AudioSessionDeactivatedReason {
  DEACTIVATED_LOWER_PRIORITY = 0,  // 「应用焦点被抢占」
  DEACTIVATED_TIMEOUT = 1          // 「音频会话超时」
}
```

而本应用的 `pause()` 结尾做了这件事：

```ts
// MusicPlayer.ts:4884（pause 末尾）
this.syncBackgroundTask(false);   // → bg.stop(context)，停掉长时任务
```

于是这个循环成立：

```
播放中    → 有音频流 + 有长时任务  → 会话保持激活 ✔
   ↓ 用户暂停
已暂停    → 无音频流 + 长时任务已停 → 会话开始计时
   ↓ 应用退到后台 / 停留一会儿
系统      → DEACTIVATED_TIMEOUT     → 会话没了（音频流全部停止后必然发生）
   ↓ 用户回来点「播放」
play()    → 走 paused 分支，不调 ensureMixAudioSession → 会话仍然没有
   ↓ 此时别的 App 在播
默认焦点  → 音乐类互相打断           → 被抢 / 抢别人
```

**关键就在这里：第 5 步是整条链上唯一没有对账的一步，而它恰好是用户最常走的一步。**

---

## 三、四条失效路径（按发生概率排序）

### P1 · 暂停后恢复（最高频，几乎必现）

1. 开着开关，播一首 → 日志出现 `audio session activated: mix with others`
2. 暂停 → 长时任务被停（`syncBackgroundTask(false)`）
3. 放置 30 秒以上（是否切后台都行，切后台更快）
4. 系统停用会话（`DEACTIVATED_TIMEOUT`）
5. 点播放 → `play()` :4757 分支 → `avPlayer.play()`
6. 音频流以**默认策略**申请焦点 → 被其他应用打断

> 这一步的确定性很高：只要「暂停 + 等待 + 别的 App 在响」三个条件同时满足，就复现。

### P2 · 单曲循环 / 播完重播

`repeatMode === ONE` 时，`handleEnded` 走 seek+play，**没有 `loadAndPlay`**，同样不对账。
用户听一整晚单曲循环，中途只要有一次会话超时，后面再也不恢复混音。

### P3 · 锁屏 / 车机 / 耳机线控恢复

```ts
// MusicPlayer.ts:1558
session.on('play', (): void => { this.play(); });
```

媒体中心、车机、线控的恢复命令全部落到同一个 `play()`，走 paused 分支，不对账。
**这条最隐蔽**：用户在锁屏上点播放，看不到应用界面，只会觉得「怎么这次把网易云干掉了」。

### P4 · 会话被更高优先级抢占

`DEACTIVATED_LOWER_PRIORITY` 表示有别的应用/系统组件抢走了焦点。
被抢占后 `isAudioSessionActivated()` 会返回 false，**但没有任何回调通知本应用**，
要等到下一次 `loadAndPlay` 才可能发现。中间这段时间用户的每一次「继续播放」都在裸奔。

---

## 四、四个放大器：让问题从「偶发」变成「玄学」

### 放大器 1 · 只判「有没有激活」，不判「是不是混音」

```ts
if (mix && !activated) { activate }   // activated === true 就什么都不做
```

只要会话处于「已激活、但策略不是 MIX」的状态，这里就永远不纠正。
理论窗口不大，但 `DEACTIVATED_LOWER_PRIORITY` 之后若系统以默认策略重建会话，就正好落进这个洞。

### 放大器 2 · 激活失败被完全吞掉

```ts
} catch (e) {
  console.error(`ensure mix audio session failed: ${JSON.stringify(e)}`);
}
```

`activateAudioSession` 会抛 `6800101`（参数校验失败）和 `6800301`（**焦点抢占失败 / 音频服务进程崩溃**）。
抛了之后：用户界面显示「已开启」，实际一点点混音都没有，**而且没有任何提示**。
「开了但没生效」比「关着」糟糕得多 —— 用户会以为是自己搞错了。

### 放大器 3 · 淡出在途时新旧播放器并存

```ts
// rebuildPlayerLocked()
if (this.fadeOutTimer !== -1 && this.fadeOutPlayer === old) {
  this.fadeOutReleaseOnDone = true;   // 旧实例押后 release
}
```

开着「淡入淡出」时，切歌瞬间**旧实例还在出声**（淡出斜坡中），新实例已经创建。
同一应用同时有两条音频流，而会话策略是按「申请那一刻」生效的 —— 这时新流能不能拿到 MIX 策略，
取决于系统怎么合并两条流。这是「同样的操作，有时行有时不行」的另一个来源。

### 放大器 4 · API 26 上这套写法已经偏保守

SDK 里两处标注值得注意：

```ts
* @typedef AudioSessionStrategy [since 12 - 24]        // :3645
* @type { AudioConcurrencyMode } [since 12 - 24]       // :3656
```

`concurrencyMode` 这个字段的适用区间在 **API 24 截止**。而 API 20 起新增了必须显式调用的场景声明：

```ts
setAudioSessionScene(scene: AudioSessionScene): void;   // :3899，@since 20
```

不调用它，会话级事件（`audioSessionStateChanged`、`currentOutputDeviceChanged`）**不会派发**，
而且部分策略会按非媒体场景处理。项目是 API 26，这一条现在没做。

## 五、怎么把它变成「确定性复现」

排查「偶发」问题的第一步，永远是先把它变成必现。三步：

| 步骤 | 动作 | 期望 |
|---|---|---|
| 1 | 开开关，播一首，看日志出现 `audio session activated: mix with others` | 确认基线生效 |
| 2 | 暂停，**切到桌面等 30 秒**（或直接打开另一个音乐 App 放歌） | 会话被系统停用 |
| 3 | 回本应用点「播放」 | **必然失效** |

判据只看一行日志：

```
audio session activated: mix with others
```

- 出现 → 这一次起播是在 MIX 策略下
- **没出现，但歌响了** → 就是本次要修的那个 bug

再补一个反证：第 3 步改成「点一首新歌」，一定生效。**同一次会话里，点歌行、点播放不行**
—— 这个对比一旦成立，根因就锁定在「对账点缺失」，与系统版本、设备、风控全都无关。

---

## 六、修复方案

核心一句话：**把「对账」从「换音源的时候」搬到「要出声的时候」。**

### 6.1 用本地记账取代「只查激活布尔值」

`isAudioSessionActivated()` 查不到策略，所以必须自己记一笔：

```ts
/** 最后一次成功激活时的并发模式（true = MIX）。会话被系统停用时置 null */
private mixSessionMode: boolean | null = null;
```

对账逻辑改成「三重判据」：

```ts
private async ensureMixAudioSession(mix: boolean): Promise<void> {
  try {
    const mgr = audio.getAudioManager().getSessionManager();
    const activated: boolean = mgr.isAudioSessionActivated();
    // 判据一：需开启且（未激活 或 记的不是 MIX）→ 都要重开
    if (mix && (!activated || this.mixSessionMode !== true)) {
      // API 20+：先声明场景，否则会话级事件不派发
      try { mgr.setAudioSessionScene(audio.AudioSessionScene.AUDIO_SESSION_SCENE_MEDIA); } catch (e) { ... }
      await mgr.activateAudioSession({
        concurrencyMode: audio.AudioConcurrencyMode.CONCURRENCY_MIX_WITH_OTHERS
      });
      this.mixSessionMode = true;
      plogInfo('audio session activated: mix with others');
    } else if (!mix && activated) {
      await mgr.deactivateAudioSession();
      this.mixSessionMode = null;
      plogInfo('audio session deactivated: mix off');
    }
  } catch (e) {
    // 判据二：失败必须留痕，且记账置 null（下次一定重试，不能「以为成功了」）
    this.mixSessionMode = null;
    plogWarn(`ensure mix audio session failed: ${JSON.stringify(e)}`);
  }
}
```

### 6.2 补三个对账点

| # | 位置 | 理由 |
|---|---|---|
| **A** | `play()` 开头（`casting` / `isPreparing` 判断**之前**） | 一网打尽 paused / completed / 播放中 的所有恢复路径，含 AVSession 命令 |
| **B** | `EntryAbility.onForeground()` | 用户切回来那一刻，正在播却没会话 → 立刻补 |
| **C** | `audioSessionDeactivated` 回调 | 系统停用即刻把记账置 null，让下一次 A 必然重开 |

`play()` 是同步方法，不能直接 `await`。两种写法：

**写法一（推荐，改动最小）**：在 `play()` 最前面加一段「前置对账 + 延后起播」，
只有「开关开 + 记账不是 MIX」这一种情况才走异步，其余路径零成本：

```ts
play(): void {
  // ...原有的 wasPlayingBeforeInterrupt / pausedForCall 复位...
  const mix: boolean = AppStorage.get<boolean>(STORE_AUDIO_MIX_ENABLED) ?? false;
  if (mix && this.mixSessionMode !== true) {
    // 会话已被系统停用（或从未激活）：必须先把策略打上，再让流出声。
    // 否则这一声响在默认焦点策略下，必然被正在播的其他应用打断。
    this.ensureMixAudioSession(true)
      .then((): void => { this.playInternal(); })
      .catch((): void => { this.playInternal(); });   // 激活失败也要能播
    return;
  }
  this.playInternal();
}

private playInternal(): void { /* 原来的 play() 全体 */ }
```

代价：会话不一致时多一次异步跳（毫秒级），**其余情况完全不多一次 await**。

**写法二（保守，零改动风险）**：不拆函数，只在 `play()` 里 fire-and-forget 调一次
`ensureMixAudioSession`。缺点是不保证「先激活再出声」，对**已经存在的音频流**可能不生效
（策略对已起的流是否追溯，各版本行为不一致）。**不推荐单独使用**。

### 6.3 订阅停用事件（这是现在完全缺的一环）

```ts
// init 里挂一次
mgr.on('audioSessionDeactivated', (ev: audio.AudioSessionDeactivatedEvent): void => {
  this.mixSessionMode = null;
  plogInfo(`[AudioSession] deactivated reason=${ev.reason}`);
  // TIMEOUT 且仍在播：说明用户没动，是被系统回收的 → 立刻补回来
  if (ev.reason === audio.AudioSessionDeactivatedReason.DEACTIVATED_TIMEOUT
      && ((AppStorage.get(STORE_IS_PLAYING) as boolean) ?? false)) {
    this.ensureMixAudioSession(true).catch((): void => { });
  }
});
```

`reason` 必须打出来：`TIMEOUT`（用户没动，系统回收）和 `LOWER_PRIORITY`（被抢）是两件不同的事，
前者应该自动补，后者至少要留证据。

> 注意：这条事件要求 `setAudioSessionScene()` 已调用（见放大器 4），否则收不到。

### 6.4 可选但不建议现在做：重建播放器

理论上最彻底的做法是「会话不一致时重建 AVPlayer，让新流在 MIX 策略下申请」。
但代价是「暂停 30 秒后点播放 → 卡 500ms 重新挂载音源」，体验损失比 bug 本身更大。
先把 6.1–6.3 做完，用真机验证「激活对已有流是否生效」；**只有确证不生效时**再上这条。

## 七、验收清单

改完必须逐条过，否则等于没改：

- [ ] 暂停 60 秒 + 别的 App 在播 → 点播放，**日志出现 activate 且不被打断**
- [ ] 连点播放/暂停 5 次 → 日志里 activate 只出现 1 次（没有每次都重开）
- [ ] 单曲循环放完自动重播 → 重播后切到别的 App 放歌，本应用不断
- [ ] 锁屏点播放（别的 App 在响）→ 不断
- [ ] 车机 / 蓝牙耳机线控播放 → 不断
- [ ] **关掉开关** → 暂停 60 秒后点播放 → 与改动前行为一致（仍被打断，不会静默变混音）
- [ ] 飞行模式 / 无其他音频时 → 播放无异常、无额外延迟感知
- [ ] `activateAudioSession` 失败场景（可临时 mock 抛错）→ 歌照常播，不静默卡死
- [ ] 前台 ↔ 后台往返 10 次 → 会话状态不抖、日志不刷屏

## 附：一句话记住

**这个 bug 的形态是「开关只在换歌时被写入，而系统会随时把它擦掉」。**
修法不是加强 activate，而是**在每一次要出声之前都确认一遍**。
