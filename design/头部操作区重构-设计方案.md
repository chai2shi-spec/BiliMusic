## 1. 问题诊断：不是「挤」，是一处结构性错误

先看数字。手机画布 356vp，头部区左右内边距 20，**可用宽度 316vp**。
按钮按源码实测口径算：`Button(type: Normal)` 默认左右 padding 各 16vp，13fp 汉字宽约 13vp，所以 **n 个字的按钮宽 = 13n + 32**。

| 元素 | 宽 |
|---|---|
| 播放全部（4 字） | 84 |
| 选择 / 订阅 / 排序 / 搜索（2 字） | 各 58 |
| 拉取新投稿（5 字） | 97 |
| 元素间距 gap | 各 8 |

**歌单详情 · 最坏情况（订阅 UP 歌单 + 可排序）**

```
84 + 58 + 97 + 58 = 297   ← 四个按钮
+ 4 × 8 = 32              ← 间距
= 329                     ← 固定占位
搜索框 = 316 − 329 = −13   ← 负值
```

这不是「搜索框很窄」，是**搜索框宽度为负、在画面上完全不存在**，而且整行还溢出 13vp。

**UP 主主页 · 最坏情况（未订阅，订阅按钮在）**

```
84 + 58 + 58 + 58 = 258 + 4 × 8 = 290
搜索框 = 316 − 290 = 26
```

26vp 减去 `SearchBox` 内部 `padding left 14 / right 34` 后是 **−22** —— 一个字形都放不下，实际什么都输入不了。

> 这些数字在原型里是实测的（用 iframe 读 `getBoundingClientRect().width`），不是估算：`row0 = [84, 58, 97, 58, 0]`、`row4 = [84, 58, 58, 26, 58]`。

### 根因三条

**① 输入框和按钮抢同一行。** `SearchBox` 以 `layoutWeight(1)` 嵌在按钮行里。按钮是固定宽、输入框是弹性宽 —— 于是「每多一个按钮，搜索就少 58–97vp」。**弹性元素和固定元素混排，弹性那个永远是最先被牺牲的。**

**② 低频动作占着最贵的位置。** 「拉取新投稿」97vp，真实使用频率是几天一次；「选择」58vp，只在整理歌单时用。两者合计 155vp，正好是搜索需要的全部空间。

**③ 所有按钮同权重。** 一排五个同色同形的按钮，用户每次都要在这一排里找「哪个是开始听」。

## 2. 设计原则：按「动作语义」分三层，而不是按顺序排成一排

| 层 | 承接什么 | 形态 | 宽度成本 |
|---|---|---|---|
| **L1 主行** | 这页唯一的主动作 | 一个撑满的主 CTA | 弹性（吃掉全部剩余） |
| **L2 入口** | 需要随时可达，但不该抢焦点的 | 两个 36×36 图标按钮 | 固定 88 |
| **L3 面板** | 低频、批量、配置类 | 底部 sheet | 0 |

宽度分配（实测）：

| 页面 | 主行内容 | 主 CTA 实宽 | 改前 |
|---|---|---|---|
| 歌单详情 | CTA + 🔍 + ⋯ | **228** | 84 |
| UP 主页 | CTA + 订阅 + 🔍 + ⋯ | **162** | 84 |

### 三条不可让的规则

**规则 1 · 搜索是「模式」，不是「控件」。**
常态只有一个放大镜图标。点它，**整行原位切换成搜索态**，输入框独占 278vp 并自动聚焦。退出用「取消」或返回键。
这一条把搜索宽度从 0（歌单）/ 26（UP）变成 **278**，放大 10 倍以上，且常态行零成本。

**规则 2 · 主 CTA 必须唯一且显眼。**
「播放全部」用**品牌色实底 + 深字**（`themePrimary` 底 + `themeOn` 字），高 36（比次级按钮 32 高 4），圆角 10。次级按钮保持「浅粉底 + 粉字」不变 —— 层级差靠**底色**，不靠字号。

**规则 3 · 低频动作进面板，但**不能**降级为「找得到才算能用」。**
面板里每一项都带**语义图标 + 副标注**（如「拉取新投稿 · 3 天前」）。判断标准是：**用户不需要学习就会去找 ⋯**，只要 ⋯ 是这一行最右、形状固定、位置恒定。

## 3. 歌单详情 · 逐区规格

### 3.1 标题行（`NavTitleRow`）

不变。`title: ''` 无标题变体（歌单名只在头部大字显示一次），`trailing` 保留「定位」按钮。

> 「定位」是**滚动中随时要用**的工具（长歌单里找当前播放），必须留在标题栏，不能进 ⋯ —— 进面板意味着每次都要「点开 → 找 → 点」，多两步。

### 3.2 头部信息区

不变：封面 96（圆角 12）+ 标题 28/36 Bold + 元信息 13/20 + 简介。
**建议顺手改一处**：简介 `descText` 现在是 `fontSize(12)`，落在 UI 铁律① 禁用的字号档（只允许 24/20/18/16/13/11）。改 `11`，行高 16。

### 3.3 操作行（常态）

```
┌──────────────────────────────────────────┐
│ [▶ 播放全部 ──────────────────] [🔍] [⋯] │   h=36
└──────────────────────────────────────────┘
```

| 元素 | 规格 |
|---|---|
| 主 CTA | `height 36` `borderRadius 10` `backgroundColor themePrimary` `fontColor themeOn` `fontSize 13 / 500` `layoutWeight(1)`，左侧 `play_fill` 图标 15 |
| 🔍 / ⋯ | 视觉 `36×36`，`borderRadius 10`，底 `themeSurface`，图标 18 `themePrimary`（深色模式用 `themeDeep`） |
| 命中区 | 用 `.responseRegion({ x: -4, y: -4, width: 44, height: 44 })` 外扩到 44，**不要**写 `width(44)` |
| 间距 | 元素间 8，行 `margin-top 12` |

### 3.4 搜索态（点 🔍 后）

```
┌──────────────────────────────────────────┐
│ [🔍 夜|                        ×]  取消   │   h=36
└──────────────────────────────────────────┘
```

| 元素 | 规格 |
|---|---|
| 容器 | `layoutWeight(1)`，`height 36`，`borderRadius 10`，底 `bgCard`，**1.5vp 品牌色描边**（聚焦态的唯一表达） |
| 输入 | `TextInput` 独占，`fontSize 14`，`placeholderColor text_tertiary`，**自动 focus 并弹键盘** |
| 框内 × | 24×24，`clearVisible` 条件不变（`searchKeyword.trim().length > 0`） |
| 取消 | 文字按钮，`fontSize 13`，`themePrimary`（深色 `themeDeep`），`flex: none` |
| 列表上方 | 一行 11fp `text_tertiary`：「匹配 N 首」—— 让用户知道是「被筛过了」而不是「歌单变短了」 |

**进出场**：整行 `transition(OPACITY, 160ms, EaseInOut)` 交叉淡出，容器给**固定高度 36**（源码已因这事踩过：换层期间退场节点脱离布局会塌缩）。

**退出**：点「取消」→ 清空关键词 → 收起 → 列表恢复全量。返回键在搜索态下先退搜索态，不退页面。

### 3.5 更多面板（点 ⋯ 后，`bindSheet`）

```
              ─── grab ───
  歌单操作                        ×
  排序方式
  ≡  按名称                      ✓
  ◷  按时长
  ▶  按播放量
  ＋  按加入时间
  ⧉  去重                    仅自建歌单
  ─────────────────────────────
  ↓  拉取新投稿                 3 天前
  ☑  选择曲目                  多选批量
```

| 项 | 语义 | 数据来源 |
|---|---|---|
| 排序 4 项 | 单选，当前项带 ✓ | 现有 `sortMenuItems()` 的 4 个 `applyAutoSort` 调用，**从二级 `bindMenu` 改为面板内直接列出** |
| 去重 | 仅 `playlist.sourceKind === ''` 时显示 | 现有 `confirmDedup()` |
| 拉取新投稿 | 仅 `LibraryStore.isUpSubscription(playlist)` 时显示 | 现有 `refreshUpTracks()`；副标注取「上次拉取时间」，`upRefreshing` 时文案切「正在拉取…」并禁用 |
| 选择曲目 | 进入多选 | 现有 `enterSelecting()` |

**为什么排序要拆掉二级菜单**：排序本身就是一个「在几个里选一个」的动作，再套一层菜单等于两步。4–5 项一屏放得下，直接列。

### 3.6 多选态（次要优化，可选）

现状 5 个按钮：`完成 / 全选 / 加入歌单 / 下载 / 移除`，`padding 10` 后约 314vp，**正好卡在 316 的边缘**，任何一个文案变长（「取消全选」）就会溢出。

建议：
```
┌──────────────────────────────────────────┐
│ [完成] [全选]        [＋] [↓] [🗑]        │
└──────────────────────────────────────────┘
```
右侧三个批量动作改 **40×32 图标按钮**（图标 18），命中区 44 外扩。改后约 207vp，留出 100+ 余量。
图标语义靠「进入多选时 toast 一次」补齐：`已进入多选 · 右下角可加入歌单 / 下载 / 移除` —— 只在本次会话首次进入时提示。

## 4. UP 主主页 · 逐区规格

结构与歌单详情同源（这是刻意的：**两个详情页右侧永远是「🔍 + ⋯」**，位置形状一致，用户学一次就够）。

### 4.1 操作行（常态）

```
┌──────────────────────────────────────────┐
│ [▶ 播放全部 ─────────] [订阅] [🔍] [⋯]    │   h=36
└──────────────────────────────────────────┘
```

**「订阅」必须留在主行。** 它是 UP 页的核心转化动作，埋进 ⋯ 等于把一个高频决策降到「找得到才算」。它只有 58vp，主行放得下（CTA 仍有 162）。

订阅态三种：

| 状态 | 表现 |
|---|---|
| 未订阅 | `订阅`，浅粉底 + 粉字 |
| 处理中（`subBusy`） | `处理中…`，`enabled(false)`，**且不挤走 🔍/⋯**（现在 `subBusy` 会让搜索区淡出，改后不需要） |
| 已订阅 | `✓ 已订阅`，**透明底 + 1vp `divider` 描边 + `text_secondary` 字**（弱化但不是隐藏），点击弹「取消订阅」确认 |

已订阅用 89vp（比未订阅多 31），CTA 从 162 降到 131 —— 仍比改前的 84 宽 56%，可接受。

### 4.2 搜索态

与歌单详情同一套，差别只有两点：

1. placeholder 是「搜索 TA 的投稿」；
2. **没有「搜索」按钮**。回车（`TextInput` 的 `enterKeyType: Search`）即触发 `runRemoteSearch()`。远程搜索在途时把输入框右侧 × 换成 14fp 的加载指示。

> 为什么删掉「搜索」按钮：这个按钮占 58vp，而它做的事和「键盘上的搜索键」完全一样。删掉后输入框多 58vp（278），且少一个「点了没反应」的误触源（源码里这个按钮因为 `enabled(false)` 会用系统灰字盖掉主题色，所以连禁用态都表达不了，空词点击只能靠宿主页兜底 no-op）。

### 4.3 更多面板

```
   UP 主操作                       ×
   ☑  选择投稿                  多选批量
   ─────────────────────────────
   ✕  取消订阅
```

只有两项，是刻意的：UP 页可收进面板的低频动作本来就只有这两个。**不要为了填满而发明功能**（我第一版画过「下载全部投稿」，源码里没有这个能力，删掉了）。

「取消订阅」放最后 + `text_error` 色，与安全操作分开 —— 和 `trackMenuItems` 的既有原则一致。

## 6. 三条实现约束（都已在源码里踩过）

**① 整行换层，不是摘按钮。**
源码注释原话：「不用『按钮 `visibility` 摘布局 + 尾部槽位换层』旧结构：退出多选时常态按钮瞬时回位，尾部槽位连同正在淡出的动作行一起被推向右侧（真机表现：动作组『向右消失』而非淡出）」。
做法：`Stack()` 内两态**条件渲染** + 交叉 `OPACITY`，`Stack` 给**固定 `height(36)`**。

**② 隐藏层必须真的不挂载，不能靠 `HitTestMode.None`。**
源码注释：「`HitTestMode.None` 只豁免容器自身，子按钮仍响应点击（真机复现：常态点搜索框位置误触透明的『加入歌单』/『下载』，搜索框要点多次）」。
所以搜索态与常态、面板与页面，一律走 `if (cond) { ... }`。

**③ 图标按钮 36 视觉、44 命中区，用 `responseRegion` 外扩。**
写 `width(44)` 会把操作行撑到 44 高、把整个头部往下推 8vp，列表首屏少半行。

## 9. 没有采纳的三种方案（及原因）

**① 缩小按钮（padding 16 → 8、字号 13 → 11）。**
5 个按钮能省 80vp，但代价是按钮变成「小字片」，`13fp` 已经是可读下限，`11fp` 在 356vp 屏上是 6pt 级别，触达和识别都崩。而且省下的 80vp 仍然不够搜索用（需要 150+）。

**② 操作行横向滚动。**
技术上可行（`Scroll` 横排），但滚动条不显示时用户不知道右边还有东西；且「播放全部」会被滚出视野 —— 主操作不该需要滚动才能点。

**③ 图标化所有次级按钮（选择/排序/拉取都变成图标）。**
省宽度最彻底，但「拉取新投稿」「排序」「去重」这三件事没有公认图标语义，用户必须逐个尝试。**图标化的收益是宽度，成本是试错** —— 而这三件事都是低频、失败代价不小的动作，不适合让用户试错。

> 结论：宽度问题应该用「层级」解决，不该用「压缩」解决。压缩只是把拥挤摊薄到每个元素上，而分层是把不常用的东西拿走。
