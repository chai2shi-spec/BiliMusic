## 1. 新发现的真 bug（2 处）

### 1.1 月/年翻页日期溢出 ★★（今天 10-31 即可复现）

`ListenDiaryStats.ts:205-221` 的 `diaryShiftAnchor`，月/年用 `setMonth`/`setFullYear` 平移：

```ts
} else if (period === DiaryPeriod.Month) {
  const d: Date = new Date(anchorMs);
  d.setMonth(d.getMonth() + delta);   // ← 31 号溢到次月
  shifted = d.getTime();
} else {
  const d: Date = new Date(anchorMs);
  d.setFullYear(d.getFullYear() + delta);  // ← 2-29 溢到 3 月
  shifted = d.getTime();
}
```

`setMonth`/`setFullYear` 在「日/月超界」时会**溢出到下个月**。锚点 `anchorMs` 初始就是
`Date.now()`，所以**只要今天落在 31 号**（或从某个月的 29/30/31 号锚点翻到天数更少的月份），
翻页就错位。实测（Node 复现）：

```
初始锚点  2026-10-31（今天）
点「上个月」→ 2026-10-01   ← 期望 9 月，实际还在 10 月！
再点「上个月」→ 2026-09-01 ← 才到 9 月，且从此每月都钉在 1 号
9-30 点「上个月」→ 2026-08-30（这天正常，因为 8 月有 30 号）
2024-02-29 点「上一年」→ 2023-03-01 ← 期望 2023-02-28
```

后果：用户点「上个月」看到「2026 年 10 月」，再点一次又变 9 月——月视图的翻页在
31 号这天是坏的，且之后锚点永久漂到每月 1 号，周/日视图从该锚点派生也会跟着偏一天。

**修法**（先归一化日/月，再平移周期，避开溢出）：

```ts
} else if (period === DiaryPeriod.Month) {
  const d: Date = new Date(anchorMs);
  d.setDate(1);                        // 先钉到 1 号，杜绝 31→次月
  d.setMonth(d.getMonth() + delta);
  shifted = d.getTime();
} else {
  const d: Date = new Date(anchorMs);
  d.setMonth(0); d.setDate(1);         // 先钉到 1 月 1 号，杜绝 2-29→3 月
  d.setFullYear(d.getFullYear() + delta);
  shifted = d.getTime();
}
```

日/周用 `anchorMs + delta × 86400000` 的固定毫秒增量在中国时区（无夏令时）是安全的，不动。

### 1.2 切周期标签云「标题新、内容旧」错配 ★

`ListenDiaryPage.ets:274-287` 的 `rebuild()`：

```ts
this.report = next;        // ① 同步：标签卡标题立即变「本月标签」
this.reportReady = true;
this.refreshTagCloud();    // ② 异步：await getTagsForBatch 期间 tagCloud 还是旧值
```

`refreshTagCloud` 内部先 `++tagCloudSeq` 再 `await getTagsForBatch(...)`。在 await 的窗口里，
`tagCloudSection`（`:890`）渲染的是：

```
本月标签            ← this.report.sectionPrefix（新周期）
[旧周期的标签云]     ← this.tagCloud（旧周期，还没被覆盖）
```

标题和内容来自两个不同周期。缓存命中时窗口是毫秒级（几乎无感），但**首次访问某个周期、
走网络时可达几百毫秒到秒级**——用户会看到「本月标签」下面挂着一串上周/上月的标签。

`tagCloudSeq` 的「旧不覆盖新」保护是对的，但它只防「旧结果晚到覆盖新结果」，
防不住「旧内容在新标题下短暂显示」。

**修法**：`rebuild()` 里更新 `report` 后、调 `refreshTagCloud()` 前，先清空：

```ts
this.report = next;
this.tagCloud = [];        // 新周期标签未就绪，整卡隐藏，避免标题/内容错配
this.reportReady = true;
this.refreshTagCloud();
```

代价是「标签卡短暂消失再出现」。若想更平滑，给 `tagCloudSection` 的内容加 200ms 淡入
（`.animation`），而不是让它突兀出现。注意清空后 `tagCloud.length === 0` 时卡片整块隐藏
（现有 `:1202` 的渲染条件已处理），无空占位、不打扰，符合设计。

## 2. 无障碍硬伤（第一轮完全没覆盖）

### 2.1 大字体（系统无障碍）下固定宽度列溢出

ArkUI 数字型 `fontSize(16)` 默认单位就是 **fp**，会跟随系统字号缩放（记忆里已确认）。
拾音页有多处**固定宽度列 + 不允许换行**的组合，系统字号一放大就截断：

| 位置 | 现状 | 放大后 |
|---|---|---|
| 时段标签列 `:828` | `Text(seg.label).width(32)`，13fp 两字 | 1.3× → 34vp 溢出 32vp，字被切 |
| 循环榜序号列 `:947` | `Text(rankLabel).width(24)`，24fp | 1.3× → 「01」超 24vp |
| KPI 数字 `:677` | 24fp，注释明说「4 位数会挤爆 83px 列」 | 放大后更挤，`maxLines(1)` 截断 |
| 时段右侧时长 `:844` | 11fp 右侧固定，`maxLines(1)` | 截断 |

**修法**（方向，不逐属性列）：
- 固定宽度列改 **`minWidth` + 自适应**：时段标签 `width(32)` → `.constraintSize({ minWidth: 32 })`
  或改 `layoutWeight`，让文字决定列宽、右侧时长被推开而不是被截。
- KPI 数字：大字档下允许降档（如 `@StorageProp` 读系统字号档，≥1.3× 时 24→18），
  或放开 `maxLines(1)` 让「1.2 万」这类短值换行不截断。
- 序号列同理 `minWidth(24)`。

原则：**文字永远比容器优先**——列宽让位于内容，而不是内容被列宽切掉。这条要写进
「UI 五条铁律」的无障碍补充。

### 2.2 减少动态（Reduce Motion）未遵循

- Hero Swiper `autoPlay`（`:625`）在系统「减少动态」开启时仍 4s 轮播；
- 分段滑块 `interpolatingSpring`（`:327`）过冲回弹、切周期 `animateTo`（`:278`）过渡都不降级。

**修法**：读系统无障碍「动画减弱」开关（`@ohos.accessibility` / 系统配置），为 true 时：
`autoPlay(false)`、弹簧改直接跳变（或 `curve: Curve.Linear, duration: 0`）、数字/柱高过渡关闭。
这是低成本、对敏感用户体感明显的一项。

## 3. 对第一轮 §5.1 完播率的口径修正

### 3.1 `completed` 无法区分「快进到结尾」与「手动切歌」

第一轮 §5.1 用 `!completed && ms < duration × 50%` 定义「中途切走」。但这个公式有个边界：

- **快进跳过结尾**：听了 90%、拖进度条到结尾 → `completed=false`（非自然播完）、
  `ms` 约等于 duration×90%，**不满足** `ms < duration×50%`，不会被算成切走 —— 这条碰巧安全。
- **但「听了一半手动切歌」和「快进到 60% 又切」会被判为「中途切走」**，而它们其实是
  「正常换歌」，不是「听不下去」。用 `completed` 单一布尔做「放弃」判定，
  会**把「主动切歌」和「听不下去」混为一谈**，`abandonedCount` 会系统性偏高，
  文案「12 首中途切走」里大部分其实是「正常换歌」。

**结论**：`completed` 能支撑「完播率」（`Σ completed / Σ 有效收听`）这个指标没问题，
但「中途放弃清单」需要更细的信号才能不冤枉用户。两个选项：
- (a) **保守口径**：只把 `ms < 30000`（连 `VALID_MIN_MS` 都没到的会话）且 `!completed`
  记为「听了开头就切」，语义改成「试听」，负面评判最轻、也最不容易错；
- (b) **P2 扩展**：`PlaySession` 增加 `endReason: 'completed' | 'skip' | 'pause-exit' | 'error'`
  与 `endedAt`，把「快进/手动切/出错」分开。旧行回落 `completed` 推导。

推荐先用 (a) 落地（零改模型），(b) 记入 P2 与 `source` 字段同一批做。

## 4. 清理项（小，顺手做）

### 4.1 `DiaryBucket.showLabel` 零消费

`ListenDiaryStats.ts:50` 定义了 `showLabel`，`:704` 也计算了，但页面 X 轴（`:770-778`）
只读 `b.label`（空串即不显示），**从未读 `b.showLabel`**。与第一轮 `heroLabel` 同性质：
字段算了却没人用。要么删掉 `showLabel`（label 空串已承载「不显示」），要么让 X 轴读它。
建议删字段，减少一个「看起来有意义、实际冗余」的坑。

### 4.2 注释与代码不一致

- `ListenDiaryStats.ts:766` 注释「循环榜榜单取前 3（设计 §4.7）」，实际 `ListenDiaryPage.ets:1006`
  是 `slice(0, 5)`。Top5 才是现状。注释过时，会误导后来者按「前 3」去改。
- `:1004` 注释「topTracks 上限即 5（Hero 轮播与榜单共用同一数据源）」是对的，和 `:766` 矛盾。

**修法**：把 `:766` 改成「循环榜榜单取前 5（与 Hero 轮播共用 topTracks）」。

### 4.3 翻页下限应是保留期下限，而非 2000 年

`MIN_ANCHOR_MS = 946684800000`（2000-01-01，`:159`）是防「翻到 1970」的护栏，但数据只有
13 个月（`PlaySessionStore.RETENTION_MONTHS`）。用户把年视图一直往前翻，会翻过 2000 到
2026 年之间整整 26 年的空周期。结合第一轮 §3.4 的 `outOfRetention`：翻页下限应钳到
**保留期下限**（13 个月窗底），到边时左箭头禁用（与右箭头「已是最新」对称），
而不是放任翻到 2000 年再靠空态提示。

## 5. 隐私透明度

### 5.1 标签云会联网拉取 B 站标签，用户不知情

拾音页的「标签云」是唯一一个**为个人听歌记录发起联网请求**的区块：
`refreshTagCloud` → `getTagsForBatch` 会把本机听过的 BV 号批量发给 B 站换标签。
听歌日记本身是「纯本地私人报告」的定位（页面文件头也这么写），但标签云悄悄破了这个
「纯本地」的心智。

**建议**（择一）：
- 首次进拾音页时，标签卡位置给一行 11/tertiary 小字「标签来自联网匹配，仅用于展示」；
- 或设置页加一个「拾音标签云」开关，默认开，关掉后标签卡不再联网。

成本极低，但把「本地」与「联网」的边界交代清楚，符合 App 一贯的隐私红线（参考导入
的 skipCookie/skipReferer 处理风格）。

## 6. 可选性能合并

`computeDiaryReport` 对 `allSessions` 做了**两趟全量遍历**：第一趟（`:538-587`）聚合
track/up + firstSeenAt，第二趟（`:661-679`）分桶 + 时段累加。第二趟本可并入第一趟
（分桶只依赖 `startedAt`/`ms`，第一趟已经拿到）。当前 1.3 万条 × 两趟 ≈ 2.6 万次循环，
单次 <2ms，**收益有限**；但既然第一轮已记了「`reload` 全量重扫」备查，这条也一并记入，
将来把 `historySessions` 改成增量维护时顺手合并即可。
