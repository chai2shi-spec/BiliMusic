# 拾音页（ListenDiaryPage）优化与功能增强方案

> 阅读范围：`pages/ListenDiaryPage.ets`（1272 行）、`service/ListenDiaryStats.ts`（1005 行）、
> `service/PlaySessionStore.ts`（287 行）、`service/VideoTagStore.ts`、`player/MusicPlayer.ts` 会话结算段、
> `common/DaySegments.ts`、`pages/Index.ets` 页签与标题栏段。
> 本文只做诊断与设计，**不改任何 App 代码**。

---

## 0. 结论摘要

页面本身已经相当完整（9 个区块、四周期、实时刷新、空态三分）。问题不在「少东西」，
而在三类：

| 类别 | 数量 | 说明 |
|---|---|---|
| **口径与文案 bug** | 4 处 | 有 3 处是真实可复现的错误文案/数字，不是风格问题 |
| **已采集但零使用的数据** | 1 个字段 | `PlaySession.completed` 写进日志 13 个月，全项目无消费者 |
| **可用性硬伤** | 4 处 | 其中「日视图回不到今天」最影响日常使用 |
| **可增强（数据现成）** | 5 项 | 不需要新增任何采集，只改聚合层 |

最值得做的三件事，按性价比排：

1. **把 `completed` 用起来** —— 完播率 / 中途放弃清单，日志里早就有，只是没人读。
2. **加「回到今天」** —— 日视图翻 30 天要点 30 次，这是每天都在发生的摩擦。
3. **修 3 处文案 bug** —— 往期「新面孔」卡永远写「本周」，翻页时很扎眼。

## 1. 口径与文案缺陷（可复现）

### 1.1 往期「新面孔」卡标题不随翻页变化 ★

`ListenDiaryStats.ts:846`：

```ts
const facePrefix: string = period === DiaryPeriod.Year ? '今年' : buildSectionPrefix(period, range, true);
//                                                                                          ^^^^ 硬传 true
```

`buildSectionPrefix` 的第三个参数是 `isCurrent`。传死 `true` 的后果：

- 翻到 **3 个月前那一周**，卡片标题仍是「**本周**新面孔」；
- 翻到 **上个月**，仍是「**本月**新面孔」；
- 翻到 **2025 年**，仍是「**今年**新面孔」。

同一屏里其它区块（`sectionPrefix`，见 `:902`）是对的，会显示「10月20日那周循环」。
两个前缀在同一屏内不一致，用户翻页时最容易察觉。

**修法**：把 `true` 换成 `isCurrent`，年视图的特判改成 `isCurrent ? '今年' : \`${from.getFullYear()}年\``。

### 1.2 「你遇见了 N 首歌」与 KPI「N 首歌曲」是两套口径 ★

`sentence` 的 `metCount` 用 `trackList.length`（`ListenDiaryStats.ts:864`），
而 KPI 的「首歌曲」用 `validSongs`（`:612-619`，只数 `plays > 0` 的）。

两者的差别：`trackAggs` 对**区间内每一个会话**都建桶，包括「听了 5 秒就切」的
（`appendSession` 只过滤 < 1s，1s–30s 全部入日志但不计入有效收听）。

于是会出现同一屏上：

```
你遇见了 47 首歌          ← metCount = trackList.length
[ 38 首歌曲 ] [ 126 次播放 ]  ← validSongs
```

47 > 38，两句话在说同一件事却给了两个数。歌越杂（大量试听后切换）差得越多。

**修法**：`metCount` 改用 `validSongs`，或句式改口径为「打开过 N 首歌」。

### 1.3 `heroLabel` 生成后零消费 —— 设计稿的封面胶囊没渲染

`DiaryReport.heroLabel`（`:101`）在 `buildHeroLabel`（`:288`）里算出了
「今日封面 / 本周封面 / 年度封面 / 10月20日那周封面」这一整串文案，
但 `ListenDiaryPage.ets` 里**一次都没读**（实测 `grep "this.report.heroLabel"` = 0 处）。

`heroCard`（`:539-581`）只有封面 + 底部渐变 + 标题/副行，没有设计 §4.3 规定的左上角胶囊。
空态与有数据两条路径都没有。

**修法**：在 `heroCard` 的 `Stack` 内加左上角胶囊（`Alignment.TopStart`，11/Medium 白字，
`rgba(0,0,0,.42)` 底、圆角 pill、`padding 6/2`），文案取 `report.heroLabel`。

### 1.4 往年年视图的「新面孔」会严重虚高

`newFaces` 判据是 `firstSeenAt ∈ [range.fromMs, range.toMs)`（`:833`），
而 `firstSeenAt` 只能在全量会话窗内求最小值 —— 这个窗被 `querySessions` 钳到
**13 个月**（`PlaySessionStore.ts:205-209`）。

所以翻到 2025 年时，窗内最早的会话是 2025-11，任何 UP 的 `firstSeenAt` 都落在
2025-11 之后，**只要那一周听过就算「新面孔」**。结果是「2025 年新面孔 42 位 UP 主」
这种明显失真的数字。

**修法**（择一）：
- (a) 往期年视图直接隐藏新面孔卡 —— 最诚实，成本最低；
- (b) 卡片副行加限定语「13 个月内首次出现」；
- (c) 把窗口下限写进 `DiaryReport` 并在标题显露「近 13 个月」。

推荐 (a) + (b) 组合：往期年视图隐藏，其余周期副行见 §3.4。

## 2. 已采集但零使用的数据

### 2.1 `PlaySession.completed` 写进了日志，但没有任何消费者

`PlaySessionStore.ts:54` 定义、`:178` 解析、`MusicPlayer.ts:4375` 写入：

```ts
completed: this.diarySessionCompleted
```

全项目 `grep "\.completed"` 排除 `PlaySessionStore.ts` 后，命中的全是
`DownloadTask.completedAt`（另一个概念）。**`ListenDiaryStats` 从未读 `s.completed`。**

这意味着下面三个指标今天就能算，却一个都没算：

| 指标 | 公式 | 价值 |
|---|---|---|
| 完播率 | `Σ completed / Σ 会话数` | 最直观的「你有多认真在听」 |
| 中途放弃数 | `!completed && ms < duration × 0.5` | 「有 12 首你听了开头就切了」 |
| 放弃清单 | 上式的曲目列表 | 天然的「待重听」候选池 |

而且判据已经现成：`isValidListen` 的**反面**就是定义明确的中途放弃
（`ms < 30000 && ms < duration × 0.5`），两边口径天然互补，不会出现
「既算有效收听又算放弃」的矛盾。

### 2.2 `PlaySession` 缺 `source` 字段 → 「哪个歌单听得最多」做不了

会话落库字段（`:34-55`）有 `trackId/title/artist/upMid/coverUrl/bvid/durationMs/startedAt/ms/completed`，
**没有来源**。所以下面这些常见问题今天无法回答：

- 这个月是「每日推荐」听得多，还是我自己的歌单？
- 从收藏夹同步进来的歌，我真的在听吗？

`Track` 本身有来源概念（`TrackSource`），但 `appendSession` 没有透传。
这属于 P2 的数据模型扩展（见 §5）。

## 3. 可用性缺陷

### 3.1 日视图回不到今天 ★★

`periodPager`（`ListenDiaryPage.ets:492-536`）只有 `‹` 和 `›` 两个箭头。
日视图下每翻一天点一次 44vp 的按钮 —— **从今天翻回一个月前要 30 次点击**，
而且中途没有任何「跳过 N 天」的捷径。周视图要好一些（4 次/月），
但连续翻 3 个月同样难受。

这是本页唯一每天都在发生的摩擦。

**修法**：非当前周期时，在翻页行**右侧**出现「今天」小字按钮（13px，`themeDeep`），
点一下 `anchorMs = Date.now()` + `rebuild(true)`。当前周期时该按钮不渲染
（不是禁用，是不占位），所以行宽不变。

可选加强：点日期文案本身唤起 `bindSheet` 日期选择器（日/周/月/年各自给粒度）。
但「今天」按钮单独就能解决 90% 的场景，先做这个。

### 3.2 首帧是一块空白，不是骨架

`build()`（`:1238-1242`）：

```ts
if (!this.reportReady) {
  // 全量会话读回前只渲染骨架（避免先闪一版空态再跳变）
} else {
  this.mainContent()
}
```

注释写「骨架」，实际 `if` 分支里**什么都没画** —— 只有顶部占位 Row。
全量 `querySessions` + `JSON.parse` 13 个月分片的耗时（冷启动首次进页，几百毫秒级）
期间，用户看到的是标题栏下方的纯背景色。

虽然冷启动门控（`loadStatsOnce`）已经把这段耗时从启动路径挪到了首次进页，
但它仍然暴露在用户眼前。

**修法**：画 3 个灰块占位（分段 32 / Hero 152 / KPI 24 高一行），
`bg_divider` 底 + 圆角，不需要 shimmer 动画（几百毫秒的加载配呼吸动画反而更闹）。
或者更省事：Hero 位直接渲染 `CoverImage({url:''})` 的空占位（自带音符 + surface 底），
视觉上和真实空态连贯。

### 3.3 循环榜只能播，没有任何长按能力

`topLoopRow`（`:940-1002`）整行 `onClick` = `playOrToggle`。没有长按。

对比全站其它列表（`TrackItem` 有长按菜单、下载页有长按），拾音页的榜单是**只读**的。
用户看到「本周听了 12 次」的第一反应往往是「加进收藏 / 加到待重听 / 看看这首歌」，
现在一个都做不到，只能点一下开始播、再自己去别处找。

**修法**：`gesture(LongPressGesture)` → `bindMenu` / `bindSheet`，菜单项：

```
播放 / 下一首播放 / 加入队列
收藏（★ 已有 LibraryStore 设施）
查看歌曲详情
复制歌名
```

注意别加「从榜单移除」这类会破坏统计真实性的操作。

### 3.4 13 个月保留期没有任何提示

`RETENTION_MONTHS = 13`（`PlaySessionStore.ts:61`），`querySessions` 把 `fromMs`
钳到保留窗下限（`:207`）。用户把年视图往前翻到前年，看到的是完整的空报告 +
「2025年新面孔」卡（见 §1.4），完全没有「超出统计范围」的说明。

**修法**：`DiaryReport` 增加 `outOfRetention: boolean`（`range.toMs <= retentionFloor`），
为 true 时把空态文案从「这一年你没有听歌记录」换成
「拾音只保留最近 13 个月的记录」（13px/tertiary，居中，同位置）。

## 4. 性能与网络

### 4.1 标签拉取失败不写缓存 → 断网时每次切周期重打 5 轮请求 ★

`VideoTagStore` 的设计是「失败不写缓存」（`:26-28` 注释明确），
`getTagsForBatch`（`:174-194`）按 4 并发分块串行推进。

20 首曲目 = 5 轮串行请求。**断网 / 被风控时，这 5 轮全部失败，且不写缓存**，
于是每次切周期、每次翻页、每次 `sessionRev` 变化触发的 `rebuild`
都会重新打这 5 轮（`ListenDiaryPage.ets:294` 的 `refreshTagCloud` 是无条件调用的）。

实测影响：断网状态下在拾音页切 4 次周期 = 20 次失败的网络调用。

**修法**：加「本次会话内的失败短路」—— `getTagsForBatch` 连续失败 N 次
（建议 3）后本进程内直接返回空，不再发请求；或者按 `bvid` 记一个
`failedAt` 时间戳，5 分钟内不重试。

### 4.2 每次 `sessionRev` 变化都全量重扫 + 重排

`reload()`（`:260-271`）调 `querySessions(0, Date.now())` —— 每次都把 13 个月
全部分片里的会话过滤一遍、`push` 进新数组、再 `sort`（`PlaySessionStore.ts:223`）。

`monthCache` 让读盘免了，但**数组重建和排序没有免**。1.3 万条会话时单次约 1–3ms，
用户感知不到；但每次切歌都会触发（800ms 去抖后），且每次都产生一个 1.3 万元素的新数组
→ GC 压力。

**修法（可选，收益有限）**：`appendSession` 时同步把新会话 push 进页面持有的
`historySessions` 尾部（时间单调递增，天然有序），`reload` 只补差集。
但这会引入「页面与 store 双写」的一致性风险，**不建议现在动** —— 记在这里备查。

### 4.3 `topLoopList()` 在 `ForEach` 里被调用两次

`:1019-1035`：`ForEach(this.topLoopList(), ...)` 和内部的
`if (idx < this.topLoopList().length - 1)` 各 `slice` 一次。
每次重渲染产生两个新数组。数量级极小（5 个元素），**不值得改**，列出来是因为
它属于「每帧都会执行」的路径，将来榜单扩容时要注意。

## 5. 功能增强：P1（零新增采集，只改聚合层）

这一档的共同点：**日志里已经有全部所需字段**，只差聚合函数与渲染。

### 5.1 完播率与中途放弃

新增 `DiaryReport` 字段：

```ts
/** 有效收听里自然播完的占比（0–100；无有效收听 = -1） */
completionPct: number;
/** 中途放弃的曲目数（!completed 且 ms < duration × 50%） */
abandonedCount: number;
```

**放哪里**：不新增卡片。塞进「听歌节奏」卡底部那一行 —— 现在那里只有
`虚线 = 日均 1.8h`（`avgLabel`），右侧还有大片空白：

```
虚线 = 日均 1.8h                              完播 76% · 12 首中途切走
```

前者 11/tertiary 左对齐，后者 11/tertiary 右对齐。一行两信息，零高度成本。

**文案纪律**：「中途切走」不用「放弃」「跳过」（带负面评判）。

### 5.2 与上一周期对比（环比）

新增字段：

```ts
/** 与等长上一周期的时长差（ms，正=变多）；无上期数据 = 0 */
deltaListenMs: number;
/** 上一周期时段时长（对比基准，0=无基准） */
prevListenMs: number;
```

**放哪里**：KPI 四格整体下方加一行 13/tertiary 居中小字（高度 +17）：

```
比上周多听了 1.2 小时
比上月少听了 40 分钟
```

只在 `prevListenMs > 0 && delta !== 0` 时渲染，否则不占位。
不逐格加箭头 —— 四格里只有「时长」和「次数」的环比有解释力，
「不同歌曲」「天听歌」的环比容易读出噪音。

**注意**：周环比的基准是「等长上一周期」，不是「上周同期」。
本月 1–10 号的对比基准是「上月 1–10 号」，否则月中看进度会一直是负的。

### 5.3 连续听歌天数

新增：

```ts
/** 当前连续听歌天数（截至周期末或今天） */
streakDays: number;
/** 历史最长连续天数（13 个月窗内） */
longestStreakDays: number;
```

已有 `listenedDays: Set<dayStamp>`，但只在周期内。连续天数要跨周期，需要
在全量会话上再跑一趟「按日去重 + 找最长连续段」。

**放哪里**：两个候选 ——
- (a) 一句话句式新增一类：`你已经连续 23 天打开拾音，最长纪录是 41 天`；
- (b) 常听 UP 卡下方一行小字。

推荐 (a)：连续天数本质是「一句话」级别的情绪信息，不属于数据区块。
且句式库已有 5 类 30 变体，加第 6 类符合既有结构。

**注意**：连续判定必须基于**有有效收听的日**，否则「打开 App 但没播」也算，
用户会觉得数字对不上。

### 5.4 「回到今天」按钮

见 §3.1。规格：

```
位置：periodPager 行右侧，宽 44 / 高 44（与左右箭头同尺寸，命中区一致）
文案：今天（13px / themeDeep）
出现：!report.isCurrent 时渲染，当前周期不占位
```

四个周期都用「今天」这个词？日/周/月视图用「今天」成立（今天所在的周/月）；
年视图用它也可以（今天所在的年）。**统一用「今天」**，不做四套词。

### 5.5 收听流水页（二级页）

现在有「聚合」，没有「流水」。`RecentPage`（最近播放）只保留 7 天 100 条，
且是按 `playedAt` 去重后的**曲目列表**，不是会话流水。
`PlaybackLogPage` 是错误日志，无关。

**建议**：新增二级页「收听流水」，按会话时间倒序：

```
10月25日 周六
─────────────────────────────
21:04  《歌名》          4:12  ✓ 听完
20:51  《歌名》          0:38  切走
20:33  《歌名》          3:58  ✓ 听完
─────────────────────────────
10月24日 周五
...
```

数据完全现成（`startedAt` + `ms` + `completed`），无新增采集。
入口放在循环榜标题右侧的「全部 ›」，或翻页行下方一行小字。

**为什么值得做**：拾音页现在是「结论」，没有「依据」。用户看到「本周听歌 6.2 小时」
想去核对时，没有任何地方能查。流水页补上这个闭环，也让 §5.1 的「完播率」
变得可验证 —— 数字有了出处，才不像编的。

## 6. 功能增强：P2（需要扩数据模型）

这一档要改 `PlaySession` 结构，涉及历史数据兼容（旧行缺字段→回落默认值），
不适合和 P1 混做。

### 6.1 会话来源

`PlaySession` 增加 `source: string`（`playlist:${id}` / `fav:${id}` / `search` / `home` / `recent`）。
`MusicPlayer` 在 `loadAndPlay` 时已知来源，透传即可。

落地后能做：**「这个月哪个歌单听得多」**（横向占比条），
以及验证收藏同步的价值（「从收藏夹同步的 320 首里，你真的听了 47 首」）。

### 6.2 输出设备

`STORE_BT_*` 系列已有蓝牙状态。会话记录 `output: 'speaker'|'wired'|'bt'` 后，
可以做「你有 62% 的时间在用蓝牙听」—— 这个数据对用户有新鲜感，成本也不高。

### 6.3 主观情绪与推断情绪

见 `design/听歌日记-心情手记-设计方案.md` 与 `design/听歌日记-情绪分析-设计方案.md`。
这两份方案的前提（`PlaySession` 会话日志）**现在已经具备**，落地门槛降低了。
但情绪层是独立的一整套交互（编辑态、罗盘、纠正面板），不应塞进本次优化。

## 7. 明确不做的事

| 候选 | 不做的理由 |
|---|---|
| 年度回顾视频 / 长图分享 | 无视频能力；图片分享属 Phase 2，且要先解决 §5.5 的「依据」问题 |
| 排行榜社交化（好友对比） | 本 App 无社交关系链，凭空造「好友」= 假数据 |
| AI 生成一句话 | 现有 30 条变体确定性轮换已经够用；接大模型会在离线/隐私上开新口子 |
| 逐柱点击查看详情 | 柱状图桶是聚合值，点开只能显示「这一小时听了 5 首」，信息密度太低 |
| 五维音乐人格雷达 | 只有一路信号（会话日志），硬拆五维就是编数据 |
