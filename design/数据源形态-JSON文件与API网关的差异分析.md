# 数据源形态对比 · 读取 JSON 文件 vs 调用 API

> 2026-10-25 · **只做分析，代码零改动**
> 承接 `design/空壳化-自定义API网关实施规格.md`（L1 方案）
> 目标工程：`E:/BiliMusic/HarmonyOS-Phone`

---

## 0. 先说结论

**有区别，而且区别比想象大 —— 但取决于你说的「JSON 文件」是哪一种。** 这两种解读的技术结论完全相反，必须先分开：

| 解读 | JSON 里装什么 | 与 API 网关的关系 | 能力影响 |
|---|---|---|---|
| **A · 数据源** | 歌单、曲目、音频路径、歌词、封面 | 是 L2 通用协议的一个特例 | **功能大幅退化**，退成「本地音乐库播放器」 |
| **B · 配置文件** | 网关地址、多源列表 | **就是 L1，只换了输入方式** | **零退化**，功能 100% 保留 |

如果你要的是 B（把地址写在 json 里而不是输入框里），那**几乎没有区别**，只省掉一个设置页输入框，反而多了一堆「文件放哪、怎么选」的麻烦 —— 不值得。

如果你要的是 A（数据本身来自 json），那**区别是本质性的**：app 从「客户端」变成「播放器」。下面全部在讲 A。

一句话概括本质差异：

> **API 是「请求-响应」，每次都能拿到新的、且能写回；JSON 是「导入-快照」，一次性、只读、会过期。**

## 1. 最硬的一条限制：音频怎么来

这一条决定了 JSON 方案的天花板，必须先讲。

### 1.1 B 站直链是有有效期的

`api/BilibiliApi.ts:1265-1266` 的注释自己写明了：

```
// 直链真的过期（AVPlayer 报 error）时，由 MusicPlayer.reloadCurrentSource
// 以 refresh=true 强制刷新兜底 —— 缓存永远不会把「过期链接」变成死胡同。
```

也就是说：**JSON 里存 B 站 playurl 直链，导出那一刻能用，几小时后整份文件全部失效**。而且失效是「静默的」——文件还在、UI 还在，只有点了播放才报错。

所以 JSON 方案要真正可用，音频**必须指向本地音频文件**，不能指向 URL。

### 1.2 好消息：本地音频播放这条链路是现成的

这一点很关键，比预想的便宜得多。工程里已经有三块现成能力：

| 能力 | 位置 | 说明 |
|---|---|---|
| `Track.localFilePath` 字段 | `model/MusicModels.ts:153-161` | 注释原文：**「非空即代表不用联网解析音源，直接播本地文件（离线也能放）」** |
| 播放调度 | `player/MusicPlayer.ts:2275-2289` | `localFilePath` 非空 → `loadLocalFile`，否则走网络 |
| 本地媒体源 | `player/MusicPlayer.ts:1804` / `:1859` | `switchSourceLocal` + `createMediaSourceWithFd`（不是拼 `file://`，fd 才是官方入口） |

`loadLocalFile` 的注释写得很直白（`:1892-1896`）：

```
* 结构与在线链路刻意保持一致 —— 同样的 token 校验、同样的 pendingSeekTo 续播机制、
* 同样的 recordRecent 时点，唯一区别是「不发任何网络请求」。
* 这样 play / pause / seek / 自动下一首这些既有逻辑一行都不用动。
```

**结论：JSON 方案在「播放」这一环几乎免费。** 真正的工作量全在「怎么把 json 变成 `localFilePath` 非空的 Track 列表」和「封面/歌词怎么办」。

### 1.3 因此 JSON 方案的真实形态

不是「空壳音乐 app」，而是：

> **「批量导入本地音频 + 元数据清单」的库管理功能。**

它和现有的「下载管理」在数据形态上是同构的 —— 都是「本地文件 + Track 元数据 + `localFilePath`」。区别只是文件的来源：一个是 app 自己下载的，一个是用户从外面拷进来的。

这既是它的可行性来源，也是它的天花板来源。

## 2. 逐项能力对照（12 项）

以 BiliMusic 现有功能清单为准，逐条判断。

| # | 功能 | API 网关（L1） | JSON 文件（A） | 说明 |
|---|---|---|---|---|
| 1 | 播放音频 | ✅ | ✅ **但需本地文件** | 见 §1 |
| 2 | 歌词 | ✅ 三源在线竞速 | ⚠️ 必须内嵌 | 见 §3.2 |
| 3 | 封面 | ✅ CDN 直链 | ❌ **需新写本地图加载** | 见 §3.1，全仓 `file://` 0 处 |
| 4 | 进度记忆 / 续播 | ✅ | ✅ | 纯本地，无差别 |
| 5 | 歌单增删改 | ✅ | ⚠️ 可写本地库，但**改不回 json** | 见 §4 |
| 6 | 搜索 | ✅ 全站搜索 | ❌ 只能搜本地已导入 | 语义完全变了 |
| 7 | 首页推荐 / 热门 / 排行 | ✅ 每次刷新都新 | ❌ 一次性快照，永不变 | 首页会「死」 |
| 8 | 收藏夹 | ✅ 读 + 写 + **双向同步** | ❌ 完全不可用 | 没有 push 目标 |
| 9 | 稍后再看 | ✅ 读 + 写 | ❌ 不可用 | 同上 |
| 10 | UP 主主页 / 关注列表 | ✅ | ❌ 不可用 | 需要 upMid 维度实时数据 |
| 11 | 分 P / 合集展开 | ✅ 点击时展开 | ⚠️ 必须预先展开写进 json | 合集成员变动后过期 |
| 12 | 登录 | ✅ | ❌ 无意义 | 没有服务端可写 |
| — | 下载 | ✅ | ⚠️ 概念消失 | 已是本地文件，无需再下 |

**保留 5 项、降级 3 项、不可用 5 项。**

值得注意的是第 7 项：**首页推荐一旦变成 JSON 快照就会「死掉」** —— 每次打开都是同一批歌。这对「音乐 app」的体感是致命的，因为推荐流是最主要的发现入口。JSON 方案实际上要求整个首页改造成「本地库视图」。

## 3. 三个真实缺口（都是 JSON 方案特有，改参数解决不了）

### 3.1 封面：本地图片这条路从未走过

全仓检索结果：

- `toThumbUrl`（`utils/TextUtil.ts:31-37`）只会给 `hdslb.com` 域名追加 `@128w_128h_1c.jpg`，**其他 URL 原样返回**
- `grep -rn "file://"` 全仓 **只有 1 处**，且在 `MusicPlayer.ts:1795` 的注释里（说明为什么**不用** `file://`）
- 已下载的曲目，封面**仍然是在线拉的** —— `DownloadsPage.ets:1441` 用的还是 `CoverImage({ url: toThumbUrl(t.coverUrl, 128) })`

也就是说：**即使「下载」这个功能已经存在，本地封面显示也没有实现过。** 完全离线的 JSON 方案需要新写一条「沙箱文件 → Image」的加载路径（`Image` 组件吃沙箱路径需要 `file://` 前缀或 fd，是新的实现，不是配置）。

这是 JSON 方案里最容易被低估的一项。

### 3.2 歌词：结构不匹配，但缓存层可以直接用

`model/MusicModels.ts:507-520` 的 `LyricResult` 不是 LRC 文本，而是**解析后的结构化结果**：

```typescript
export interface LyricResult {
  lines: LyricLine[];      // 已解析的行
  synced: boolean;         // 是否带时间轴
  instrumental: boolean;   // 是否纯音乐
  trackName: string;
  artistName: string;
  sourceId: string;
  source?: string;
  hasTranslation?: boolean;
  dynamic?: boolean;       // 是否带逐字轨
}
```

JSON 里如果内嵌 LRC 原文，需要先过一遍既有的 SPL 解析器才能变成 `LyricResult`。好消息是 `service/LyricCacheStore.ts` 的写入口是现成的 —— 导入时直接把解析结果写进歌词缓存目录（`${filesDir}/lyrics`），后续渲染链路零改动。

⚠️ 注意：歌词缓存**绝不能进 Preferences**（该文件头已明令），必须走文件系统。这一点原有设计已经做对了。

### 3.3 存储：JSON 文件反而是优势，但数据不会自动同步

现有存储的两条硬约束：

- Preferences **单值 8192 字节上限**，`LibraryStore` 按 `PREF_VALUE_BUDGET_BYTES = 6000` 分片
- 歌单/最近播放都走这套分片机制

JSON 文件**没有这个上限** —— 一份文件装几千首毫无压力。这是它相对「手动输入 API」的唯一实质性技术优势。

但代价是：**JSON 是「入」不是「出」**。用户导入后如果在 app 里改了歌单、加了几首、听了几个进度，这些改动落在 Preferences / RDB 里，**不会回写 json**。下次再导入同一份 json，改动会被覆盖或产生重复。这是「文件」形态的固有缺陷，除非额外做双向合并 —— 而那需要「哪边更新」的判定规则，复杂度会接近 `FavSyncManager`。

## 4. 一个反直觉的结论：JSON 不该替代 API，应该作为 API 的出口

上面列的缺口加起来，意味着「纯 JSON 版 BiliMusic」等于把 app 重做成另一个产品（本地音乐库播放器），代价 2~3 周，还要放弃 5 项功能。

**但如果把 JSON 当「导出/备份格式」而不是「数据源」，它是纯收益的：**

| 场景 | 现在的状态 | 有 JSON 导出后 |
|---|---|---|
| 换手机 / 重装 | 歌单靠 Preferences，重装即丢 | 导出一份 json 带走，新机导入 |
| 分享歌单 | 无 | 发文件给对方 |
| 离线备份 | 无 | 可选「连音频一起导出」 |
| 调试 / 排障 | 需抓 Preferences | 直接看 json |

而且这条路**和 L1 完全不冲突**：L1 解决「怎么连」，JSON 导出解决「怎么带走」。两者共用同一套 `Track` 序列化（`slimTrack` 已经在做类似的事）。

**推荐组合：先 L1，再把 JSON 作为「库导出」功能。** 不建议用 JSON 替换 API。

## 5. 如果确定要做 JSON 数据源，最小可行形态

（仅供决策参考，不代表推荐）

### 5.1 Schema 草案

```jsonc
{
  "schemaVersion": 1,
  "exportedAt": 1761350400,
  "playlists": [
    {
      "id": "local-pl-1",
      "name": "我的本地歌单",
      "tracks": [
        {
          "id": "local::0001",
          "title": "曲名",
          "artist": "歌手",
          "duration": 245,
          "audioPath": "audio/0001.m4a",   // ⚠️ 相对路径，绝对路径换机即废
          "coverPath": "cover/0001.jpg",   // 可选
          "lyricPath": "lyric/0001.lrc",   // 可选
          "bvid": "", "cid": "", "upMid": "",  // 留空；有值则保留「去 B 站看」能力
          "playCount": 0,
          "pubdate": 0
        }
      ]
    }
  ]
}
```

三条硬性设计约束（都是踩过的坑）：

1. **`audioPath` 必须是相对路径**，相对 json 文件所在目录。绝对路径里含沙箱 uuid，换设备 / 重装后全部失效。
2. **必须有 `schemaVersion`**。没有版本号的导入格式，第一次改结构就会变成「老文件能导入但静默丢字段」。
3. **`id` 必须自带命名空间前缀**（如 `local::`），否则会和 `bvid::cid` 撞键 —— `LyricCacheStore.fileNameOf` 和最近播放去重都靠 id 唯一。

### 5.2 改动面（约 8 项）

| # | 改动 | 位置 | 复用度 |
|---|---|---|---|
| 1 | 文件选择器 | 新建 `pages/LibraryImportPage.ets`，用 `picker.DocumentViewPicker.select()`（SDK `@ohos.file.picker.d.ts:679`，返回 `Array<string>` 的 uri） | 新代码；`PublicDownloadsSaver` 已有 picker 用法可参照 |
| 2 | 解析 + 校验 | 新建 `service/LibraryImporter.ts` | 新代码 |
| 3 | 音频拷进沙箱 | `${filesDir}/local/` | 复用 `fs` 写法（`LyricCacheStore` 有模板） |
| 4 | 写 `localFilePath` | `Track.localFilePath`（已存在） | **零改动** |
| 5 | 播放 | `MusicPlayer` 既有分流（`:2275`） | **零改动** |
| 6 | 歌词 | 解析 LRC → 写 `LyricCacheStore` | 复用解析器 |
| 7 | 封面 | 新建本地图加载（`file://` + 沙箱路径） | **真新代码，注意验证** |
| 8 | 首页改本地视图 | `HomePage.ets` 两套数据源分支 | 改动大，建议一期不做，先只做「导入到歌单」 |

**第 5 项是关键：播放内核一行不用改。** 这是这个方案最便宜的部分。

### 5.3 明确不做（一期）

- 不做「JSON 回写」：用户改动只落本地，json 视为只读输入
- 不做「增量合并」：重复导入 = 整份替换，先提示用户
- 不做「首页本地视图」：一期只做「导入成一个歌单」，首页仍走在线
- 不做「分 P / 合集自动展开」：json 里有什么就是什么

## 6. 禁止项（做的时候不能碰）

1. **不要用 `file://` 给 AVPlayer** —— 本地音频必须走 `createMediaSourceWithFd`（`MusicPlayer.ts:1795` 注释已说明原因），拼 `file://` 是错的
2. **不要把 json 内容塞进 Preferences** —— 8192 字节上限，几百首必然截断，且截断是静默的
3. **不要用绝对路径存音频位置** —— 沙箱路径含 uuid，换机会全废
4. **不要给导入的 Track 编 `bvid`** —— 伪造 bvid 会让「去 B 站看」「换源重试」「收藏」这些逻辑走进错误的网络请求，报错比空着更难查
5. **不要复用 `FavSyncManager` 的镜像标记** —— `sourceKind === 'fav'` 的镜像会被同步逻辑当成「上游数据」参与删除门控，导入曲目混进去有被批量删除的风险
6. **不要在 `slimTrack` 里丢掉 `localFilePath`** —— 丢了就变成「记录还在但播不了」，且重启后才发现
7. **不要做「导入时自动联网补元数据」** —— 一导入就发几百个请求，必然吃风控；这恰恰是用户想避开的
8. **不要在两份来源同时写同一个 `playlistId`** —— 与 `LibraryStore` 的 `STORE_LIBRARY_REV` 冲突，UI 会不刷新

## 7. 验收清单（真机）

- [ ] 导入 3 首的 json（含相对路径音频）→ 歌单出现 3 首，封面正常显示
- [ ] 断网 → 点播放 → 能出声（这是「离线可用」的唯一判据）
- [ ] 杀掉进程重启 → 歌单还在、还能播（验证 `localFilePath` 落盘）
- [ ] 导入后马上导入同一份 → 有覆盖提示，不产生重复条目
- [ ] 导入一个音频文件缺失的 json → 逐条报错而不是整份失败
- [ ] 导入一个 `schemaVersion: 99` 的 json → 明确拒绝并提示版本不支持
- [ ] 一首带 LRC 的曲目 → 歌词正常滚动
- [ ] 已下载的曲目和导入的曲目混在一个歌单 → 都能播

## 8. 三档最终对比

| 维度 | 只改输入框（L1 网关） | JSON 数据源 | L2 通用协议 |
|---|---|---|---|
| 用户操作 | 填一个地址 | 选一个文件 | 填地址 + 定协议 |
| 工期 | 1~2 天 | **2~3 周** | 2~4 周 |
| 功能完整度 | **100%** | ~45%（5 保留 / 3 降级 / 5 不可用） | ~75% |
| 解决风控 | ✅ 换出口 IP | ✅ 根本不联网 | ✅ 不联网 |
| 数据时效 | 实时 | **永久冻结** | 实时 |
| 内容发现 | 推荐/搜索/排行全在 | **基本消失** | 搜索在，推荐弱 |
| 播放内核改动 | 无 | **无**（得意于此） | 需改（多源分发） |
| 主要风险 | 网关稳定性 | 用户得自己备好音频文件 | 协议设计不当 |

**结论：JSON 数据源是「另一种产品」，不是「另一种配置」。**

如果目标是「让 app 不依赖官方 API 也能跑完整功能」，JSON 做不到 —— 它只能做「不依赖官方 API 的本地播放器」。真正的完整性只有 L1（换出口）或 L2（换协议）能给。

## 9. 可直接粘贴的 prompt（若选择「JSON 作为导出格式」这个低风险版本）

```

1. 设置页「数据」分组新增一行「导出歌单」。

【JSON 结构】
{
  "schemaVersion": 1,
  "exportedAt": <unix 秒>,

- 不要动 LibraryStore 的存储格式。

```
