# 歌单一级页 · 顶部与布局优化方案

> 对象：歌单 tab 的一级列表页（不是 `PlaylistDetail`）。
> 涉及文件：`pages/PlaylistsPage.ets`（1689 行）、`components/PlaylistsTabBar.ets`（139 行）、
> `pages/Index.ets` 的 `tabTitleRow()`（1440–1459）。
> 本文所有结论都对着源码核过，行号可直接跳转。

---

## 0. 先划清边界

| | 歌单一级页 | 歌单详情页 |
|---|---|---|
| 文件 | `pages/PlaylistsPage.ets` | `pages/PlaylistDetail.ets` |
| 顶部 | 根栏 `tabTitleRow` + `PlTitleActions` | 页内自绘 Hero + 操作行 |
| 已有方案 | **本文** | 《歌单页布局优化-方案.md》（上一轮） |

两者共用「顶部拥挤」的病因，但表现不同：详情页是**头部长、钉死不收**；一级页是**标题行被操作按钮占满、列表第一屏被工具行吃掉**。

## 1. 现状逐区实测

### 1.1 顶部三段

```
┌─ 根栏 titleBar（Index.tabTitleRow，高 56 + safeTop）──────────┐
│  歌单                       [定位] [选择] [新建]              │  ← 标题 20fp Bold
├──────────────────────────────────────────────────────────────┤
│  列表首项：空白占位 ListItem，高 = safeTop + 56  ← 只为让位    │
├──────────────────────────────────────────────────────────────┤
│  [📥] 下载                                    3 个任务 · 1 个下载中 │  ← 84vp 恒排第一
│  [封面] 夜航星 2026 精选集                     ⋮              │  ← 84vp
│         32 首                                                 │
│  [封面] 某UP主投稿                             ⋮              │  ← 84vp
│         386 个投稿                                            │
└──────────────────────────────────────────────────────────────┘
```

- **标题行**：`Text('歌单')` 20fp Bold + `PlTitleActions`（`Index.ets:1442-1451`）。三页签（歌单/拾音/设置）共用这一行，只有歌单页塞了动作组。
- **占位**：`List` 视口铺满全屏，首个 `ListItem` 高度 `barTotalHeight()` = `safeTop + 56`（`PlaylistsPage.ets:1423`）。
- **下载入口**：`DownloadsEntryRow` 是独立 `ListItem`，恒排列表第一（`:1433-1436`），组件本体 `:1579-1690`。

### 1.2 行规格

| 元素 | 值 | 出处 |
|---|---|---|
| 行高 | **84**（封面 64 + 上下 padding 10×2） | `:1231` |
| 封面 | 64×64，圆角 8，按 2x 请求 128 缩略图 | `:1180-1186` |
| 歌单名 | 16fp / `lineHeight(21)` / **maxLines(2)** | `:1191-1196` |
| 副行 | 13fp / `lineHeight(17)` /「N 首」或「N 个投稿」 | `:1200-1204`、`:440-447` |
| ⋮ | 44×44 命中区（视觉 20） | `:1212-1228` |
| 左右 padding | left 16 / right 4 | `:1231` |
| 多选勾选槽 | width 0 ↔ 44，`translate` 位移进出 | `:1157-1175` |

那个 64 封面是**刻意**的硬预算：名称两行 21×2 + 间距 4 + 副行 17 = **63 ≤ 64**，所以文字区永远塞得进封面高度、封面不会浮空（注释 `:1177-1179`、`:1197-1198`）。这个设计是对的，下面挑战它的部分会说清代价。

### 1.3 首屏预算（360×780，safeTop 32，底部页签区 72）

```
可视区 = 780 − 72 − 88(占位) = 620vp
现状   620 − 84(下载行) = 536 → 536 / 84 = 6.38 → 6 个歌单
```

**一屏只能看到 6 个歌单，其中第一行还是「下载」。**

## 2. 六个诊断（每条都有证据）

### D1 · 下载入口占了首屏 1/7，且与歌单同权重

`DownloadsEntryRow` 的视觉与 `PlaylistRow` **几乎一模一样**：64 图标位（浅粉底 + 图标）+ 16fp 标题「下载」+ 13fp 副行 + 同样的 0.9 按压缩放（`:1642-1668`）。唯一的区别是副行文字。

结果：
- 首屏 620vp 里它吃掉 84vp（13.5%），等于**每天少看一个歌单**；
- 「工具」和「内容」在视觉上无法区分，削弱「这里是歌单」的心智；
- 它还会随列表滚走——**滚下去就再也看不见下载进度**，说它「常驻」其实只是「排第一」。

### D2 · 行高被「最坏情况」钉死

行高 84 是为了容纳「名称 2 行(42) + 4 + 副行(17) = 63」这个**极端情况**。但实际歌单名绝大多数一行就够：16fp 在 228vp 可用宽度里能放 **14 个汉字**。

平均内容高只有 `21 + 4 + 17 = 42`，比封面 64 少 22vp。为了让 1% 的长名不撑高行，100% 的行都按 84 走。

> 这不是「写错了」，是「用一个代价换版面整齐」。我要做的是把代价量化出来，让取舍可判断——见 §5 高度账。

### D3 · 三种来源在列表里完全分不出来

`Playlist.sourceKind` 有 `'up'` / `'fav'` / `''` 三值（`MusicModels.ts`），语义注释写得很清楚。但在歌单一级页：

```
grep -n "sourceKind" pages/PlaylistsPage.ets   →   0 处
```

也就是说：**收藏夹镜像歌单、UP 订阅歌单、自己建的歌单，在列表里长得一模一样**，只有 UP 订阅的副行文字变成「N 个投稿」（`:440-447`）。收藏夹镜像连这个都没有，副行还是「N 首」，跟自建完全一致。

而 `updatedAt` 字段每次增删改都在写（`LibraryStore.ts` 20+ 处），一级页 **0 处展示**。

### D4 · 顶栏只做「操作」，不做「信息」；「定位」大部分时间是死的

常规态三个按钮（`PlaylistsTabBar.ets:100-137`）都没写 `padding`，走 `Button` 默认 16 → 每个「两字按钮」= 26 + 32 = **58vp**：

```
58 + 8 + 58 + 8 + 58 = 190vp   ← 占标题行可用宽 328 的 58%
```

三个里：
- `新建` 高频，该留；
- `选择` 低频（还要 ≥2 个歌单才出现），该收；
- **`定位`** —— `locateCurrentPlaying()`（`:354-384`）在「没在播曲目」和「在播曲目不在任何歌单」两种情况下都只 toast 就返回。而这两个状态恰恰是大多数时候。**一个 58vp 的按钮，点下去 80% 概率只弹一句提示**，还占着标题行最左的黄金位。

同时，标题行**零信息**：不显示歌单总数、不显示总曲目数、没有任何筛选。首页有问候语、拾音页有周期切换，歌单页只有两个字。

### D5 · 多选态 4 个文字按钮在 360vp 上已经贴边

多选态（`PlaylistsTabBar.ets:48-99`）4 个按钮都显式 `padding({left:10,right:10})`、`fontSize(13)`、`space: 8`：

| 按钮 | 字宽(13fp) | +padding 20 | 小计 |
|---|---|---|---|
| 完成 | 26 | 20 | 46 |
| 全选 / **取消全选** | 26 / **52** | 20 | 46 / **72** |
| 删除选中 | 52 | 20 | 72 |
| 合并选中 | 52 | 20 | 72 |
| space ×3 | — | — | 24 |
| **合计（最坏）** | | | **286** |

加「歌单」标题 40 + 页面 padding 32 = **358vp**，屏幕 360 → **只剩 2vp**。

HarmonyOS 系统字体最大可放大到 1.45 倍，12/13fp 文字宽度同步放大 → **必然溢出**（标题被挤成省略号，或按钮重叠）。

而且多选态**不显示选中数量**——注释明确写「不带计数」（`:51`），`selectedIds.length` 明明是现成的。选了 20 个歌单，得靠数勾选圈。

### D6 · 「一键排全部」从来没存在过（真 bug）

`model/MusicModels.ts:373` 的注释：

> 由歌单页顶栏「一键排全部」置起，用户可再对单个歌单取消（见 LibraryStore）。

但：

```
grep "titleSorted" 全仓 → 只有读，没有写
grep "titleSorted: true" → 0 处
grep "排全部" → 只有注释
```

而排序基础设施**全都写好了**：
- `sortTracksByTitle()`（`LibraryStore.ts:952`）——`localeCompare` 走 ICU 中文按拼音序，还专门用下标兜底排序稳定性；
- `isTitleSorted()`（`:968`）——被追加曲目（`:1169`、`:1237`）和合并（`:1670-1671`）两处调用。

**结论**：一个完整实现好的「按中文拼音排序 + 此后新歌自动按名插入」能力，**卡在最后一个入口没做**。`titleSorted` 永远是 `false`，所有 `isTitleSorted()` 分支都是死代码。

这是本轮最值得先修的一条——它不需要新设计，只需要一个菜单项。

### D7 · 空态只教「新建」，而导入能力埋在两三级深

空态文案（`:1365-1371`）：

```
还没有歌单
点击右上角"新建"创建
```

但现成能力有：
- 网易云 / QQ 音乐歌单导入：`PlaylistImport`，入口在 **设置 → 歌单备份 → 从网易云·QQ 音乐导入**（`PlaylistBackupPage.ets:314`）；
- B 站收藏夹双向同步：`FavSync`。

新用户真正的诉求是「把我已有的歌单搬进来」，而不是「从零手建 30 首」。空态把最有价值的两个入口藏起来了。

### D8 · 网格模式三处不一致

| | 长条（`PlaylistRow`） | 网格（`PlaylistCard`） |
|---|---|---|
| 副行字号 | 13fp | **12fp**（`:1327`）—— 违反字阶六档（24/20/18/16/13/11） |
| 拖动排序 | 支持（`:1522`） | **不支持**（配对后错乱，`:1439`） |
| 下载入口 | 整行长条 | 仍是整行长条，混在网格里 |

网格模式下用户想排序，只能先切回长条模式排完再切回来。

## 3. 方案总览

分三层，可以只做其中一层：

| 层 | 内容 | 收益 | 风险 |
|---|---|---|---|
| **L1 信息层** | 标题副行、副行三段式、列表尾巴、网格字号修正 | 一眼读懂「有几个、谁是自己的、多久没动」 | 零 |
| **L2 结构层（推荐）** | 下载入口移出列表 + 标题行重构 + 行高 84→76 | **首屏 6 → 8 个歌单（+33%）** | 中（要动 build 结构） |
| **L3 功能层** | `⋮` 菜单（补「按名称排序全部」/ 导入 / 同步）、多选计数、空态三入口 | 补齐缺口，修 D6 真 bug | 低 |

## 4. L1 · 信息层

### 4.1 标题行加副行

```
现在                          改后
歌单                         歌单
                             12 个歌单 · 386 首
```

| 元素 | 规格 |
|---|---|
| 主标题 | 20fp Bold，不变 |
| 副行 | 11fp / `text_tertiary` / lineHeight 15 / `margin-top: 1` |
| 整块高度 | 26 + 15 = 41 ≤ 56 ✔ 不用改 `NAV_TITLE_BAR_HEIGHT` |
| 文案 | `${count} 个歌单 · ${totalTracks} 首`；筛选态显示 `${筛选名} · ${count} 个` |

派生（在 `refresh()` 里算一次，不放进 build）：

```ts
private totalTrackCount(): number {
  let sum: number = 0;
  for (let i: number = 0; i < this.playlists.length; i++) {
    sum += this.playlists[i].tracks.length;
  }
  return sum;
}
```

> ⚠️ `Index.ets:1440` 的 `tabTitleRow()` 是**三页签共用**的。加副行必须 `if (this.activeTab === TAB_PLAYLISTS)` 分支，否则拾音/设置页会突然多出一行空白——它们的标题行高度虽不变，但垂直居中会偏移。

### 4.2 副行三段式

```
现在：  32 首
改后：  收藏夹 · 32 首 · 3 天前
        └来源┘  └数量┘  └更新┘
```

| 段 | 来源 | 颜色 |
|---|---|---|
| 来源 | `sourceKind`：`''`→不显示 / `'fav'`→收藏夹 / `'up'`→UP 订阅 | `text_tertiary` |
| 数量 | 现有 `subLineOf(p)` | `text_secondary` |
| 更新时间 | `updatedAt` 相对时间：`今天` / `3 天前` / `2 周前` / `3 个月前` / `2025-06` | `text_tertiary` |

**自建歌单不显示来源段**（`''` 就是「自己的」，没必要写「自建」），只在数量和更新时间前留白——这样默认页更干净，而收藏夹/订阅一眼可辨。

改 `subLineOf` 的返回结构（`PlaylistsPage.ets:440`），返回三个字段而不是一个字符串：

```ts
// 新增：相对时间，超过 1 年直接显示年月
private relTime(iso: string): string { /* 今天/N 天前/N 周前/N 个月前/YYYY-MM */ }

private subPartsOf(p: Playlist): string[] {
  const parts: string[] = [];
  if (p.sourceKind === 'fav') { parts.push('收藏夹'); }
  else if (LibraryStore.isUpSubscription(p)) { parts.push('UP 订阅'); }
  parts.push(this.subLineOf(p));           // 沿用现有口径
  const rel: string = this.relTime(p.updatedAt);
  if (rel.length > 0) { parts.push(rel); }
  return parts;
}
```

渲染用单个 `Text` 拼 `join(' · ')`，**不要拆成三个 Text**——三个 Text 要各自处理省略、行高会打架，而且次级色差用 `Span` 更省事：

```ts
Text() {
  Span(parts[0]).fontColor($r('app.color.text_secondary'))
  for (let i = 1; i < parts.length; i++) {
    Span(' · ' + parts[i]).fontColor($r('app.color.text_tertiary'))
  }
}
.fontSize(13).lineHeight(17).maxLines(1)
```

> 为什么不放徽章？徽章（高 18、圆角 9、左右 padding 6）在**详情页**合适——那里头部只有 1 个对象。一级列表一屏 8 个，8 个彩色徽章会变成噪音，而且每个徽章多 6–10vp 宽，会把副行挤成省略号。

### 4.3 列表尾巴

`List` 末尾加一个不可点的统计行：

```
共 12 个歌单 · 386 首
```

11fp / `text_tertiary` / 居中 / 上下 padding 20。给列表一个「到底了」的确认，同时顺手把 §4.1 的统计数字复述一遍（用户滚到底时标题行已经滚上去看不见了）。

### 4.4 网格副行 12 → 13

`PlaylistsPage.ets:1327` 的 `fontSize(12)` 改 13。同一信息在长条模式是 13、网格模式是 12，属于同页内不一致；且 12 不在字阶六档里。

## 5. L2 · 结构层（推荐）

### 5.1 下载入口移出列表 → 标题行图标

把 `DownloadsEntryRow`（84vp）从「列表第一」改成**标题行右侧的图标按钮 + 数字角标**。

```
┌─ 标题行 56 ──────────────────────────────────────────┐
│  歌单                              [↓②] [+] [⋮]      │
│  12 个歌单 · 386 首                                   │
└──────────────────────────────────────────────────────┘
│  [封面] 夜航星 2026 精选集          ⋮                │  ← 列表从标题栏底部直接开始
```

| 元素 | 规格 | 说明 |
|---|---|---|
| 下载图标 | 36×36 圆角 10，`themeSurface` 底 + `themePrimary` 图标 | 有下载任务时右上角 8×8 数字角标 |
| `+` 新建 | 36×36，品牌色**实底** + `themeOn` 图标 | 唯一主 CTA，实底强调；其余为浅底 |
| `⋮` 更多 | 36×36，`themeSurface` 浅底 | 见 §6 |
| 图标间距 | 8 | |
| 右侧总宽 | 36×3 + 8×2 = **124** | 标题区剩 328 − 124 = 204，放「12 个歌单 · 386 首」（11fp ≈ 118）绰绰有余 |

**为什么下载能上标题行，而「选择」不能**：下载有**实时状态**（任务数、进行中数量），状态需要常驻可见；而下载页是二级页，入口需要「随时能进」。现在的实现（排列表第一）恰好两头不占：滚两屏就看不见进度，也不常驻。

角标逻辑复用 `DownloadsEntryRow.onTasks()` 的分级（`:1592-1631`），只取「进行中 + 待开始」的数量：

```ts
// 从 tasks 快照算一个数，@StorageLink 已经在本页可用
private activeDownloadCount(): number {
  let n: number = 0;
  for (let i: number = 0; i < this.downloadTasks.length; i++) {
    const s: DownloadStatus = this.downloadTasks[i].status;
    if (s === DownloadStatus.PENDING || s === DownloadStatus.DOWNLOADING) { n++; }
  }
  return n;
}
```

> 失败任务用**红色小圆点**而不是数字（失败比进行中更需要被看见），规则与下载页 `DownloadsTabBar` 保持同一套。

### 5.2 行高 84 → 76

| 项 | 现在 | 改后 |
|---|---|---|
| 封面 | 64×64 | **56×56** |
| 上下 padding | 10 | 10（不变） |
| 行高 | 84 | **76** |
| 歌单名 | 16fp / 2 行 | 16fp / **1 行**（超长省略） |
| 副行 | 13fp / 17 | 13fp / 17（不变） |
| 内容高 | 21×2+4+17 = 63 | 21+4+17 = **42 ≤ 56** ✔ |

**代价说清楚**：取消名称第 2 行。超过 14 个汉字的歌单名会被省略号截断，点进详情页才能看全。

**为什么值得**：
- 每行省 8vp，一屏 620vp 直接多出 8vp × 7 ≈ 整 1 行的空间；
- 16fp 一行在 228vp 里放 14 个汉字，覆盖绝大多数真实歌单名（「夜航星 2026 精选集」= 12 字，「某UP主投稿」= 6 字）；
- 现在允许 2 行的那些行，**绝大多数时候第二行是空的**，白占 21vp。

> 如果不想放弃 2 行名称，可以只做 §5.1，收益是 +1 行（6→7）；两个都做才是 +2 行（6→8）。§6 给了 A/B 两个方案对照。

改法（`:1180-1205`）：

```ts
CoverImage({
  url: toThumbUrl(p.coverUrl, 128),   // 112 也行，保留 128 有余量
  imgWidth: 56,
  imgHeight: 56,
  imgRadius: 8,
  altText: p.name
})
...
Text(p.name)
  .maxLines(1)                        // ← 2 改 1
  .lineHeight(21)
```

### 5.3 高度账（360×780，safeTop 32，底部页签 72）

```
可视区 = 780 − 72 − 88(占位) = 620vp

① 现状            620 − 84(下载行) = 536  → 536/84 = 6.38 → 6 个（第 7 个露 32vp）
② 只做 5.1        620              = 620  → 620/84 = 7.38 → 7 个（+1）
③ 5.1 + 5.2       620              = 620  → 620/76 = 8.15 → 8 个（+2，+33%）
```

表格化：

| 方案 | 单行高 | 首屏歌单数 | 相对现状 | 取舍 |
|---|---|---|---|---|
| 现状 | 84 | 6 | — | 下载占第一行 |
| A（只移下载） | 84 | **7** | +1（+17%） | 无取舍，纯结构 |
| **B（A + 行高）** | 76 | **8** | **+2（+33%）** | 歌单名只 1 行 |
| 若再压标题行占位 | — | 不建议 | — | `safeTop + 56` 是真实栏高，压了会遮挡 |

## 6. L3 · 功能层

### 6.1 `⋮` 菜单（把散落的功能收一处）

现有能力盘点 + 缺失项，全部收进一个菜单：

```
┌──────────────────────────────┐
│  选择歌单                     │  ← 原标题行「选择」（≥2 个才可用）
│  定位当前播放          灰/可用 │  ← 原「定位」，无在播时置灰而不是 toast
│  ────────────────────────    │
│  按名称排序全部曲目            │  ← 🆕 补 D6，激活 titleSorted
│  按最近更新排序               │  ← 🆕 只改展示顺序（本地数组 sort）
│  ────────────────────────    │
│  从网易云 / QQ 音乐导入        │  ← 🆕 从设置页提上来
│  B 站收藏夹同步               │  ← 🆕 从设置页提上来
└──────────────────────────────┘
```

**「按名称排序全部曲目」的实现**（D6 的修法，代码量很小）：

```ts
// service/LibraryStore.ts 新增导出
export function sortAllPlaylistsByTitle(): void {
  const list: Playlist[] = getPlaylists();
  const next: Playlist[] = [];
  for (let i: number = 0; i < list.length; i++) {
    const sorted: Track[] = sortTracksByTitle(list[i].tracks);
    next.push(Object.assign({}, list[i], {
      tracks: sorted,
      titleSorted: true,                       // ← 唯一缺的那一行
      updatedAt: new Date().toISOString()
    }));
  }
  persistPlaylists(next);
}
```

配套加一个「取消按名称排序」（把 `titleSorted` 置回 false，不改现有顺序）——因为这是个「今后新增也按名插入」的持续规则，必须能关。

> 注意 `sortAllPlaylistsByTitle` 会重写全部曲目分片，**大库（几千首）要走预热式的分片让出**，参考 `prewarmPlaylists` 的做法（`PlaylistsPage.ets:295-302` 有先例）。当前实现是同步遍历，歌单很多时可能触发 `THREAD_BLOCK_6S`。

### 6.4 来源筛选（可选，默认收起）

`sourceKind` 有三种值，但**不做常驻 chips**——只在来源种类 ≥2 时，才在副行显示当前筛选并支持点击切换：

```
全部：  12 个歌单 · 386 首

```

点击副行弹 `bindMenu`（4 项 + 计数）。理由：歌单少（<6）时 chips 纯属占地方，而筛选的真正用户（有收藏夹镜像 + 订阅 + 自建各几个）一眼就能从副行文字看出自己在什么视图。

> 这一项我刻意压到最后：它需要新的派生状态（当前筛选值 + 过滤后的列表），而收益依赖用户真的混用三种来源。先做 6.1/6.2/6.3 更实在。

### 6.5 网格模式两处补齐

- 副行 12 → 13（§4.4）；
- 排序：网格不注册 `onMove` 是既定取舍（配对后整行错乱）。替代给 `⋮` 菜单加一项 **「移到最前」**——覆盖「这个歌单我要常用」这个 80% 的排序诉求，成本一行 `LibraryStore.movePlaylist(id, 0)`。
