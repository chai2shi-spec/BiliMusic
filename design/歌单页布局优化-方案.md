# 歌单详情 · 顶部与页面布局优化

> 交付物：`歌单页布局优化-交互原型.html`（4 屏 × 深浅）、`-预览.png`。
> **本轮不改 App 代码**，只出设计资产与可落地规格。
> 代码依据：`pages/PlaylistDetail.ets`（`PlaylistHeader()` `:1471`、`build()` `:1876`、`playlistHeaderAreaNarrow` `:1785`）。
> 上一轮《头部操作区重构》已解决「操作行宽度溢出 / 搜索框被压成 0」，**本轮不再重复操作行**，
> 聚焦它没覆盖的：**顶部信息层级**与**页面滚动布局**。

---

## 0. 结论

顶部的问题不是「不好看」，是两件事叠在一起：

1. **头部常驻 178vp，滚到底也不让位** —— 首屏能看 7 行曲目，滚 20 行后**还是 7 行**，
   因为头部钉在 `titleBar.bottomBuilder` 上不动。列表空间被一个不随浏览退让的区块长期占着。
2. **信息层级是平的** —— 封面 96 / 标题 28 / 元信息 13 / 简介 11 四层全左对齐堆着，
   而且 `metaText` 把「N 首 · 创建于 X」或「N 首 · 同步自 XXX」**全压在一行 13fp 里**，
   **没有音乐 App 歌单头部标配的「总时长」**（32 首究竟是一个半小时还是三小时，看不到）。

按性价比排，值得做的顺序：

| 顺序 | 改动 | 风险 | 收益 |
|---|---|---|---|
| 1 | 元信息补「总时长」+ 来源徽章（方案 A） | 零（纯文案/加字段） | 一眼读懂这个歌单是什么、多长 |
| 2 | 简介折叠 + 元信息重排（方案 A） | 零 | 高度净省约 17vp；价值主要在「来源与时长一眼读懂」 |
| 3 | 搜索态收起封面/标题（方案 B） | 低 | 搜索时列表上移，多 2 行结果 |
| 4 | 滚动收展 + 标题吸顶（方案 C） | **高**（改 titleBar 高度，需真机验证） | 滚动后多 2 行，且随时知道在哪 |

> 一句话：**A 是稳赚的信息层改造，B 是状态层的顺手优化，C 才是真正的空间重构但必须谨慎。**

## 1. 现状拆解（Frame / Auto Layout 视角）

把头部当成一个 Figma Frame 拆开，Auto Layout 是 Vertical：

```
Frame「PlaylistHeader」  W=full-40  padding 20/20/4/8  → 实测高 156–190
├─ HStack「CoverRow」      H = max(96, 右侧文本列高)   ← 不定高，这是隐患
│   ├─ Cover  96×96  r12
│   └─ VStack「TextCol」   H 可达 129（标题 2 行 + meta + desc 2 行）
│       ├─ Title  28/Bold  maxLines 2
│       ├─ Meta   13/Sec   maxLines 1   ← 数量+来源+时间全塞这一行
│       └─ Desc   11/Ter   maxLines 2   ← 默认就展开两行
├─ Stack「ActionRow」  H=36  margin-top 12   ← 上一轮已重构（CTA + 🔍 + ⋯）
└─ Text「匹配 N 首」   11/Ter  仅搜索态
```

`headerAreaHeight` 由内层 `onAreaChange` 实测（`:1741`），`titleBar` 用实测值做
`bottomBuilder` 高度（`:2169`），估算兜底 `PLAYLIST_HEADER_ESTIMATE_HEIGHT = 178`（`:119`）。

**首屏空间账**（6 寸屏可用高约 780vp）：

```
状态栏 safeTop        ≈ 38
标题栏                56
头部区（实测均值）    178
─────────────────────────────
总让位                ≈ 272
列表可视              ≈ 508  → TrackItem 约 64vp/行 → 约 7.9 行
```

滚到第 50 首时，头部纹丝不动，可视区**仍是这 508vp** —— 这是「顶部布局」最实的问题。

## 2. 诊断：五个结构性问题

### 2.1 头部常驻，滚动不让位 ★★

`bottomBuilder` 的高度是显式常量（`headerAreaHeight`），**与滚动偏移无关**。
对比主流：网易云 / QQ 音乐 / Spotify 的歌单头都是「大封面 → 滚动后缩进标题栏」。
本页等于把一个 178vp 的区块永久贴在屏幕上方。

### 2.2 信息层级平，缺「类型标识」与「总时长」★★

`buildMetaText()`（`:723`）产出的是：

```
32 首 · 创建于 2026-09-01          ← 自建
320 首 · 同步自 某UP主             ← 收藏夹镜像
48 首 · 订阅自 某UP主              ← UP 订阅
```

三个问题：
- **来源藏在句子里**：用户要读完一整行才知道「这是我自建的，还是从 B 站同步来的」。
  而来源决定了这页能不能排序、能不能删（`canReorder` 闸门就依赖 `sourceKind`）。
- **没有总时长**：`Track.duration`（秒）现成，`Σ duration` 一行代码就能算，但没做。
- **长名称被截**：`maxLines(1)`，UP 名一长就省略号，反而丢了最关键的信息。

### 2.3 简介默认展开两行 ★

`descText`（歌单 `description`）`maxLines(2)`，11fp 两行约 38vp 常驻。
B 站收藏夹简介常是长段介绍，多数用户扫一眼就走。默认两行 = 用 38vp 换一次「扫一眼」。

### 2.4 搜索 / 多选态头部不让位 ★

搜索态只把操作行换成输入框，**封面、标题、简介照旧占着 178vp**，
用户正在找歌，却比平时看到更少的候选。多选态同理。

### 2.5 封面 96 与文字列高度不对齐

`Row.alignItems(Top)`，右侧文本列最坏 129vp > 封面 96vp → Row 高被撑到 129，
封面下方空出 33vp，视觉上「封面浮在半空」。也让 `headerAreaHeight` 在 156–190 浮动，
列表首项位置随简介行数跳。

## 3. 方案 A · 信息层重构（P0，零布局风险）

只动「显示什么」，不动骨架，不改滚动逻辑。四件事：

### 3.1 元信息 = 「徽章 + 主行」一行，来源详情收进徽章

```
现在：  32 首 · 同步自 某UP主                    ← 一行，来源混在句子里
改后：  [收藏夹] 32 首 · 2 小时 18 分             ← 一行，来源成为独立视觉
```

| 元素 | 内容 | 规格 |
|---|---|---|
| 来源徽章 | 自建 / 收藏夹 / UP 订阅 | 11fp/Medium，高 18，圆角 9，padding 0/6；**可点** |
| 主行 | `N 首 · X 小时 Y 分` | 13fp / text_secondary |
| 来源详情 | 同步自谁 / 多久前 / 单向双向 | **不进文本行**，点徽章弹 11fp toast 或小 sheet |

> 为什么「同步自 XXX · 3 天前」不单独起一行：单起一行会让头部**净增高 19vp**，
> 正好把简介折叠省下的空间吃回去（见 §3.5 的高度账）。来源是「属性」，
> 属性适合「点开看」，不适合「常驻占一行」。

**徽章配色**（不抢品牌粉，品牌色留给「播放全部」）：
- 自建：`bg_divider` 底 + `text_secondary` 字
- 收藏夹：`#5B7FA8` 15% 底 + `#5B7FA8` 字（蓝灰，示意「来自 B 站」）
- UP 订阅：`themePrimary` 12% 底 + `themeDeep` 字（弱粉，与品牌关联但不实底）

> 为什么用徽章而不是继续拼字符串：**来源是「属性」，不是「句子」**。属性该用视觉编码
> （色块 + 短词）让人在 0.2 秒内识别；句子适合放「3 天前更新」这种需要读的补充。

### 3.2 总时长

`Σ track.duration`（秒，跳过 `duration=0` 的直播条目），格式：

```
≥ 1h：`2 小时 18 分`
< 1h：`46 分钟`
全 0：整段省略（不显示「0 分钟」）
```

放在主行，与「N 首」并列 —— 这是音乐 App 的肌肉记忆位置。

### 3.3 简介默认 1 行 + 展开

```
默认：  简介文字最多一行…                        ⌄
展开：  简介文字（最多 4 行）                     ⌃
```

- 11fp / text_tertiary，默认 `maxLines(1)`；
- 行尾一个 12vp 的展开箭头（`chevron_down` / `chevron_up`），命中区 44；
- 只有「文本实际超过一行」时才显示箭头（用 `Text.onAreaChange` 或测量行数，避免短简介也挂个箭头）；
- 展开状态**不持久化**（离开页面重置），避免用户无意间把头部撑高后忘了。

省 1 行简介（约 16vp）。完整的头部高度账见 §3.5 —— 别指望单独靠它大幅腾空间。

### 3.4 封面列固定与文字列对齐

```
Cover 96 固定；TextCol 加 .height(96) + .justifyContent(SpaceBetween)
```

让 TextCol 撑满 96（标题顶、meta/desc 底），Row 高恒 96 —— 封面不再浮空，
`headerAreaHeight` 也稳定在 156–172 附近（不再 156–190 随简介行数跳）。

> 如果标题 2 行 + meta + desc 超过 96，说明信息确实多，这时让它溢出到 96 以外是合理的
> （`SpaceBetween` 只在内容 ≤96 时生效）；关键是**短标题的歌单不再被 desc 撑高**。

### 3.5 高度账（重要，别高估方案 A）

方案 A 如果按「徽章一行 + 次行 + 折叠简介」硬排，右侧文本列反而**变长**：

| 组成 | 现状 | 若加次行 | 精简版（3.1 采纳） |
|---|---|---|---|
| 标题 2 行 | 67 | 67 | 67 |
| 元信息 | 24（1 行） | 24 | 24（徽章+主行同行） |
| 次行（来源补充） | 0 | 19 | **0（收进徽章）** |
| 简介 | 38（2 行） | 21（1 行） | 21（1 行） |
| 右侧列合计 | **129** | **131** | **112** |
| headerAreaHeight | ~189 | ~191 | **~172** |

所以：**加次行 = 白干（129→131）**；精简版才是真省 ~17vp（189→172）。
17vp 约等于 **1/4 行**，视觉上几乎看不出来 —— **方案 A 的价值在信息层，不在空间**。

真正的空间收益在 B（搜索态省 ~130vp）和 C（滚动后省 ~126vp），见 §4、§5。

> 如果一定要 A 也多省点，只有两条路：
> - 标题限 1 行（67→34，省 33）—— 长歌单名读不全，不推荐；
> - 封面 96 缩到 72，标题列变宽少换行 —— 省 24，但封面显得小气，也不推荐。
> 结论：**别为了省空间去削 A 的信息，A 就该"信息优先"。**

## 4. 方案 B · 状态感知布局（P1，低风险）

### 4.1 搜索态收起封面与标题

点 🔍 进入搜索态时：

```
┌──────────────────────────────────┐
│ [🔍 夜|              ×]   取消   │   ← 操作行原位切成搜索框（上一轮已做）
│ 匹配 3 首                        │
├──────────────────────────────────┤
│ 曲目结果直接从标题栏下方开始       │
```

封面 / 标题 / 元信息 / 简介 **整块让位**（`if (!searchMode)` 不挂载，与操作行同一套
「真不挂载」纪律，见上一轮 §6②）。列表因此上移约 130vp，多显示 2 行结果。

> 为什么搜索时可以不显示歌单名：用户刚点开这个歌单就点了搜索，他知道自己在搜什么；
> 而「匹配 3 首」比「歌单名」更能回答「我现在在看什么」。

### 4.2 多选态只收简介

多选时用户需要知道「在哪个歌单里选」，**标题保留**；但简介无用于多选，收起。
（`if (!selecting)` 包住 desc 即可，省 22–38vp。）

## 5. 方案 C · 滚动收展 + 标题吸顶（P2，高风险）

这是真正的空间重构，但要先接受约束：**`bottomBuilder` 的高度一改，`titleBar` 总高就变，
列表首项占位（`barTotalHeight()`）也跟着变** —— 滚动中连续改会重排抖动。

所以只给**两段式**（不是连续 lerp）：

### 5.1 行为

```
滚动 < 120vp ：头部完整（178vp），标题栏 title = ''（歌单名只在头部大字显示）
滚动 ≥ 120vp ：一次切换 ↓
               headerAreaHeight 178 → 52（只留操作行 + padding）
               封面/标题/meta/desc 整体 opacity 0 + 裁切
               标题栏 title 淡入 = 歌单名
滚动回到 < 120vp：反向切回
```

用 `animateTo(220ms, EaseInOut)` 过渡一次，而不是每帧改高度。

### 5.2 为什么不是连续收展

连续 lerp 会让 `titleBar` 高度每帧变化 → HDS 材质重算 + 列表占位重排 +
滚动位置补偿，快滑时极易「内容跳一下」。两段式只有一次重排，肉眼是「头部收起来」的
自然过渡，抖动不可见。

### 5.3 状态与占位的自洽

只改 `headerAreaHeight` 一个变量：`barTotalHeight() = safeTop + 56 + headerAreaHeight`
（`:169`）会自动跟随，占位 `ListItem` 高度自动变 —— **不要**单独去改占位高度，
否则两处不同步会出现「首项被头部压住」或「首项上方多一条空白」。

### 5.4 退路

如果真机验证仍有抖动（HDS 材质重算跟不上），降级为 **C-lite**：
不比高度，只做「头部内容淡出」+ 标题吸顶，`headerAreaHeight` 保持 178。
收益打折（空间没还回去），但零重排风险。

> ⚠️ 这条与第 3 轮（拾音页）踩过的坑同源：**别让布局回调（`onAreaChange`）去回写
> 驱动自适应的状态变量**。这里必须由**滚动偏移**驱动（`onDidScroll` 里算，
> 已有 `syncTopBlurProgress` 同款入口），而不是 `onAreaChange`。

## 8. 实现约束（都已在本工程踩过）

**① 固定宽度列不写死，文字优先于容器。**
徽章是「短词」，但仍用 `minWidth` 而非 `width`；`metaMain` 允许 `maxLines(1)` 省略，
但**总时长不能被截**（放前面，`N 首` 放后面）。

**② 搜索态用 `if` 不挂载，不用 `HitTestMode.None` / `visibility`。**
（上一轮 §6② 同款结论：透明层子按钮仍响应点击。）

**③ 头部高度只由 `headerAreaHeight` 一个变量驱动。**
`barTotalHeight()` 是它的函数，占位高度自动跟随；**不要**再单独给占位设一个高度。

**④ 滚动驱动自适应，必须走 `onDidScroll` 计算，不能由 `onAreaChange` 回写状态。**
（拾音页 miniBar 的坑：布局回调里回写换自适应 → 真机「展开迷你栏消失」。）

**⑤ 简介折叠状态不持久化。** 每次进页重置为折叠，避免无意撑高头部。

**⑥ 字号只用 24/20/18/16/13/11；徽章 11、次行 11，不出现 12/14/15。**

## 9. 可直接粘贴的 AI 提示词

### 9.1 方案 A（信息层，最小改动，先做这个）

```
在 HarmonyOS-Phone 的 pages/PlaylistDetail.ets 重构歌单头部信息区，
只改「显示什么」，不动操作行、不动滚动逻辑：

1. buildMetaText 改为返回结构 { main, sub, badge }：
   main = `${N 首} · ${总时长}`，总时长 = Σ track.duration（秒）跳过 duration===0，
   格式 ≥1h 用「X 小时 Y 分」、<1h 用「Y 分钟」、全 0 省略时长段。
   detail = 来源详情（自建=创建日期 / 收藏夹=同步自某UP·多久前·单向双向 / 订阅=订阅自某UP），
            仅用于「点徽章时弹出」，**不进文本行**（进文本行会净增高 19vp）。
   badge = 三种来源（自建 / 收藏夹 / UP订阅）。
   这三个字段在 load() 里预计算成 @State（Builder 内不判空、不声明局部变量）。
2. PlaylistHeader 的 CoverRow 右侧列改为：
   标题 28/Bold（不变）→ 一行「[来源徽章] main 13/text_secondary」（徽章与主信息同行，
   **不要**给来源补充单独开一行，那会让净增高 19vp、把简介折叠的收益抵消）
```
