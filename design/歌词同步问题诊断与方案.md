# 歌词同步问题诊断与解决方案

> 2026-10-21 · 只做诊断与方案，未修改任何代码
> 涉及文件：`player/MusicPlayer.ts`、`api/LyricsApi.ts`、`utils/TextUtil.ts`、
> `components/player/LyricsComponent.ets`、`lyric/LrcView.ets`

---

## 一、结论速览

歌词「有时候」不同步不是一个 bug，而是**六个独立缺陷叠加**的结果。按实测影响排序：

| # | 缺陷 | 症状 | 实测影响 | 优先级 |
|---|---|---|---|---|
| 1 | 进度按 **500ms 分桶**推送，歌词直接吃这个值 | 换行慢半拍；密集行整行跳过 | 平均滞后 **171ms**，最坏 **360ms**；行间隔 300ms 时 **12/31 行被完全跳过** | **P0** |
| 2 | `findShowLine` 用 `>=` 做右边界（应为左闭右开） | 换行再多等一个 tick | 起点恰为 500 倍数时，平均滞后从 171→**307ms**，最坏 500ms | **P0** |
| 3 | 歌词缓存 `ok` 状态**永不过期**，匹配错就永久错 | 「就这几首歌永远对不上」 | 一旦匹配到翻唱/Live 版，除非切歌前后「缺时长→有时长」触发一次清理，否则**永久错位** | **P0** |
| 4 | `synced === false`（无时间轴歌词）被当作有时间轴处理 | 歌词卡在最后一行不动 | `plainToLines` 把 `time` 全设 **-1** → 10 行里**只有最后一行能匹配**，其余永不命中 | **P1** |
| 5 | LRC 的「制作人员行」不过滤、`[offset:]` 不应用 | 歌开头 20~30 秒显示"词：周杰伦 / 编曲：…" | 《晴天》开头 **7 行 / 0~29 秒** 全不是歌词 | **P1** |
| 6 | `LrcView` 字号行距硬编码（24/20vp、行距 24），且是 `private` | 大屏歌词偏小、行距偏紧 | 无任何断点参数可调，平板/折叠屏无法适配 | **P2** |

另有两个次要问题（见 §五）：加载中会闪"此歌曲为纯音乐，请您欣赏"、不可见页仍在全量重绘 Canvas。

## 二、数据流全景

```
AVPlayer.timeUpdate  (~100ms 一次)
   │
   ├─ isPreparing / seeking ? → return（抑制）
   ├─ bucket = floor(time / 500)
   └─ bucket 变化时 → AppStorage['progress'] = time/1000   ← 精度只剩 500ms，这是缺陷 1
                          │
            ┌─────────────┴─────────────┐
            ↓                           ↓
  ControlAreaComponent            LyricsComponent
  （进度条，500ms 视觉无损）        @StorageLink time
                                        │  ×1000
                                        ↓
                                   LrcView @Prop lyricMilliSecondsTime
                                        │  @Watch → onTimeUpdated()
                                        ↓
                                   findShowLine(ms)   ← 缺陷 2：>= 右边界
                                        ↓
                                   换行 → smoothScrollTo(400ms animator)
                                   同行 → drawContent 全量重绘
```

关键事实：**`STORE_PROGRESS` 是全局唯一的时间源，歌词没有自己的时钟。**
进度条按 500ms 分桶是合理的（显示到秒），但歌词的判定精度被同一个桶绑死了。

## 三、逐项证据

### 缺陷 1：500ms 分桶 = 歌词精度的天花板

`player/MusicPlayer.ts:67`
```ts
const PROGRESS_PUSH_INTERVAL_MS: number = 500;
```
`MusicPlayer.ts:708-712`
```ts
const bucket: number = Math.floor(time / PROGRESS_PUSH_INTERVAL_MS);
if (!this.seeking && bucket !== this.lastProgressBucket) {
  this.lastProgressBucket = bucket;
  this.setStore(STORE_PROGRESS, time / 1000);
}
```

用真实 QQ 音乐歌词跑模拟（复刻 `parseLrc` → `toLrcEntries` → `findShowLine`，
AVPlayer 100ms 回调 + 500ms 分桶，整首播放）：

| 歌曲 | 换行次数 | 平均滞后 | 最大滞后 |
|---|---|---|---|
| 晴天（269s, 63 行） | 63 | **226ms** | **500ms** |
| Lemon（256s, 57 行） | 57 | 235ms | 500ms |
| 七里香（299s, 38 行） | 38 | 189ms | 500ms |

只改推送间隔做对照：

| 推送间隔 | 平均滞后 | 最大滞后 |
|---|---|---|
| 100ms | 46ms | 80ms |
| 250ms | 71ms | 160ms |
| **500ms（现状）** | **171ms** | **360ms** |

**更严重的是密集行。** 构造行间隔 300ms 的序列（说唱、快歌、日文短句）：

| 方案 | 换行次数 | 被跳过行数 |
|---|---|---|
| 现状（500ms 桶） | 19 / 31 | **12 行** |
| 500ms 桶 + 边界修正 | 19 / 31 | **12 行**（边界修不了） |
| 100ms 推送 + 边界修正 | 31 / 31 | 0 行 |

真实数据里《Lemon》的 `[00:00.53]词：米津玄師` 行时长只有 **530ms**，
刚好比 500ms 多 30ms 才侥幸没被跳过 —— 说明这个阈值就在悬崖边上。

### 缺陷 2：`findShowLine` 的右边界用了 `>=`

`lyric/LrcView.ets:534-544`
```ts
findShowLine(milliSeconds: number): number {
  for (let index = 0; index < this.mLrcEntryList.length; index++) {
    if (this.mLrcEntryList[index].lineStartTime <= milliSeconds
      && this.mLrcEntryList[index].lineStartTime + this.mLrcEntryList[index].lineDuration >= milliSeconds) {
      return index;
    }
  }
  return this.mCurrentLine;
}
```

因为 `lineDuration = 下一行起点 - 本行起点`，右边界 `>=` 让**上一行在下一行起点那一刻仍然命中**。
线性扫描从前往后，于是返回上一行：

```
行 A: start=10000, dur=5000
行 B: start=15000, dur=...

t = 15000 → 行 A: 10000<=15000 && 15000>=15000 ✓ → 返回 A（错，应为 B）
t = 15500 → 行 A ✗, 行 B ✓ → 返回 B
```

实测（起点多为 500 整数倍的片段，tick 相位 0）：

| 边界写法 | 平均滞后 | 最大滞后 | ≥500ms 次数 |
|---|---|---|---|
| `>=`（现状） | **307.5ms** | 500ms | **3 / 12 次换行** |
| 左闭右开 `>` / 二分 | 182.5ms | 490ms | 0 |

另外 `return this.mCurrentLine` 这个兜底在**时间落在第一行之前**时是对的（不高亮），
但在「歌词被清空后 `mCurrentLine` 还是上一首行号」的情况下会返回越界索引。

### 缺陷 3：歌词缓存永久有效，匹配错无法自愈

`api/LyricsApi.ts:36-41`
```ts
type CacheEntry = { status: 'ok'; result: LyricResult } | { status: 'miss'; ts: number };
const MISS_TTL: number = 24 * 60 * 60 * 1000;   // 只有 miss 有 TTL
```

`getLyricForTrack` 命中 `ok` 直接返回，**没有任何时效、没有重新校验**。
唯一的失效路径是 `LyricsComponent.onTrackChanged` 里那条：

```ts
if (track.duration > 0 && !hadDuration) {
  LyricsApi.clearLyricCache(track.id);   // 只在「上次缺时长、这次有」时清
}
```

而 B 站视频标题天然脏（`【4K修复】晴天 - 周杰伦`、`晴天（Live）`、`周杰伦-晴天 cover`），
`scoreCandidate` 用 `dice` 相似度 + 时长加分选候选：

- 原版与翻唱版的 `normIncludes` 都会命中（`晴天` 包含于 `晴天女声独唱版`），得 0.86×180 ≈ 155 分；
- 时长差 ≤4s 再 +130 → 两项都过阈值 120，**谁先遍历到谁赢**；
- 一旦翻唱版胜出并写入 `ok`，这首歌就永久错位。

这正是「有时候」的典型特征：**不是随机抖动，而是特定几首歌永远对不上。**

### 缺陷 4：无时间轴歌词被当作有时间轴

`api/LyricsApi.ts:109-123`
```ts
const syncedLines = parseLrc(content);
const lines = syncedLines.length > 0 ? syncedLines : plainToLines(content);
return { lines, synced: syncedLines.length > 0, ... };
```

`utils/TextUtil.ts:182-189`
```ts
function plainToLines(plain: string): LyricLine[] {
  return plain.split('\n')
    .map(...).filter(...)
    .map((text: string): LyricLine => ({ time: -1, text: text }));   // ← 全部 -1
}
```

`LyricsComponent.toLrcEntries` 把它转成毫秒：

```
第 i 行: lineStartTime = -1000
        lineDuration  = 第 i+1 行起点 - (-1000) = -1000 - (-1000) = 0
最后一行: lineDuration  = Number.MAX_VALUE
```

`findShowLine` 对任何 `t > 0`：
- 前 9 行：`-1000 <= t` ✓ 但 `-1000 + 0 = -1000 >= t` ✗
- 最后一行：`-1000 + MAX_VALUE >= t` ✓ → **返回最后一行**

实测：**10 行的纯文本歌词，只有第 10 行会被高亮，且从头到尾不动。**
而 `synced` 字段在全仓**零个消费者**（只在 `LyricsApi` 里被写入），
`model/MusicModels.ts:437` 定义的 `LyricStatus = 'idle'|'loading'|'ok'|'unsynced'|'empty'`
也是**完全没有被引用的死类型**。设计意图存在，但没接上。

### 缺陷 5：制作人员行不过滤，`[offset:]` 不应用

真实返回（《晴天》）：
```
[ti:晴天] [ar:周杰伦] [al:叶惠美] [by:] [offset:0]
[00:00.00]晴天 - 周杰伦 (Jay Chou)
[00:02.25]词：周杰伦
[00:04.50]曲：周杰伦
[00:06.75]编曲：周杰伦
...
[00:27.01]混音工程：杨大纬（杨大纬录音工作室）
[00:29.26]故事的小黄花      ← 第一句真正的歌词
```

`parseLrc` 跳过的是 `ti:/ar:/al:/by:/offset:` 这类**元信息行**，
但「词：周杰伦」这类**制作人员行带时间标签、是正常歌词行**，会原样进入时间轴。

实测各曲制作人员行占比：

| 歌曲 | 制作人员行数 | 占据时长 |
|---|---|---|
| 晴天 | 7 行 | 0 ~ 22.5s |
| 七里香 | 3 行 | 0 ~ 20.8s |
| Lemon | 2 行 | 0 ~ 1.5s |

同时 `[offset:0]` 被识别为元信息**直接丢弃**，但其数值从未应用到时间轴。
QQ 音乐偶尔下发非 0 offset（如 `[offset:-500]`），此时整首歌词会恒定偏移 500ms，
且用户完全无法察觉原因。

### 缺陷 6：歌词字号/行距无法适配断点

`lyric/LrcView.ets:64-66`
```ts
private mNormalTextSize: number = 20;
private mDividerHeight: number = 24;
private mCurrentTextSize: number = 24;
```

三个都是 `private`，`LyricsComponent` 实例化 `LrcView({...})` 时
（`LyricsComponent.ets:287` LG 分栏 / `:301` 非 LG）**只传了 4 个参数**：
`lyricMilliSecondsTime / mLrcEntryList / lyricScrollEffect / isPlay`，
外加普通成员 `lyricTopPosition`。**字号与行距没有任何入口可调。**

对比同一文件里标题/歌手字号是走 `BreakpointType` 的（`LyricsComponent.ets:239-254`），
说明断点体系是有的，只是歌词正文没接进去。平板上歌词仍是 24vp / 行距 24vp，观感偏小偏挤。

补充：Canvas 用 `'24vp'` 而非 `'fp'`，**不跟随系统字体缩放**。这是 Canvas 方案固有代价，
需要单独按 `fontSizeScale` 手动补偿（可选）。

## 四、解决方案

### P0-1 让歌词拿回自己的时钟（解决缺陷 1 与「跳行」）

**不建议**直接把 `PROGRESS_PUSH_INTERVAL_MS` 从 500 改成 100：
那样播放页声明式重渲染从 2 次/秒涨到 10 次/秒，
而 `MusicPlayer.ts:693-697` 的注释明确记录过这个后果 ——「拖进度条被拖帧 / 拖了又跳回去」。

**推荐：分桶不动，LrcView 内部做「本地时钟外推 + 精准唤醒」。**

1. `LyricsComponent` 给 `time` 加 `@Watch`，每次 tick 时记下
   `baseAudioMs = time*1000`、`baseLocalMs = Date.now()`，与上一次外推值比较：
   偏差 > 400ms（seek / 换歌 / 暂停恢复）则立即硬对齐并重绘。
2. `LrcView` 用 `audioNow = baseAudioMs + (Date.now() - baseLocalMs) * rate` 判行
   （`isPlay` 为 false 时冻结）。
3. **不要起常驻 60fps 定时器。** 每次判行后算「距下一行起点还差多少」，
   用 `setTimeout` 精准唤醒：差值 > 300ms 就睡 300ms 再查，差值 ≤ 300ms 就按
   ~30ms 步进。每行只唤醒 2~3 次，比现在每 tick 全量重绘还省。
4. 换行时的 400ms 补间动画不受影响（它本来就独立于 tick）。

收益：判行精度从 500ms → ~30ms，且**不增加任何声明式重渲染**。
风险：低，改动集中在 `LrcView` 内部；`MusicPlayer` 一行不用动。

> 若不想动 LrcView 的定时逻辑，退而求其次的最小改动：
> 让 `LyricsComponent` 只在「临近换行」时用本地插值写一次 `@Prop`（每行 1~2 次），
> 代价是换行前一瞬间会有一次额外重渲染，可接受。

### P0-2 修正 `findShowLine`（解决缺陷 2）

```ts
// 现状：线性扫描 + 右边界 >=  → 换行晚一个 tick
// 改为：二分找「最后一个 startTime <= ms」的行，天然左闭右开
findShowLine(ms: number): number {
  const list = this.mLrcEntryList;
  if (!list || list.length === 0) return this.mCurrentLine;
  let lo = 0, hi = list.length - 1, ans = -1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    if (list[mid].lineStartTime <= ms) { ans = mid; lo = mid + 1; } else { hi = mid - 1; }
  }
  // ans === -1 → 时间在第一行之前，不高亮（返回 -1，不要返回 mCurrentLine）
  return ans;
}
```

顺带解决三个衍生问题：
- 复杂度从 O(n) 降到 O(log n)（每 tick 都调）；
- 不再依赖 `lineDuration`，**重复时间标签导致的 `duration=0` 行也能被正确命中**
  （实测现状下 `[00:10.00]A / [00:10.00]B / [00:10.00]C` 会跳过 A、B 两行）；
- `ans === -1` 时返回 `-1` 而不是 `mCurrentLine`，避免切歌后越界。

### P0-3 歌词缓存加自愈（解决缺陷 3）

三选一或组合：

**a) 结果里带上「可信度」，低分时给短 TTL。**
`LyricResult` 增加 `confidence: number`（复用 `scoreCandidate` 的分数），
`cacheOk` 时按阈值写 `ok` 或 `weak`；`weak` 状态 TTL 7 天，且**每次打开播放页允许一次后台重校验**。

**b) 时长交叉校验。**
命中缓存时比对 `track.duration` 与缓存里记录的候选时长，
偏差 > 15s 视为「可疑」，清缓存重搜（不阻塞 UI，先显示旧歌词，重搜到更好的再替换）。

**c) 用户手动纠正入口。**
`LyricsApi` 已经有 `searchLyricCandidates` / `chooseLyricCandidate` 两个函数，
但**全仓零调用方** —— 接口写好了，UI 没接。
在歌词页长按给一个「搜索歌词 / 换一个版本」，选完写 `ok` 并在记录里打 `manual: true`
（手动选择的永不自动重搜）。这条最能兜住「少数几首永远错」的长尾。

建议：**a + c**。a 负责自动自愈，c 给用户终极手段。

### P1-1 无时间轴歌词走「纯文本模式」（解决缺陷 4）

1. `LyricsComponent` 读 `result.synced`，为 `false` 时：
   - **不要把 `time = -1` 转成 LrcEntry**；
   - 改为把整篇文本按 `\n` 切成 `LrcEntry[]`，`lineStartTime = -1`、`lineDuration = MAX`，
     并给 `LrcView` 一个新开关 `unsyncedMode = true`；
   - `LrcView` 在 `unsyncedMode` 下：不判行、不高亮任何行、不滚动（或允许手势滚动），
     全部按 normal 色绘制，顶部显示一行灰色提示「该歌词无时间轴」。
2. 顺手把死类型 `LyricStatus` 用起来，或在确认不用后删掉，
   避免下一个人再次误判「这套东西已经接好了」。

### P1-2 清洗歌词行（解决缺陷 5）

在 `parseLrc` 之后、`toLrcEntries` 之前加一道 `sanitize(lines, duration)`：

- **应用 offset**：解析 `[offset:n]`（毫秒），把所有 `time += n/1000`；负数时钳到 0。
- **过滤制作人员行**：`/^(作?词|作?曲|编曲|制作人?|合声|和声|吉他|贝斯|鼓|录音|混音|母带|监制|统筹|出品|发行|策划|OP|SP|演唱|原唱|翻唱)[：:]/`
  - ⚠️ 只过滤**歌曲开头前 N 秒（建议 30s）内**的这些行，
    避免误伤歌词正文里恰好以「曲：」开头的句子；
  - 过滤后如果第一行起点显著 > 0，可把第一行起点拉到 0 之前的空白段，
    让「前奏 + 制作人员」时段保持无高亮而不是空屏。
- **标题行**：首行文本等于 `cleanTitle(track.title)` 或包含「 - 歌手」的，同样处理。
- **去重**：`time` 与 `text` 都相同的连续重复行只留一条。

### P2-1 字号/行距参数化（解决缺陷 6）

把三个 `private` 改成带默认值的 `@Prop`（或普通成员 + 构造参数）：

```ts
@Prop normalTextSize: number = 20;
@Prop currentTextSize: number = 24;
@Prop lineGap: number = 24;
```
`LyricsComponent` 按 `currentBreakpoint` 传值（sm/md/lg 三档，与标题字号同一套响应式逻辑），
LG 分栏下适当放大（如 26/30 + 行距 28）以匹配半宽栅格。

注意：改字号后 `getOffset` 的累计高度会自动跟着变（它内部调 `getLineHeight`），
但**必须在字号变化时重算 `initFirstLineY`** —— 现在它是 `if (this.initFirstLineY === 0)` 只算一次，
字号变了会让「当前行居中」的位置偏掉。建议改用 `@Watch` 在字号变化时重置为 0 触发重算。

### P2-2 加载态与「纯音乐」区分

`LrcView.drawContent` 在 `mLrcEntryList` 为空时统一画 `EMPTY_LYRIC`
（"此歌曲为纯音乐，请您欣赏"）。而 `LyricsComponent` 切歌时会先
`this.mLrcEntryList = []`，所以**每次切歌都会闪一下这个提示**，请求失败则永久显示。

建议传一个显式的 `loadState: 'loading' | 'ok' | 'empty'`：
- `loading` → 画 3 个呼吸点 / 或留空（不误导）；
- `empty` → 才画「此歌曲为纯音乐，请您欣赏」；
- `ok` 但 `unsynced` → 见 P1-1。

### P2-3 不可见时不重绘

`LyricsComponent` 在 `Swiper` 第 2 页始终存活，用户停在封面页时
歌词 Canvas 仍在每 tick 全量重绘（62 行 × `measureText` + 折行 `while`）。
建议用 `Swiper.onChange` 维护 `isLyricPageVisible`，仅在 `true` 时响应 tick 与动画；
切回时立即 `drawContent` 补一帧。顺带解决「封面页唱片旋转掉帧」。

## 五、其他发现（不影响同步，但值得顺手处理）

1. **`smoothScrollTo` 在暂停时不尊重 `isPlay`**：`startAnimator` 里无条件 `play()`，
   暂停状态拖动进度条，歌词会自己滚 400ms。
2. **seek 大跨度是「一路滑过去」**：从第 3 行拖到第 50 行，400ms 补间会让整篇快速滑过。
   可考虑「跨度 > 5 行时改为瞬时对齐 + 短淡入」。
3. **`LrcUtils.ets` 整体是死代码**：`parseLrcLyric`、`parseKrcLyric`、`angleToRadian`
   （`angleToRadian` 被 `LrcView` 用，另两个零调用）。文件头写着「保留备用」，
   但 LyricsApi 走的是 `TextUtil.parseLrc`，两套解析器并存容易改错地方。
4. **`LrcView` 头注释过时**：写着「400ms 线性补间」，实际 `startAnimator` 是 `ease-in-out`。
5. **`OiapiLyricData.base64` 字段声明了但从不使用**。若某天 `content` 为空而 `base64` 有值
   （KRC 格式），会直接返回空字符串并缓存成 `miss` 24 小时。
6. **`fontFamily` 硬编码 `'HarmonyHeiTi'`**，与项目其它地方 `PlayerConstants.FONT_FAMILY_BOLD` 不一致。

## 七、怎么验证（不靠肉眼猜）

1. **加一行可检索日志**：`LrcView.onTimeUpdated` 打印
   `tick=${ms} line=${line} delta=${ms - lineStartTime}`，
   真机 hilog 过滤 `[Lrc]`。若 `delta` 长期 > 300ms，P0-1/P0-2 还没生效。
2. **造一首密集行测试曲**：找一首说唱（行间隔常 < 400ms），
   修前必然出现「跳行」，修后应逐行命中。
3. **造一首无时间轴测试曲**：随便找一首只有纯文本歌词的（小众歌/上传版），
   修前卡最后一行，修后应显示整篇静态文本 + 提示。
4. **造一首缓存错位测试曲**：拿一首标题带 `【4K】` `(Live)` 的视频，
   观察首次匹配是否选中翻唱版；用第 4 步的手动入口纠一次，确认不会再被自动覆盖。
5. 平板/折叠屏单独看 LG 分栏下的字号与行距（P2-1 前后对比截图）。
