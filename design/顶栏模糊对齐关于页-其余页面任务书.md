# 顶栏滚动模糊「对齐关于页」任务书（其余页面参数补偿）

> 写于 2026-10-09 22:45，基于**真机反馈 + 源码实证**。
> 本任务**只改模糊时机参数**（样式助手加一个入参 + 五个调用页各改一行 + 若干注释），
> **不改任何布局 / 让位量 / 材质 / 转场结构**。
> 参照物 = **关于页（AboutPage）当前行为**，用户已确认为“正确”：「内容没上移出屏幕，顶栏就开始出雾」。

---

## 0. 一句话

五个列表页当前的 `styleOptions(30, 80)`，其起雾时机被 HDS 的取数方式**整体推后约 C vp**（C = 该页让位量）。
改为调用时附带补偿（`styleOptions(30, 80, this.barTotalHeight())`，样式助手内部 `−C`），
让起雾时机回到「**首条内容自静止位上移 30vp**」——与关于页同一口径。
**关于页 / 登录页 / 短信登录页不动；四个 Tab 页（搜索/歌单/下载/设置）不在本任务内。**

---

## 1. 基准：关于页的“正确”行为（验收标尺）

关于页用 Scroll + 内容侧 `padding({ top: safeTop + 56 })` 让位——内容顶边**静止时贴着顶栏底缘**。

真机确认的正确观感：

| 滚动量（内容自静止位上移） | 观感 |
|---|---|
| 0 ~ 30vp | 顶栏完全透明（无雾） |
| **30vp** | **开始起雾**（此时内容完整可见、没出屏） |
| 30 ~ 80vp | 渐变增强（对栏后内容做磨砂） |
| **80vp** | 完全显影 |
| 下拉回弹（负偏移） | 保持透明，无闪烁 |

本任务 = 让其余页达到**同一相对时机**：「首条内容自静止位上移 30vp 起雾、80vp 满」。

---

## 2. 为什么其他页与关于页不同：实测模型（关键，先读懂再动手）

### 2.1 两条让位通路（全工程现状，已核实）

| 通路 | 页面 | 让位实现 | 备注 |
|---|---|---|---|
| **A（基准，不动）** | AboutPage / LoginPage / SmsLoginPage | Scroll + 内容侧 `padding({ top: safeTop + 56 })` | 内容让位走 padding，HDS 看不到 |
| **B（本任务）** | RecentPage / FollowsPage / WatchHistoryPage / UpSpacePage / PlaylistDetail | List + `contentStartOffset(this.barTotalHeight())` | 让位量是 List 的**可读属性** |

### 2.2 真机证据链 → 拟合模型

| # | 配置 | 观察（用户真机） |
|---|---|---|
| 1 | 全部页缺省参数（start=0, end=56） | 「条目要**移出屏幕后**，顶栏才开始渐进模糊」 |
| 2 | 统一改为 `(30, 80)` 后，**关于页** | 「内容**没出屏**就起雾」→ 正确，即基准 |
| 3 | 同参数下，**列表页** | 「条目**要移动到屏幕外**才开始起雾」→ 依旧太晚 |

两页唯一结构差异 = 是否使用 `contentStartOffset`。拟合结论：

> **HDS 实际用于渐变判定的滚动量 F，被让位量 C 整体推后：**
>
> - 通路 B（列表页）：`F = raw − C`
> - 通路 A（关于/登录/短信）：`F = raw`
>
> 其中 `C = contentStartOffset 的值 = 本页 barTotalHeight()`，`raw` = 用户实际滚动的距离。
> （机制假说：List 带 contentStartOffset 时，HDS 读到的偏移零点含这段让位。机制无论是否如此，
> **补偿式相同**；本模型由上面两条真机观察 + About 对照拟合得出，Step 1 还会再验一次。）

自检一下这个模型与观察 1/3 是否吻合：UpSpace 的 C ≈ safeTop+56+头部区 ≈ 276（safeTop≈40），
`F = raw − 276`；参数 `(30, 80)` 意味着 **raw ≈ 306 才起雾**——此时条目顶边已经出了屏幕约 30vp，
正是用户描述的现象。✓

### 2.3 推论：补偿公式

要让「**raw = 30 起雾**」成立，需 `F = 30` 时恰好达下限：

```
start 改动量 = 30 − C        // 即：基准 30 减去本页让位量
end   改动量 = 80 − C        // span 保持 50，渐变速度不变
```

等效描述：**列表页把两个参数整体减去本页让位量 C**。
⚠️ 结果会**出现负值**（如 −246）——这是“偏移量”不是物理距离，属预期，不是 bug。

## 3. 修改实现（推荐：样式助手加第三参，调用页各改一行）

### 3.1 `utils/HdsTitleBarStyle.ets` —— `styleOptions` 加可选第三参

现状（约 50~67 行）：`static styleOptions(blurStartVp?: number, blurEndVp?: number)` 直接把两个值
写进 `LengthMetrics.vp(...)`。**改为**：

```ts
/**
 * @param blurStartVp 滚动模糊起始偏移（基准口径 = 关于页：“首条内容自静止位上移量”的下限）。
 *   不传 = HDS 默认（0）。
 * @param blurEndVp 滚动模糊完成偏移（上限，不传 = HDS 默认：沉浸档 56 / 兜底档 8）。
 * @param coffsetComp 让位量补偿（vp）：传本页 contentStartOffset 的值（= barTotalHeight()）。
 *   HDS 对使用 contentStartOffset 让位的列表页，取到的滚动量会被让位量整体推后
 *   （实测拟合，见 design/顶栏模糊对齐关于页-其余页面任务书.md §2），
 *   传入后在效果上等价于「首条内容自静止位上移 blurStartVp 起雾」。
 *   padding 让位的页（关于/登录/短信）保持不传（默认 0）。
 */
static styleOptions(blurStartVp?: number, blurEndVp?: number, coffsetComp: number = 0): TitleBarStyleOptions {
  // ⚠️ 不要对结果钳制到 ≥0：负值是补偿后的正常取值（如 30−276=−246）
  const startNum: number | undefined = blurStartVp !== undefined ? blurStartVp - coffsetComp : undefined;
  const endNum: number | undefined = blurEndVp !== undefined ? blurEndVp - coffsetComp : undefined;
  // 后续 LengthMetrics.vp(startNum / endNum) 与两处日志文本改用 startNum / endNum
  ...
}
```

要点：
- **不要钳制负值**（钳制 = 补偿失效，见 §4 失败签名）。
- 日志 `[TopBar] blurStart=... blurEnd=...` 改为打印**补偿后的值**（真机用它核对，见 §4）。
- 两参调用（关于/登录/短信）行为**零变化**（coffsetComp 默认 0）。
- 顺带更新文件头注释中「按‘条目顶边触到本页标题栏底缘那一刻的滚动距离’计算——首例 16」这段旧口径
  （已被本任务书取代）。

| 1 | `pages/UpSpacePage.ets` | L73-74 `UP_BLUR_*` | L1117 | 头部区实测高，C = safeTop+56+头部区 |

改法（以 UpSpace 为例，其余页同构替换前缀）：

同步把每页常量注释从旧的「滚动 0~30vp 完全透明 → 30~80vp 材质渐变」改为基准口径，例如：

```ts
/** 顶栏滚动模糊时机（基准口径 = 关于页，任务书 §2）：首条内容自静止位上移 30vp 起雾 → 80vp 满显影。
 *  列表页须在调用处补第三参 barTotalHeight()，抵消 HDS 对 contentStartOffset 让位的推后。 */
```

**注意（UpSpace / PlaylistDetail）**：`barTotalHeight()` 在头部区实测完成前会偏小（少头部区高度），
参数会先算一次「小 C」、实测后再刷新为「大 C」——公式自洽，**两种状态下“起雾 = 上移 30vp”都成立**，
不需要额外门控。见 §7 未知项 2（核对是否被 HDS 重读）。

## 5. 回退方案（Step 1 失败时，按序试）

**A. 临时缓解（不达标，只用于争取时间）**
把五个页面的参数改为 `(0, 50)`：起雾点从 `raw = C+30` 提前到 `raw = C`（条目顶边刚到屏幕顶），
仍偏晚，仅比现状早 30vp。**明确：这不是目标态。**

**B. 结构性迁移（负值不可用时的主回退）**
把这些列表页的让位从 `contentStartOffset` 改为「关于页同款」——内容侧
`padding({ top: this.barTotalHeight() })`，参数回 `(30, 80)`（与关于页完全同构，F = raw）。
**先只用 RecentPage 单页真机验证**：List + padding 下条目仍能从栏下穿过（不被裁剪、不吃点击），
通过后再推广；失败则回收。

**C. 终极兜底（B 也失败时）**
该页放弃 `scrollEffectOpts`，恢复旧 `GlassTopBar` 式「backgroundEffect + onDidScroll 手动 reveal」
（旧版本真机验证过、完全可控），代价是失去 HDS 材质/温控。仅对确实无解的单页使用。

## 6. 红线与工程注意事项

1. **不动** About / Login / SmsLogin 的调用与参数；**不动** 四个 Tab 页（搜索/歌单/下载/设置——
   它们仍走旧 `GlassTopBar` 通路，40vp 浮出，不在本任务口径内，别拿来对比）。
2. **不改** 任何布局/让位量（`barTotalHeight()`、`contentStartOffset`、padding 一律不动）。
3. span 恒等于 50（只平移窗口，不改渐变速度）。
4. `coffsetComp` 用**运行时值** `this.barTotalHeight()`，不硬编码、不钳制负值。
5. `UpSpacePage` 的 `.clip(false)`（L1082）保持不动；其余页**暂不加**。
6. 编译流程（本项目踩坑口径）：
   - 修改后先 `touch` 所有改动文件（否则增量缓存会跳过 CompileArkTS）；
   - 编译前设 `$env:CODEBUDDY_SAFE_DELETE_BULK_STATE_DIR = ""`（否则沙箱删除保护误报 00308018）；
   - 错误看 `HarmonyOS-Phone/.hvigor/outputs/build-logs/build.log`，不在 stdout；
   - 判据 = `BUILD SUCCESSFUL` + ArkTS ERROR 0；ArkUI 括号错误报错行号会指向后面的无关节点，先往前找 `}`。
7. 全程**不要**把“编译通过”当“效果验证”——起雾时机必须在真机上按 §4 判据确认。
