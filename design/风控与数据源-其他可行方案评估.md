## 1. 一个被忽略的事实：应用本来就在走系统代理

这一条可能让整个改造都不必要。

SDK `@ohos.net.http.d.ts:201-216` 原文：

```
HTTP proxy configuration. If this item is not configured, the system proxy is used by default.
- If usingProxy is set to true, the default network proxy is used.
- If usingProxy is set to false, no proxy is used.
- If usingProxy is of the HttpProxy type, the specified network proxy is used.
usingProxy?: boolean | HttpProxy;   // since 11
```

而工程里 `grep -rn "usingProxy"` → **0 处**。

**结论：`http.createHttp()` 的请求默认就走系统代理。** 如果用户手机开着 VPN / 代理 App（全局模式），BiliMusic 的 API 请求**已经在走代理出口了**。

所以第一件事不是写代码，而是验证：

> **开一个代理（换掉当前出口 IP）→ 冷启动 app → 播一首之前 `-352` 的歌。**
> 若能播 → 风控确认是 IP 维度，且用户自己就能解，不需要任何改造（只需在设置页加一句说明）。
> 若不能播 → 说明 -352 不只是出口 IP 问题，继续看下面。

⚠️ 注意：这里说的是**系统级代理 / VPN**。如果只开「代理 App 的分应用代理」而没有把 BiliMusic 选进去，等于没开。

## 2. 先排除已被证伪的路（省得再走一遍）

`api/BilibiliApi.ts:255-264` 有一段本机实测记录，直接否定了所有「换指纹」类方案：

```
* API 搜索是**按 IP 计量**的硬配额，长歌单必然撞墙，撞墙后整批「未找到」。
*
* 实测（本机，PC UA + buvid）：
*   · /x/web-interface/wbi/search/type 干净起步第 48 次请求 → HTTP 412；
*   · 撞墙后换全新 buvid / 不带任何 Cookie / 换 iPhone UA → 全部仍然 412
*     （所以限流跟设备指纹无关，是 IP 维度）；封禁持续 9 分钟以上未恢复；
*   · 同一时刻 search.bilibili.com/all?keyword= 的 HTML 页仍返回 200，
*     且压测 40/40 次全部正常，每页 41~42 张卡片。
```

**三条结论，别忘：**

1. **换 UA / buvid / Cookie 无效** —— 已经试过，全是 412。这类方案以后不必再提。
2. **封禁是 9 分钟以上的时间窗**，不是「重试一次就好」。这决定了 S3 / S4 的价值。
3. **同一时刻 HTML 页 40/40 正常** —— 这是 S5 的实证基础，说明「API 配额」和「网页访问」是两套计量。

## 3. S2 · 应用内代理设置（首选方案）

### 3.1 为什么比 L1 网关好

| 维度 | L1 网关（自建反代） | S2 应用内代理 |
|---|---|---|
| 用户要做什么 | 部署 Cloudflare Worker / Nginx，配域名和证书 | **填一个 `host:port`** |
| 需要写服务端代码 | 是（透传 + 可选改写） | **否** |
| 覆盖范围 | 只 API 域 | **全部流量**（含 passport、CDN、短链、HTML 兜底） |
| 改动量 | 6 文件 | **2 文件**（`HttpUtil` 三入口 + 设置页） |
| 被网关自己风控的风险 | 有（共享 IP 的公共反代必死） | 无（用户自己的出口） |
| 凭据暴露 | Cookie 经第三方网关可见 | HTTPS 隧道内不可见 |

**关键差异：S2 是网络层换出口，L1 是应用层换域名。** 前者顺带解决了 L1 文档里所有「不代理 passport / 不代理 CDN / 不代理短链」的遗留缺口。

### 3.2 可用的两个字段

| 字段 | 类型 | since | 字段结构 |
|---|---|---|---|
| `usingProxy` | `boolean \| HttpProxy` | **11**（兼容 API 23） | `host` / `port` / `username?` / `password?` / `exclusionList?` |
| `usingSocks5Proxy` | `Socks5Proxy` | **26.0.0** | 同上 + `dnsStrategy?` |

- `HttpProxy`：`@ohos.net.connection.d.ts:2286`
- `Socks5Proxy`：`@ohos.net.connection.d.ts:2355`
- 文档明确：`usingSocks5Proxy` **优先于** `usingProxy`，建议不要同时配
- 两者标注 `@stagemodelonly`（本工程是 Stage 模型，满足）

**建议只做 HTTP 代理（`usingProxy`），不做 SOCKS5。** 理由：`@since 26` 意味着 API 23~25 设备用不了，而工程 `compatibleSdkVersion` 是 23。要支持就得分版本走，收益不值得。

### 3.3 改动点（精确）

`http.createHttp()` 全仓 **6 处**：

| 位置 | 用途 | 是否必须注入 |
|---|---|---|
| `utils/HttpUtil.ts:183` | `requestText`（主通道） | ✅ |
| `utils/HttpUtil.ts:235` | `probeRedirectLocation`（短链 302） | ✅ |
| `utils/HttpUtil.ts:290` | `requestTextWithCookies` | ✅ |
| `service/DownloadManager.ts:1030` | 音频下载（`requestInStream`） | ✅ 音频量大，最该走 |
| `player/MusicPlayer.ts:1154` | 封面图取字节 | 可选 |
| `components/player/PlayerInfoComponent.ets:788` | 直连 HTTP | 可选 |

`HttpUtil.ts:185-200` 的 options 是**内联字面量**，加一行 `usingProxy: AppProxy.current()` 即可（三处同形）。

### 3.4 ⚠️ 一条必须知道的限制：代理不覆盖音频流

**AVPlayer 播放音频不走 `http.createHttp`**，它有自己的网络栈。所以：

| 流量 | S2 应用内代理 | 系统 VPN |
|---|---|---|
| API 请求（view / playurl / search） | ✅ 生效 | ✅ 生效 |
| 音频流（`bilivideo.com` CDN） | ❌ **不生效** | ✅ 生效 |
| 封面图（走 `createHttp` 那处） | ✅ 生效 | ✅ 生效 |
| 下载（走 `requestInStream`） | ✅ 生效 | ✅ 生效 |

这个区分很关键：

- **`-352` 出自 playurl 接口**（走 `createHttp`）→ **S2 能解**
- 如果问题是「直链拿到了但 CDN 拒绝 / 慢」→ S2 **解不了**，只能靠系统 VPN

所以 S2 上线后要在真机上确认：`-352` 是否真的来自接口层。如果换了出口还是报错，说明问题在 CDN 侧，方向要切到系统 VPN 或 CDN 域名改写（`api/BilibiliApi.ts` 里已有 backup URL 逻辑）。

### 3.5 必须做的兜底

代理挂了不能让 app 全瘫。三条硬要求：

1. **连接阶段失败要能识别**：`usingProxy` 指向不可达的 host，请求会在 connect 阶段失败（不是 HTTP 错误码），要区分「代理不可用」与「接口报错」。
2. **失败回落直连**：某次请求因代理失败 → 自动用 `usingProxy: false` 重试一次。回落要**记一笔日志**，不要静默。
3. **设置页要能一键关**：开关 + 输入框 + 「测试连接」按钮（调 `GET {base}/x/web-interface/nav`，判 HTTP 200 + 可解析 + 有 `code` 字段）。

## 4. S3 · 听后音频缓存（纯收益，与所有方案叠加）

### 4.1 现状

全仓**没有音频缓存**（`grep -rn "audioCache"` → 0 处）。只有：

- 歌词缓存：`service/LyricCacheStore.ts`（`${filesDir}/lyrics`，上限 300 首，文件系统）
- 下载：`${filesDir}/downloads`（用户主动，永久）
- `Track.audioUrl`：缓存了直链，但**直链会过期**（`BilibiliApi.ts:1265`）

也就是说：**每播一次同一首歌，都要重新发 view + playurl 两个请求**，哪怕这一小时里已经播过三次。

### 4.2 为什么这能治风控

风控是「按 IP 计量的硬配额」。配额消耗的基本单位是**请求次数**，不是「歌曲数」。所以减少重复请求是**直接**降低撞墙概率的手段，而且和 S1/S2/S5 完全兼容。

一首歌典型请求：`view`（拿 cid）+ `playurl`（拿直链）+ 封面 + 歌词 ≈ 4~5 个。二次播放若能命中缓存，降到 0~1 个。

### 4.3 做法

不是新造轮子 —— **复用下载模块的成品**：

- 存储：`${filesDir}/audio_cache/`，与 `downloads/` 分目录（下载是用户资产，缓存可清）
- 播放：文件存在就写 `Track.localFilePath`，走 `MusicPlayer.ts:2275` 的既有分流，**播放内核零改动**
- 淘汰：LRU + 总量上限（建议 500MB），**清理入口复用 `pages/DownloadSettingsPage.ets:185` 的「清理缓存」**（该行确为缓存清理入口；`SettingsPage.ets` 本身没有清理项）
- 关键约束：**缓存文件不能和下载文件混在同一目录**，否则「清理缓存」会误删用户下载的歌

### 4.4 与「已下载」的边界

| | 下载 | 听后缓存 |
|---|---|---|
| 触发 | 用户主动 | 自动（播完 / 播过 30s） |
| 位置 | `filesDir/downloads` | `filesDir/audio_cache` |
| 会被自动清理 | 否 | 是（LRU） |
| UI 可见 | 下载页 | 不需要（透明） |
| 音质 | 用户选的那档 | 同 |

⚠️ 已下载的曲目**不要重复缓存**（`localFilePath` 非空就直接跳过）。

## 5. S4 · 风控可恢复化 + 封禁窗口落盘

### 5.1 现状

`utils/BiliRequestGate.ts` 已有 `noteRisk()` / `noteSuccess()`，`BilibiliApi.ts:140` 有 `RETRYABLE_BIZ_CODES = [-352, -412, -509, -799]`。

但有一个缺口：**封禁窗口没有持久化**。实测封禁持续 9 分钟以上，如果用户在这期间杀掉 app 重开，新进程不知道「刚才刚被封过」，会立刻再发请求，把窗口继续延长。

### 5.2 做法（2 小时量）

1. `noteRisk()` 时把「封禁开始时间 + 预计结束时间（+10 分钟）」写进 Preferences（单值，几十字节，不涉上限）
2. 启动时读一次：还在窗口内 → 闸门直接按「冷却中」启动，请求排队而不是打出去
3. UI 上给一句明确文案：**「B 站限制访问中，约 3 分钟后恢复」**（倒计时），而不是报错弹窗
4. **窗口结束后不要自动重试全部积压请求** —— 要按优先级逐个放，否则一出窗口就打满，立刻再被封

第 4 条最容易做错：**解除封禁瞬间的流量尖峰会被立刻重新判定为风控**。

### 5.3 为什么值得做

风控不可能 100% 避免。真正决定体验的不是「能不能不撞墙」，而是「撞墙后 app 表现成什么样」。现在大概率是「加载失败，请稍后重试」——用户不知道要等 9 分钟，会反复点，越点越久。

## 6. S5 · HTML 通道扩容（有实证，但天花板不明）

### 6.1 已证实的部分

`BilibiliApi.ts:260-262` 实测：同一时刻 API 全 412，**HTML 搜索页 40/40 次全部正常**。工程里已经有 `searchVideoByHtml()`（`:313`）。

这说明：**B 站对「API 配额」和「网页访问」是两套计量。** 那么理论上，其他被 API 风控卡住的能力，也可能有 HTML 等价物。

### 6.2 可以试的（需真机验证，不能断言）

| 能力 | HTML 路径 | 可行性 |
|---|---|---|
| 搜索 | `search.bilibili.com/all?keyword=` | ✅ **已落地**，40/40 |
| 视频详情（拿 cid / 标题 / UP） | `www.bilibili.com/video/{bvid}` 页面 SSR 数据 | ⚠️ 待验 |
| 音频直链 | 播放页 HTML 的 `window.__playinfo__` | ⚠️ **待验，风险最高** |
| UP 主投稿列表 | `space.bilibili.com/{mid}/video` | ⚠️ 待验（该页已是 JS 渲染，SSR 可能拿不到） |

### 6.3 为什么「音频直链」这条要谨慎

它看起来最诱人（一步拿到底），但：

- `__playinfo__` 需要页面执行 JS 后才有，或依赖 SSR 输出，**B 站随时可能移出 SSR**
- 未登录态播放页可能不输出 `__playinfo__`
- 拿到的还是同一个 CDN 直链，**同样会过期**，没有解决根本问题
- 一旦 B 站改版，这条通道静默失效（和现有 HTML 搜索兜底同样的风险）

**建议：S5 只做「视频详情」这一项**（拿 cid 用），音频仍然走 playurl。因为 `view` 接口的调用频次和 `search` 同级，是最容易被配额卡的。

### 6.4 硬性要求

- HTML 解析**必须只是兜底**：解析失败返回空，绝不能让主通道跟着失败（现有 `searchVideoByHtml` 就是这么写的，照抄这个模式）
- 依赖的 class 名要集中成一个常量块并注释「B 站改版会失效」（现有代码已有此惯例）
- 每个 HTML 通道要有独立开关，出问题能单独关

## 7. S6 · 备用音源熔断降级（轻量版 L2）

### 7.1 思路

不做「通用协议替换 B 站」（那是 L2，2~4 周），而是**加一个备用源，只在 B 站熔断时启用**。

- 正常时：100% 走 B 站，体验不变
- B 站风控窗口内：搜索结果为空 / 播放失败 → 自动切备用源
- 备用源只做「搜索 + 播放」，不做收藏/UP 主/分 P

这样 app **永远不会完全不可用**，而成本只有 L2 的 1/5。因为不需要覆盖 12 项能力，只需要覆盖 2 项。

### 7.2 代价

- 需要 `Track.sourceId` 之类的源标识（现在 `bvid` 是全仓 270 处的强假设，加源标识是渐进重构）
- 备用源的版权与合规风险要自己评估（社区音源接口普遍不稳定，且随时可能关停）
- UI 要能显示「当前来源」，否则用户会困惑「为什么这首歌听起来不一样」

### 7.3 什么情况下才值得做

只有当「B 站风控严重到日常不可用」时才值得。如果 S2 + S3 + S4 之后已经能正常听歌，做这个就是过度工程。

## 8. S7 / S8 简述

**S7 · 端点扩容**：取流已有「双 Web 通道 + TV 端」三级兜底（前序已落地）。可再加 `/pgc/player/web/playurl`。收益递减，因为风控是 IP 维度不是端点维度 —— **换端点不换出口，配额还是同一个**。所以这条优先级低，除非某个端点有独立配额。

**S8 · 局域网中转（NAS / 树莓派）**：L1 的家庭版。优点是不需要公网域名和证书、不受运营商 QoS、速度最快、完全私密。缺点是用户必须有 NAS 且会配 Docker。适合「自己人用」的分发场景，不适合公开。

## 9. 方案组合与顺序

```
第 0 步（5 分钟，0 代码）
  开系统代理 → 播一首 -352 的歌
    ├─ 能播 → 风控确认 IP 维度。S2 有效，且用户自己就能解
    └─ 不能播 → 问题在 CDN 侧或账号侧，S2 只能部分解决
                 → 优先确认 -352 到底出自哪个请求（看 hilog）

第 1 步（1~2 小时）
  S2 应用内代理 + 设置页「网络」分组（含测试连接、一键关、失败回落）

第 2 步（半天，可并行）
  S3 听后音频缓存 —— 这是唯一「做了就一定有用」的优化
  S4 封禁窗口落盘 + 倒计时文案

第 3 步（按需）
  S5 HTML 视频详情通道（只做 view，不碰音频直链）
  S6 备用音源（仅在 B 站日常不可用时才启动）

不建议
  S7（换端点不换出口，配额还是同一个）
  S8（门槛高，只适合自用）
```

### 推荐终态

| 手段 | 作用 | 一次改动后长期有效 |
|---|---|---|
| S2 代理 | 换出口，解 -352 | ✅ 用户自己换代理即可，不用改 app |
| S3 缓存 | 降频，减少配额消耗 | ✅ |
| S4 窗口 | 撞墙后体感可接受 | ✅ |
| S5 HTML | 单个能力的独立配额 | ⚠️ B 站改版会失效 |

三者叠加后，即使风控依旧存在，**日常听歌的成功率会有质的变化**，而且**都不需要重构架构**。

## 10. 可直接粘贴的 prompt（S2 + S3 + S4 合并版）

```
为 BiliMusic 实现三项网络层优化。不要改 Track 模型，不要动 API 层调用点。

【S2 应用内 HTTP 代理】
1. 新建 utils/AppProxy.ets（.ets 因为要用 connection 类型）：
   - init(context) 从 Preferences 读 host/port/username/password/enabled
   - current(): 返回 http.HttpProxy | null（enabled 且 host 非空才返回）
   - 静态方法即可，不要做成状态变量
2. HttpUtil.ts 的三个入口（requestText:183 / probeRedirectLocation:235 /
   requestTextWithCookies:290）的 options 字面量各加一行 usingProxy。
   注意：值为 null 时不要传该字段（SDK 要求「不配置」才走系统默认）。
3. DownloadManager.ts:1030 的 requestInStream 同样加。
4. 设置页新增「网络」分组：开关 + 4 个输入框 + 「测试连接」按钮。
   测试用 GET {BILI_API}/x/web-interface/nav，判据是
   「HTTP 200 + 可解析 + 存在 code 字段」，不要判 code === 0（未登录返回 -101 正常）。
5. 兜底：某次请求因代理连接失败时，用 usingProxy:false 重试一次，
   并把「代理回落」写进 hilog（关键字 [Proxy]）。

【S3 听后音频缓存】
6. 缓存目录 ${context.filesDir}/audio_cache，与 downloads/ 严格分开。
7. 播放超过 30 秒后，把当前音频文件落到 audio_cache；
   命中缓存时给 Track 设 localFilePath，走 MusicPlayer 既有本地分流（不要改播放内核）。
8. LRU 淘汰，总量上限 500MB；已下载（localFilePath 指向 downloads/）的曲目跳过缓存。
9. 缓存清理入口并入 pages/DownloadSettingsPage.ets:185 现有「清理缓存」，
   但必须只清 audio_cache，不要动 downloads（该页当前清的是歌词缓存，
   要区分成两个可选项或合并统计后分别清）。

【S4 封禁窗口落盘】
10. BiliRequestGate.noteRisk() 把「封禁开始时间 + 预计恢复时间（+10 分钟）」
    写进 Preferences 单键（几十字节）。
11. 启动时读取：仍在窗口内则以冷却态初始化闸门，请求排队不发。
12. 窗口结束不要一次性放开全部积压请求，要按优先级逐个放（避免解封瞬间再被封）。

【禁止】
- 不要改 Track 接口、不要改 MusicPlayer 的 source 解析逻辑
- 不要把代理配置做成 @State 传给 HttpUtil（每次请求读静态值即可）
- 不要在代理失败时静默失败
- 不要用 usingSocks5Proxy（@since 26，兼容性不够）
- 不要动 FavSyncManager
```
