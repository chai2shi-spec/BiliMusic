# 首页 · 布局优化方案

> 对象：搜索 tab 下的首页（`pages/HomePage.ets`，2655 行）+ 两个头部组件
> （`components/HomeQuickCards.ets` 429 行、`components/HomeCategoryChips.ets` 112 行）
> + 根栏标题行（`pages/Index.ets:1483-1535` `homeTitleRow`）。
> 数字都对着源码算过，行号可跳。

## 2. 首屏预算（360×780，safeTop 32，底部页签 72）

```
可视区  = 780 − 96(占位) − 72(页签) = 612vp
头部    = 56(搜索) + 184(快捷卡) + 60(chips) = 300vp   ← 占可视区 49%
列表    = 612 − 300 = 312vp → 312 / 84 = 3.71
```

**首屏只见 3 个完整曲目 + 第 4 个露 60%。**

对比：歌单详情页头部 178vp / 7 行；歌单一级页头部 84(下载行) / 6 行。**首页是三者里最挤的，头部比详情页还高 122vp。**

但有个反直觉的结论要说清：

```
滚到 248（chips 顶缘触及导航栏）：可视 = [248, 860]，对应「chips 尾 52 + 列表 560」→ 6.7 行
滚到 300（chips 完全滚出）      ：可视 = 612 全是列表        → 7.3 行
```

**首页滚一下就很高效，问题 100% 集中在「第一屏」。** 所以优化的靶心是「头 300vp 能不能少」，而不是「滚动结构改不改」。

## 3. 诊断

### D1 · 快捷卡 184vp 是最大的一块，但它服务的是「可选内容」

184 占首屏 30%，换来的可见量是 **2 张整卡**：

```
360(屏宽) − 16×2(padding) = 328 可用
卡1 156 + 间距 12 + 卡2 156 = 324         ← 两张，只剩 4vp
卡3 从 x=352 起 → 屏宽 360 下只露 8px
```

**第 3 张卡在 360 屏上完全看不见**——而「＋添加」卡正好排在第 3 位以后。也就是说，用户收藏了 2 个歌单之后，就再也找不到「添加」入口了（`QUICK_CARD_WIDTH_VP` 注释里写的「两卡半可见暗示可横滑」在 360 屏上不成立，要 400 宽才成立）。

而这行卡的内容是：
- 第 1 张「最近播放」——**恒存在**，没有播放记录时显示渐变占位 + 「暂无播放记录 / 去听点什么吧」；
- 中间 N 张收藏歌单卡——用户从歌单页 ⋯ 菜单「加入首页」自选（`HomeCardStore` 持久化）；
- 最后 1 张「+ 添加」虚线卡——**只要没满额就恒存在**。

**新用户（没有播放记录、没有收藏卡）看到的是：一张空卡 + 一个添加按钮，占 184vp。** 这是最浪费的场景，而它恰恰是新用户的第一印象。

### D2 · chips 上下各 12 的留白，占掉了 24vp

`HomeCategoryChips` 的 `Scroll` 有 `padding({ top: 12, bottom: 12 })`（`:110`），chip 本体 36 高。60vp 里 24vp 是纯留白（40%）。

而滚动 248 后 chip 条滚走、标题栏三图标接管 —— **这套「双形态」机制已经存在**，说明 chip 条本来就是「初始态的临时展示」，更应该做薄。

### D3 · chip 图标语义错位

| chip | 现在 | 问题 |
|---|---|---|
| 推荐 | `sys.symbol.play_fill` | **播放三角**表达的是「播放」，不是「推荐」 |
| 排行榜 | `sys.symbol.list_bullet` | 列表符号，看不出「榜」 |
| 音乐中心 | `sys.symbol.waveform` | 可接受 |

已在符号表（`sdk/default/openharmony/ets/build-tools/ets-loader/sysResource.js` 3372 行起）核实存在更贴切的：
- `hand_thumbsup` / `hand_thumbsup_fill`（推荐）
- `ranking` / `ranking_fill`（排行榜，与底栏同批资源）
- `wand_and_stars`（精选）

同一份 `HOME_CATEGORY_CHIPS` 常量（`HomeCategoryChips.ets:41-45`）被 chip 条**和**标题栏三图标共用（`Index.ets:1503-1508`），改一处两处同时生效。

### D4 · 标题栏在字体放大时会挤爆

`homeTitleRow`（`Index.ets:1484-1530`）在 360 屏的可用宽是 `360 − 16×2 = 328`：

```
BiliMusic 22fp ≈ 103 + 问候「晚上好」14fp ≈ 42 + space 6
+ 三图标 40×3 + 4×2 = 128 + margin left 8
+ 搜索按钮 40
= 327  ≈  328     ← 余 1vp
```

系统字体放大到 1.15 倍即溢出。问候语有 `flexShrink(1)` 兜底，但它是被牺牲的那一个 —— **第一个被截断的是「晚上好」，而不是布局本身**。

### D5 · 切 tab 后不对齐

`HomeCategoryChips` 点击只写 `STORE_SEARCH_TAB`（`:89`），`HomePage` 的 `@StorageLink` 收到后换数据源（`onListSourceChanged`），**但不动滚动位置**。

场景：用户滚到第 5 屏（偏移 ~700），在标题栏点「排行榜」→ 内容换成排行榜，但视野还停在第 5 屏的中间位置 —— **看到的是排行榜的第 20 名，而不是榜首**。

### D6 · 三图标透明占位，但这是有意的

`opacity(this.homeChipsActive ? 0 : 1)`（`Index.ets:1511`）—— 静止时三图标透明但**仍占 136vp 布局**。

这不是 bug：换成 `visibility` 会让标题区在翻转瞬间跳一下宽度。代价是字体放大时可用宽少 136（见 D4）。**这条不改，只记录。**

### D7 · 「上拉加载更多 / 已经到底啦」48 高固定条

`LIST_FOOTER_HEIGHT_VP = 48`（`InteractionConstants.ets:182`），注释说明是为了「数据落地帧尾部 extent 只增不减，防列表整体跳动」。这是对的取舍，不动。

## 4. 方案

四层，可逐层叠加：

| 层 | 做什么 | 省 | 首屏 | 风险 |
|---|---|---|---|---|
| **A 修正** | chips 36→32、padding 12→8；搜索框 margin 12→8；图标语义 | **+20** | 3.7 → 3.9 | 零 |
| **B 压缩** | 快捷卡 156×184 → 132×152 | **+32** | 3.9 → 4.3 | 低 |
| **C 折叠** | 卡片行可收起为 56 高横条 | **+128** | 4.3 → 5.8 | **中** |
| **D 对齐** | 切 tab 时滚到 chips 顶 | — | 体验修正 | 低 |

### 方案 A · 修正（零风险）

| 项 | 现在 | 改后 | 省 |
|---|---|---|---|
| chips 高 | 36 | **32** | 4 |
| chips 上下 padding | 12 / 12 | **8 / 8** | 8 |
| 搜索框下间距 | 12 | **8** | 4 |
| 图标 | play_fill / list_bullet | **hand_thumbsup / ranking** | — |

chips 从 60 → 48。chip 本体 32 高、圆角 16、图标 16、文字 12 —— 仍然满足 44vp 命中区的横向尺寸（宽 90+）。

> 32 高是**视觉高度**，命中区靠 `Row` 的 padding 撑到 36；若实测发现点击率下降，退路是保持 36 只压 padding（省 8）。

### 方案 B · 压缩快捷卡

| 项 | 现在 | 改后 |
|---|---|---|
| 卡宽 | 156 | **132** |
| 卡高 | 184 | **152** |
| 圆角 | 16 | 14 |
| 可见卡数 | 2 整 + 第 3 张露 8px | **2 整 + 第 3 张露 56px（42%）** |
| 信息条 | 小标 11 + 标题 13 + 副题 11 + 播放钮 34 | 不变（占 58 → 58） |
| 封面区 | 126 高 | **94 高** |

比例 132:152 = 0.868，仍接近竖版（1:1.15），不破坏「海报」感。封面区从 126 降到 94 —— 竖版封面裁切会更多，但 132 宽的卡本来就不是「看封面」，是「认标题」。

**B 还顺带修了一个可发现性问题**：`16 + 132 + 12 + 132 + 12 = 304`，剩 56px 露给第 3 张卡 —— 用户收藏满 2 个歌单后「＋添加」入口仍然看得见（现状只露 8px，等于消失）。

### 方案 C · 卡片行可折叠（收益最大，也最需要想清楚）

**收起态（56vp）**：一行横条代替整行卡

```
┌──────────────────────────────────────────────────┐
│ [40封面] 继续听 · 夜航星           [▶]  [⌃ 展开] │  56
└──────────────────────────────────────────────────┘
```

**展开态（152vp）**：现在的快捷卡行

**什么时候收起**：两个选项，建议**都做**——

1. **手动**：横条右端「展开 / 收起」按钮，状态存 `Preferences`（`STORE_HOME_CARDS_COLLAPSED`）。用户下次进来保持上次选择。
2. **自动**：列表偏移 > 120 时收起，回到顶部（< 40）时展开。两段式（一次 `animateTo` 改高度），不做连续 lerp。

自动收起的收益要算清：滚 120vp 后卡片让出 96vp（152−56），可视区从 `612−300+120 = 432` 变成 `+96 = 528`，行数从 5.1 到 6.3。

> ⚠️ **风险点（必须按这个顺序做）**：
> ① `ListItem` 高度变化会让下方内容位移，`List` 的 `currentOffset` 不变 → 视野内容向上跳 96vp。**必须在同一次 `animateTo` 里 `scrollBy(0, ±96)` 补偿**，否则「卡片收起」会变成「内容突然上窜」。
> ② 收起动画与 `onDidScroll` 的 `syncEntryActive/syncChipsActive` 会打架：高度动画期间偏移在变，翻转阈值可能来回抖。**收起动作期间冻结这两个同步**（加一个 `cardAnimating` 闸门，动画结束再校准一次）。
> ③ 如果 ① 补偿不干净，退路是**不做高度动画，只做透明度**：卡片 `opacity` 淡出但保留 152 占位 —— 那就等于没省空间，只能放弃这个方案。**先做 A+B，C 单独用真机验。**

### 方案 D · 切 tab 对齐（低风险，体验修正）

```ts
private onListSourceChanged(propName: string): void {
  // ... 现有逻辑
  // 切 tab：若当前偏移已越过 chips 顶缘，把 chips 顶对齐到导航栏底
  const y: number = TabScrollerHolder.home.currentOffset()?.yOffset ?? 0;
  if (y > HOME_CHIPS_TOP_VP) {                    // HOME_CHIPS_TOP_VP ≈ 240
    TabScrollerHolder.home.scrollTo({ xOffset: 0, yOffset: HOME_TABS_FLIP_VP, animation: true });
  }
}
```

对齐到 `HOME_TABS_FLIP_VP`（248）而不是 240，因为 248 正是「chips 顶缘刚好触及导航栏底」的偏移量（`96 − 248 + 240 = 88 = safeTop + 56`），可直接复用现有常量，不新增魔数。

这样用户在任何位置切 tab，都会落到「chips 已上移、列表从顶部开始」的状态 —— 与在顶部切 tab 的视觉一致。

### 方案 E · 新用户空卡场景（顺带）

`cardPlaylists.length === 0 && recentTracks.length === 0` 时，整行 184 只有一个「+ 添加」虚线卡。

改：这种状态下直接渲染**收起态横条**（56），文案「添加常用歌单到首页 ›」，点击进选择器。省 96vp，且比一张空卡更有引导性。

## 8. 风险与取舍

| 风险 | 说明 | 退路 |
|---|---|---|
| 卡 132×152 裁切变多 | 竖版封面在更方的框里裁掉更多上下 | 只降高度保 156 宽（156×160，省 24） |
| chips 32 高命中率 | 视觉 32 但触屏目标是整个 Row 40 高，实测无碍 | 保持 36，只压 padding（省 8） |
| 卡片收起跳视野 | 高度动画 + scrollBy 补偿不同步 | **先不做 C**，A+B 已 4.3 行 |
| 图标改动影响标题栏 | 单一来源，两处同时变 | 只改 chips 表里的 `icon` 字段前先看标题栏 |
| 切 tab 强制滚动打断 | 用户可能正在看某处 | 只在 `y > 240` 时对齐；`y ≤ 240` 不动 |

**建议落地顺序：A（零风险，20vp）→ D（体验修正）→ B（低风险，32vp）→ C（真机验，128vp）。**
A+B+D 之后首屏就有 4.3 行，比现状多 0.6 行；C 是「要不要为 1.2 行冒视野跳动的风险」的判断题。

## 附 · 一条不改但要记录的事

`homeTitleRow` 的三图标用 `opacity(0)` 隐藏但**保留 136vp 占位**（`Index.ets:1509-1513`）。换成 `visibility` 会让标题区在翻转瞬间跳宽度，所以这是有意取舍。

代价：字体放大到 1.15x 时，标题 + 问候 + 三图标 + 搜索 = 327vp ≈ 328 可用宽，**第一个被截断的是「晚上好」**。如果后续要治，做法不是改 `visibility`，而是给标题 Row 加 `layoutWeight(1)` 让图标区宽度固定、标题区吸收压缩 —— 这样截断的是标题区的尾部空白而不是问候语。
